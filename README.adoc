= K8S Installer
:github: https://github.com/ten1010-io/k8s-installer
:version: 1.36.0

== 개요

K8S Installer는 오프라인 환경에서 쿠버네티스 클러스터를 구성하는 도구입니다

노드 프로비저닝과 kubeadm 기반 클러스터 구성까지만 수행하며, CNI를 포함한 애드온 차트는 설치하지 않습니다.
클러스터 구성 후 CNI 플러그인은 직접 설치해야 노드가 Ready 상태가 됩니다.

== 릴리스와 쿠버네티스 버전

릴리스 버전은 이 도구가 감싸고 있는 쿠버네티스 버전입니다.

[cols="1,4"]
|===
|자리 |올라가는 때

|메이저
|쿠버네티스 메이저가 올라갈 때

|마이너
|지원하는 쿠버네티스 마이너 중 제일 높은 것이 올라갈 때

|패치
|그 밖의 전부 — 이 저장소의 수정, 패키지와 이미지 버전, 고정된 쿠버네티스 패치
|===

한 릴리스는 쿠버네티스 마이너를 최대 3개 지원하고, 그중 제일 높은 것이 곧 릴리스의 마이너입니다.
목록은 `release.yml` 의 `k8s_versions` 이고, 마이너마다 릴리스가 고정한 패치 하나를 들고 있습니다.

[source,yaml,subs="+attributes"]
----
# release.yml
version: "{version}"
k8s_versions:
  "1.36":
    kubernetes: "v1.36.4"
    pause: "3.10.2"
  "1.35":
    kubernetes: "v1.35.8"
    pause: "3.10.1"
  "1.34":
    kubernetes: "v1.34.11"
    pause: "3.10.1"
----

`pause` 는 그 마이너의 kubeadm 이 요구하는 샌드박스 이미지입니다. containerd 가 파드마다 직접
당기는 것이라 노드 설정에 들어가며, 마이너마다 다를 수 있어 패치와 함께 적어 둡니다.

클러스터가 어느 마이너로 돌지는 `vars.yml` 의 `k8s_minor_version` 이 고릅니다. 패치는 고르지
않습니다. 릴리스가 고정한 것이 쓰이므로 번들에 없는 패치를 가리킬 수 없습니다.

[source,yaml]
----
# group_vars/all/vars.yml
k8s_minor_version: "1.36"
----

그래서 릴리스를 올리는 것과 쿠버네티스 마이너를 올리는 것이 분리됩니다. 새 릴리스를 받으면
패키지와 이미지, 그리고 쿠버네티스 **패치**가 올라가고 마이너는 그 자리에 있습니다. 마이너를
올리는 것은 `k8s_minor_version` 을 한 칸 올리는 별개의 결정이며 <<클러스터 업그레이드>> 가
적용합니다. kubeadm 이 한 번에 한 마이너만 올리므로 한 칸씩만 올라갑니다.

윈도가 움직이면 제일 낮은 마이너가 지원에서 빠집니다. `1.36.x` 가 1.36/1.35/1.34 를 지원하므로
`1.37.x` 는 1.37/1.36/1.35 를 지원하고 1.34 는 더 이상 지원하지 않습니다. 1.34 에 있는 클러스터는
`1.36.x` 에서 1.35 까지 올린 뒤 `1.37.x` 로 업그레이드합니다. 그러지 않으면 업그레이드가
아무것도 건드리기 전에 그렇게 알려주고 멈춥니다.

번들은 릴리스마다 하나입니다. 릴리스 `1.36.1` 은 `bundle-1.36.1.tgz` 만 읽고, 한 번 공개된
번들은 다시 만들지 않습니다.

[NOTE]
====
패치 릴리스가 조용한 릴리스라는 뜻은 아닙니다. 패키지와 이미지가 바뀔 수 있고, 변수가 사라지거나
`inventory.yml` 에 그룹이 추가되는 변경도 패치로 나갑니다. 무엇을 고쳐야 하는지는 플레이북이
알려주고 멈추지만, 릴리스 노트를 먼저 읽으세요.
====

=== 릴리스가 고정하는 나머지

쿠버네티스만 고정되는 것이 아닙니다. 배포판이 아니라 만든 곳에서 받아 오는 패키지 —
containerd, docker, nvidia container toolkit — 와 `bundle/bin` 의 바이너리도 `release.yml` 이
버전으로 적습니다.

[source,yaml]
----
# release.yml
packages:
  containerd.io: "2.3.5"
  docker-ce: "29.8.1"
  ...
binaries:
  helm: "4.3.0"
  etcdctl: "3.6.14"
  ...
----

`install-packages.sh` 와 `install-programs.sh` 가 아무것도 설치하기 전에 번들과 대조하고,
어긋나면 무엇이 어긋났는지 적어서 멈춥니다. 번들에 아예 없는 것도 같은 실패입니다. 버전을
적어 두는 이유의 절반은 엉뚱한 곳에서 채운 디렉토리를 잡는 것이고, 빈 디렉토리는 그것의
증거가 지워진 형태입니다.

여기에 적히지 않는 것도 있습니다. `bundle/linux-packages` 의 나머지는 오프라인 설치에 필요한
의존성 묶음(systemd, libselinux, nettle 같은 것들)이고, OS 저장소가 준 그대로이며 이름도
버전도 OS 마다 다릅니다. 아무도 고른 적이 없는 것이라 적어 봐야 릴리스의 선언이 아니라 잡음이
됩니다. 쿠버네티스 패키지도 여기 없습니다 — 그쪽은 위의 `k8s_versions` 가 마이너마다 고정하고,
노드는 자기 클러스터가 도는 마이너 것만 받습니다.

비교는 업스트림 버전만 합니다. deb 는 앞에 epoch 이, 뒤에 패키징 릴리스가 붙고 rpm 은 뒤에
릴리스가 붙는데 그건 OS 마다 다른 것이 정상입니다. `28.5.2` 는 한쪽에서
`docker-ce_5:28.5.2-1~ubuntu.22.04~jammy` 로, 다른 쪽에서 `docker-ce-28.5.2-1.el8` 로 오고
둘 다 릴리스가 말하는 그 도커입니다.

바이너리는 실행해서 물어보는 수밖에 없습니다. 패키지 파일은 안에 버전을 들고 있지만
`bundle/bin` 에 있는 것은 `helm` 이라는 이름의 파일이고 이름만 봐서는 어느 helm 인지 알 수
없습니다. 도구마다 묻는 법이 달라서, `binaries` 에 이름을 더하는 것은 `install-programs.sh`
에 그 도구를 어떻게 묻는지 알려 주는 일이기도 합니다. 모르는 이름은 넘어가지 않고 멈춥니다.

==== 이 릴리스가 담고 있는 것

`release.yml` 이 말하는 그대로입니다. 그쪽이 원본이고 이 표는 읽기 편하라고 옮겨 둔 것이므로,
어긋나면 `release.yml` 이 맞습니다. 쿠버네티스는 위의 `k8s_versions` 를 보세요.

두 곳이 어긋나지 않는지는 `tools/check-release-docs.sh` 가 봅니다. 릴리스를 자르기 전에
돌리세요 — 무엇이 어긋났는지 짚어 주고 실패합니다.

== 시작하기

클러스터를 처음 세울 때 한 번 하는 일들입니다. 이미 서 있는 클러스터에 하는 일은
<<작업>> 에 있습니다.

K8S Installer는 제어 노드의 `/opt/k8s-installer`에 설치되며, 릴리스 단위로 관리됩니다.
설치된 릴리스는 `/opt/k8s-installer/release` 파일에 기록되고, 모든 관리 노드가 동일한 릴리스를 갖습니다.

*제어 노드는 반드시 `ki_cp_node` 그룹에 속해야 합니다.* `/opt/k8s-installer/ansible` 디렉토리는
`ki_cp_node` 그룹의 노드에만 배치되고 플레이북 실행 시마다 제어 노드 기준으로 동기화되므로,
제어 노드를 잃어도 다른 `ki_cp_node`에서 그대로 작업을 이어갈 수 있습니다.

제어 노드가 인벤토리의 어느 노드인지는 `inventory.yml`의 `control_node_ih`로 선언합니다.

[source,yaml]
----
control_node:
  hosts:
    localhost:
      ansible_connection: local
      control_node_ih: node1
----

=== 클러스터 설치

[source,shell,subs="+attributes"]
----
git clone {github}.git
cd k8s-installer
git checkout v{version}
./download-bundle.sh
sudo ./setup.sh

sudo /opt/k8s-installer/ansible/configure-control-node-ssh.sh   # 출력된 안내에 따라 모든 관리 노드에 SSH 설정

# /opt/k8s-installer/ansible/inventory.yml 과
# /opt/k8s-installer/ansible/group_vars/all/vars.yml 수정

source /opt/k8s-installer/venv/bin/activate
cd /opt/k8s-installer/ansible
ansible-playbook -i inventory.yml playbooks/setup-k8s-installer.yml
ansible-playbook -i inventory.yml playbooks/setup-cluster.yml
----

=== 인터넷이 없는 제어 노드

`download-bundle.sh`는 번들을 받아 프로젝트 루트에 `bundle-<릴리스 버전>.tgz` 로 둘 뿐이고,
`setup.sh`가 그 파일을 풀어 설치합니다. 제어 노드에 인터넷이 없으면 다운로드만 밖에서 하고
파일을 그대로 옮기면 됩니다.

[source,shell,subs="+attributes"]
----
# 인터넷이 되는 머신에서
./download-bundle.sh          # bundle-{version}.tgz 생성

# 매체로 옮긴 뒤, 에어갭 제어 노드의 프로젝트 루트에 같은 이름으로 배치하고
sudo ./setup.sh
----

파일명은 `release.yml`의 버전에서 정해집니다. 다른 릴리스의 번들을 가져오면 이름이 맞지
않아 `setup.sh`가 시작 단계에서 중단됩니다.

=== ephemeral-storage 전용 디스크

노드의 컨테이너 데이터는 기본적으로 루트 디스크에 쌓입니다. 이미지 하나가 크거나 파드 로그가
오래 쌓이면 루트 파일시스템이 차고 노드 전체가 불안정해집니다.

`ephemeral_storage_device` 에 블록 디바이스를 지정하면 그 디스크를 포맷해서
`/var/lib/kubelet`, `/var/log/pods`, `/var/lib/containerd` 를 전부 그 디스크로 옮깁니다.
노드마다 다르므로 보통 `inventory.yml` 에서 노드별로 지정합니다.

[source,yaml]
----
k8s_node:
  hosts:
    node4:
      ephemeral_storage_device: "/dev/disk/by-id/nvme-eui.0123456789abcdef"
----

LVM 논리 볼륨이면 `/dev/<vg>/<lv>` 도 재부팅에 안정적인 경로입니다. 어느 쪽을 적든 fstab 에는
파일시스템 UUID 로 기록되므로, 여기 적는 경로는 설치 시점에만 쓰입니다.

[IMPORTANT]
====
* 디바이스는 *포맷됩니다.* 아무것도 들어있지 않은 디스크를 지정해야 하며, 파티션 테이블이
  있거나 이미 마운트되어 있으면 플레이북이 중단됩니다
* *노드를 프로비저닝할 때만* 적용됩니다. 이미 돌고 있는 노드에 지정하면 기존 데이터가 가려진
  채 루트 디스크를 계속 점유하므로 거부합니다. 기존 노드에는 `remove-node` 후 `add-node` 로
  적용하세요
* 재부팅하면 내용이 사라지는 디스크(클라우드 instance store 등)를 지정하면 *안 됩니다.*
  이름은 ephemeral 이지만 `/var/lib/kubelet` 에는 kubelet 이 재시작 후에도 찾아야 하는
  상태가 들어 있습니다
====

지정하지 않으면(`null`) 아무것도 하지 않고 기존처럼 루트 디스크를 씁니다.
설계 판단은 link:docs/impl-notes.adoc[구현 노트]에 있습니다.

=== 파드와 서비스 서브넷

클러스터 안에서 쿠버네티스가 나눠 주는 주소입니다. 기본값은 파드 `10.244.0.0/16`, 서비스
`10.96.0.0/12` 이고, 먼저 있던 망과 부딪힐 때 `vars.yml` 에서 바꿉니다.

[source,yaml]
----
k8s_pod_subnet: "10.244.0.0/16"
k8s_service_subnet: "10.96.0.0/12"
----

[IMPORTANT]
====
* *서 있는 클러스터에서는 바꿀 수 없습니다.* 서비스 서브넷은 모든 서비스의 주소를 정하고 그중
  하나가 kubelet 이 클러스터 dns 로 아는 주소이며, 파드 서브넷은 CNI 가 그것을 전제로
  설치됩니다. `update-cluster.yml` 이 거부합니다
* `internal_network_subnets` 와 겹치면 안 됩니다. 노드와 로드밸런서, dns 서버, 레지스트리가
  그 대역에 있어서 겹치면 파드에서 그것들에 닿지 못합니다. 플레이북이 시작 전에 봅니다
* *CNI 에도 같은 값을 줘야 합니다.* 설치본은 CNI 를 깔지 않으므로, 다른 파드 서브넷으로 올린
  CNI 는 노드가 영영 Ready 가 되지 않는 것으로만 드러납니다
====

두 줄 다 있어야 합니다. 지우면 기본값으로 떨어지지 않고 플레이북이 시작 전에 멈춥니다.

|<<설정 변경 적용>>

|새 릴리스로 올린다
|<<K8S Installer 업그레이드>> 후 <<클러스터 업그레이드>>

|쿠버네티스 마이너를 올린다
|<<릴리스와 쿠버네티스 버전>> 후 <<클러스터 업그레이드>>

|제어 노드를 다른 노드로 옮긴다
|<<제어 노드 인계>>

|노드가 죽어서 접속이 안 된다
|<<고장난 노드 제거>>

|클러스터를 걷어낸다
|<<클러스터 제거>>
|===

=== 설정 변경 적용

`vars.yml` 이나 `inventory.yml` 을 고친 뒤 이미 서 있는 클러스터에 반영합니다.

[source,shell]
----
source /opt/k8s-installer/venv/bin/activate
cd /opt/k8s-installer/ansible
ansible-playbook -i inventory.yml playbooks/update-cluster.yml
----

각 노드가 마지막으로 무엇을 가지고 만들어졌는지 기록해 두므로, 무엇이 달라졌는지 스스로
알아내고 변수마다 정해진 방법으로 적용합니다. 바꿀 수 없는 변수나 노드를 다시 만들어야 하는
변수가 섞여 있으면 **아무것도 적용하지 않고** 어느 노드의 어떤 변수가 문제인지 알려준 뒤
멈춥니다. 적용 방법은 `ansible/group_vars/all/constant-vars.yml` 의 `ki_var_classes` 에
변수별로 적혀 있고, 자세한 근거는 `docs/impl-notes.adoc` 에 있습니다.

`k8s_minor_version` 은 여기서 적용되지 않습니다. 쿠버네티스를 옮기는 것은 kubeadm 이 하는 일이고
이 플레이북은 그것을 하지 않으므로, 바뀌어 있으면 <<클러스터 업그레이드>> 를 부르라고 알려준 뒤
멈춥니다.

NOTE: 기록에 없는 것은 변경이 아닙니다. 기록이 아예 없는 노드도, 릴리스가 새로 더해서 기록에만
없는 변수도, 첫 실행은 지금 값을 기준점으로 삼고 그렇게 알려 줍니다. 변경 감지는 그 다음
실행부터입니다.

=== apiserver 에 인자와 볼륨 더하기

클러스터가 반드시 켜고 돌아야 하는 apiserver 옵션 — 감사 정책, oidc 발급자, feature gate,
`runtime-config` — 을 `vars.yml` 에 적습니다. 설치본은 이것들에 대해 의견을 갖지 않고 그대로
넘깁니다.

[source,yaml]
----
k8s_apiserver_extra_args:
  - name: audit-policy-file
    value: /etc/kubernetes/audit/policy.yaml
  - name: audit-log-path
    value: /var/log/kubernetes/audit/audit.log
k8s_apiserver_extra_volumes:
  - name: audit
    hostPath: /etc/kubernetes/audit
    mountPath: /etc/kubernetes/audit
    readOnly: true
  - name: audit-log
    hostPath: /var/log/kubernetes/audit
    mountPath: /var/log/kubernetes/audit
    pathType: DirectoryOrCreate
----

인자의 `name` 에는 대시를 붙이지 않습니다. 여러 번 줄 수 있는 플래그는 여러 줄로 적습니다.

값은 클러스터의 kubeadm 설정에 들어갑니다. 그래서 나중에 들어오는 컨트롤 플레인 노드와
업그레이드가 지나가는 모든 노드에 그대로 적용되고, 정적 파드 매니페스트를 손으로 고쳤을 때처럼
다음 업그레이드에 지워지지 않습니다.

[IMPORTANT]
====
*볼륨은 컨트롤 플레인 노드의 호스트 경로이고, 그 경로에 파일을 놓아 주는 것은 설치본이 하지
않습니다.* 없는 파일을 가리키는 인자는 뜨지 않는 apiserver 입니다. 파일을 모든 컨트롤 플레인
노드에 먼저 놓고 값을 바꾸세요.
====

그렇게 되면 kubeadm 이 그 노드의 매니페스트를 되돌립니다. 노드는 5분쯤 뒤 예전 설정으로 스스로
돌아오고, 그 사이 자기 apiserver 가 없어서 `NotReady` 로 보입니다. 첫 노드에서 멈추므로 뒤
노드는 손대지 않고, 값을 고치는 것은 노드를 살리기 위해서가 아니라 변경을 반영하기 위해서입니다.

이미 서 있는 클러스터에 반영하는 것은 <<설정 변경 적용>> 입니다. 설정을 올린 뒤 컨트롤 플레인
노드를 한 대씩 로드밸런서에서 빼고 매니페스트를 다시 쓰고 다시 넣습니다. 3노드에서 6분쯤
걸립니다.

=== 사용자 레지스트리

클러스터에는 레지스트리가 둘 있습니다. kubeadm 이 쓰는 것(`ki-cp-k8s-registry`, 5000)은 릴리스가
채우고, 워크로드가 쓰는 것(`ki-cp-user-registry`, 5001)은 여기서 채웁니다.

담을 이미지를 `ki-cp-user-registry-images.yml` 에 선언합니다.
`ki-cp-user-registry-images.yml.example` 을
복사해서 쓰면 됩니다. 그 다음 **이미지를 받을 수 있는 곳에서** 아카이브를 만듭니다.

[source,shell]
----
./download-bundle.sh                        # crane 이 번들에 들어 있습니다
tools/build-user-registry-images.sh
----

나온 `ki-cp-user-registry-images.tgz` 를 매체로 반입한 뒤, 제어 노드에서 밀어 넣습니다.

[source,shell]
----
source /opt/k8s-installer/venv/bin/activate
cd /opt/k8s-installer/ansible
ansible-playbook -i inventory.yml playbooks/push-user-registry-images.yml \
  -e archive=/media/usb/ki-cp-user-registry-images.tgz
----

모든 ki cp 노드에 같은 내용이 들어갑니다. 파드는 그때 VIP 를 들고 있는 노드에서 당기므로 노드마다
내용이 다르면 같은 파드가 어디에 스케줄되느냐에 따라 뜨기도 하고 안 뜨기도 합니다. 그래서
레지스트리는 읽기 전용으로 돌고 **직접 push 는 막혀 있습니다.**

**ki cp 노드를 추가하면 그 노드의 레지스트리도 같은 내용으로 채워집니다.** `add-node` 가 이미 서비스
중인 다른 ki cp 노드에서 복사해 옵니다. 내용은 이미 에어갭 안쪽에 있으니 아카이브를 다시 반입할 필요가
없습니다. 노드 수에 비례해 오래 걸리는 것이 아니라, 레지스트리에 담아 둔 양에 비례해 오래 걸립니다.

노드의 디스크를 잃었거나 `remove-broken-node` 뒤에 되살린 경우처럼 따로 맞춰야 할 때는:

[source,shell]
----
ansible-playbook -i inventory.yml playbooks/sync-user-registry.yml
----

맞는지 물어보기만 하려면:

[source,shell]
----
ansible-playbook -i inventory.yml playbooks/check-user-registry.yml
----

`check` 는 보고만 합니다. 어긋난 채로 두면 그 노드가 VIP 를 드는 순간부터 그 이미지를 당기는 파드가
실패하는데, 레지스트리는 정상 응답하고 카탈로그만 짧아서 **아무것도 티가 나지 않습니다.** 첫 신호가
"어떤 노드에 스케줄되면 뜨고 어떤 노드면 안 뜨는 파드" 이고, 그때는 원인에서 한참 떨어져 있습니다.
그래서 `add-node`, `push-user-registry-images`, `prune-user-registry` 끝에서 자동으로 돌아갑니다.

워크로드에서는 이렇게 씁니다.

[source,yaml]
----
image: ki-cp.ki.local:5001/library/nginx:1.25
----

==== 사용자 레지스트리 정리

push 는 더하기만 하므로 레지스트리는 계속 커집니다. 목록 파일에 없는 것을 지우려면:

[source,shell]
----
# 무엇이 지워질지만 봅니다
ansible-playbook -i inventory.yml playbooks/prune-user-registry.yml \
  -e keep=/path/to/ki-cp-user-registry-images.yml

# 실제로 지웁니다
ansible-playbook -i inventory.yml playbooks/prune-user-registry.yml \
  -e keep=/path/to/ki-cp-user-registry-images.yml -e delete=
----

[WARNING]
====
에어갭 안의 레지스트리는 그 이미지의 유일한 사본입니다. 지운 이미지를 되돌리려면 다시 반입해야
하므로, `-e delete=` 없이 먼저 목록을 확인하세요.
====

=== 인증서 갱신

kubeadm 이 발급한 컨트롤 플레인 인증서를 갱신합니다. 서비스는 끊기지 않습니다.

[source,shell]
----
source /opt/k8s-installer/venv/bin/activate
cd /opt/k8s-installer/ansible
ansible-playbook -i inventory.yml playbooks/renew-certs.yml
----

컨트롤 플레인 노드를 한 대씩 돌면서, 그 노드를 모든 ki cp 노드의 로드밸런서에서 뺀 뒤 갱신하고,
다시 넣어 트래픽을 받는 것까지 확인한 다음 다음 노드로 넘어갑니다. 3노드 기준 3분 남짓 걸립니다.

중간에 실패하면 그 노드를 로드밸런서에 되돌려 놓고 멈추므로, 작업 전과 같은 노드들이 서비스하는
상태로 남습니다. 뒤 노드는 손대지 않습니다.

NOTE: 워커 노드는 대상이 아닙니다. kubeadm 이 발급한 인증서를 갖지 않고, kubelet 이 쓰는 것은
kubelet 이 스스로 갱신합니다.

=== etcd 백업

각 k8s cp 노드가 자기 etcd 스냅샷을 받아 노드 안에 보관합니다. 클러스터를 바꾸는 플레이북
(`remove-node`, `renew-certs`, `upgrade-cluster`)이 시작 전에 자동으로 한 번 받고, 따로 돌릴 수도
있습니다.

[source,shell]
----
source /opt/k8s-installer/venv/bin/activate
cd /opt/k8s-installer/ansible
ansible-playbook -i inventory.yml playbooks/backup-etcd.yml
----

스냅샷은 각 노드의 `/var/lib/k8s-installer/etcd-backups` 에 UTC 타임스탬프 이름으로 쌓이고,
`ki_etcd_backup_retention_count`(기본 5)를 넘는 오래된 것부터 지워집니다. 제어 노드 루트
파일시스템에 쌓이므로 개수를 두지 않으면 디스크가 찹니다.

받은 직후 `etcdutl snapshot status` 로 읽어 보고, 읽히지 않으면 그 파일을 지우고 실패합니다.
쓸 수 없는 스냅샷을 보관해 두면 정작 필요할 때 알게 됩니다.

NOTE: 스냅샷은 노드 안에만 있습니다. 노드를 잃으면 그 노드의 스냅샷도 같이 잃으므로, 정기적으로
노드 밖으로 복사해 두세요. 에어갭이라 설치본이 대신 보낼 곳을 가정할 수 없습니다.

=== etcd 복구

WARNING: 복구는 클러스터의 상태를 스냅샷 시점으로 되돌립니다. 그 뒤에 쓰인 것은 전부 사라지고,
복구된 클러스터는 기존 클러스터를 고친 것이 아니라 새 클러스터입니다. 되돌릴 수 없습니다.

복구할 스냅샷을 제어 노드로 가져온 뒤 경로를 지정합니다. 어느 노드의 어느 스냅샷을 쓸지는
무엇이 잘못됐는지에 달려 있어서 설치본이 대신 고르지 않습니다.

[source,shell]
----
# 스냅샷을 제어 노드로 가져옵니다
scp root@<노드>:/var/lib/k8s-installer/etcd-backups/etcd-<타임스탬프>.db /tmp/

source /opt/k8s-installer/venv/bin/activate
cd /opt/k8s-installer/ansible
ansible-playbook -i inventory.yml playbooks/restore-etcd.yml \
  -e etcd_snapshot=/tmp/etcd-<타임스탬프>.db \
  -e confirm_data_loss=
----

모든 k8s cp 노드가 **같은** 스냅샷으로 복구됩니다. etcd 가 그것을 요구합니다. 서로 다른
스냅샷에서 복구된 멤버들은 클러스터를 이루지 못합니다.

기존 데이터 디렉토리는 지우지 않고 `/var/lib/etcd.replaced-<타임스탬프>` 로 이름만 바꿔 둡니다.
잘못된 스냅샷으로 복구한 것을 알게 되는 시점에는 이미 스냅샷을 받을 대상이 없기 때문입니다.
확인이 끝나면 직접 지우세요.

=== 인증서 만료 확인

만료가 임박한 인증서를 보고합니다. `add-node`, `remove-node` 끝에서 자동으로 돌고, 따로 돌릴 수도 있습니다.

[source,shell]
----
source /opt/k8s-installer/venv/bin/activate
cd /opt/k8s-installer/ansible
ansible-playbook -i inventory.yml playbooks/tasks/check-cert-expiry.yml
----

기본 임계치는 180일이며 `ki_cert_expiry_warning_days`로 바꿉니다. 보고만 하고 실패시키지는 않습니다.

|===
|인증서 |유효기간 |만료 시 대응

|kubeadm 인증서 (`/etc/kubernetes/pki`)
|3년
|`kubeadm certs renew`. `kubeadm upgrade` 시 자동 갱신됨

|kubeadm CA
|10년
|클러스터 재구축

|ki PKI (`/etc/k8s-installer/pki`)
|10년
|*클러스터 재구축.* CA와 리프가 같은 날 만료되므로 리프만 재발급하는 경로가 성립하지 않습니다
|===

ki PKI가 만료되면 레지스트리 TLS가 깨져 모든 노드에서 이미지 pull이 실패합니다.
설치 시점 + 10년이 이 배포의 하드 리밋이고, 재설치할 때마다 초기화됩니다.

같은 측정을 모니터링 시스템이 읽을 수 있게 파일로도 남깁니다. <<인증서 만료 메트릭>> 을 보세요.

=== 클러스터 업그레이드

새 릴리스가 담고 있는 것들을 실제 클러스터에 적용합니다. 쿠버네티스뿐 아니라 리눅스 패키지
(containerd, docker, kubelet 등), 유저 바이너리(helm, etcdctl 등), 레지스트리 이미지,
ki cp 서비스 이미지가 모두 대상입니다.

`k8s_minor_version` 을 올려 두었다면 쿠버네티스 마이너도 여기서 올라갑니다. 그대로라면 릴리스가
그 마이너에 고정한 패치까지만 올라갑니다. 어느 쪽이든 아무것도 건드리기 전에 확인합니다 —
클러스터가 기록한 버전을 읽어서, 이 릴리스가 그 마이너를 지원하는지와 한 마이너 안의 이동인지를
보고 아니면 멈춥니다.

[source,shell]
----
source /opt/k8s-installer/venv/bin/activate
cd /opt/k8s-installer/ansible
ansible-playbook -i inventory.yml playbooks/upgrade-cluster.yml
----

레지스트리를 먼저 채우고, ki cp 서비스를 한 노드씩 올린 뒤, 노드를 하나씩 drain 하여 패키지와
쿠버네티스를 올리고 다시 투입합니다. 3노드 기준 4분 남짓 걸립니다.

[WARNING]
====
실패해도 되돌리지 않습니다. kubeadm 이 클러스터 버전과 저장된 데이터를 옮기므로 되돌리는 쪽이
더 위험합니다. 어느 노드까지 끝났는지 알려주고 멈추며, **다시 실행하면 이미 새 버전인 노드는
건너뛰고 멈춘 자리에서 이어집니다.**

멈춘 동안 클러스터는 두 버전이 섞인 상태입니다. 쿠버네티스는 컨트롤 플레인과 kubelet 사이
한 마이너 버전 차이를 허용하므로 그 범위에서는 동작하지만, 오래 두지 마세요.
====

==== 레지스트리 정리

업그레이드는 새 릴리스의 이미지를 레지스트리에 밀어 넣을 뿐 옛 이미지를 지우지 않습니다. 그래서
클러스터를 거쳐 간 모든 릴리스가 그대로 남습니다. 3노드 클러스터를 세우고 마이너를 한 번 올린
직후 노드마다 다음과 같았습니다.

----
kube-apiserver: v1.34.1, v1.35.0
etcd:           3.6.4-0,  3.6.6-0
coredns:        v1.12.1,  v1.13.1
                                      합계 355M
----

지금 번들에 없는 것을 지웁니다.

[source,shell]
----
source /opt/k8s-installer/venv/bin/activate
cd /opt/k8s-installer/ansible

# 무엇이 지워질지만 봅니다
ansible-playbook -i inventory.yml playbooks/prune-k8s-registry.yml

# 실제로 지웁니다
ansible-playbook -i inventory.yml playbooks/prune-k8s-registry.yml -e delete=
----

사용자 레지스트리 정리와 달리 목록 파일을 주지 않습니다. 번들이 곧 릴리스이고, 릴리스 중에서
클러스터가 돌리는 것은 `k8s_minor_version` 이 고른 마이너이므로, 무엇을 남길지는 번들에서 그
마이너의 이미지 디렉터리가 이미 답하고 있습니다. 번들에 같이 들어 있는 다른 마이너의 이미지는
이 클러스터가 돌리지 않는 것이라 남기지 않습니다.

[NOTE]
====
업그레이드에 딸려 돌지 않습니다. 업그레이드는 노드를 하나씩 올리므로 중간에 멈추면 앞 노드는
새 릴리스, 뒤 노드는 옛 릴리스인 상태가 되는데, 이때 지워질 이미지가 바로 뒤 노드들이 아직
당겨야 할 것들입니다. 클러스터가 한 버전으로 온전해진 뒤에 부르세요.

잘못 지웠으면 `upgrade-cluster.yml` 이 레지스트리를 번들에서 다시 채웁니다. 매체를 다시
반입해야 하는 사용자 레지스트리와 다른 점입니다.
====

[WARNING]
====
지운 자리를 실제로 되찾으려면 레지스트리가 저장소를 훑어야 하고, 그동안은 레지스트리를 내려야
합니다. 노드를 하나씩 처리하지만 레지스트리는 VIP 로 직접 붙으므로, **VIP 를 들고 있는 노드
차례에는 클러스터 어디에서도 이미지를 당길 수 없습니다.**

3노드에서 2노드 분량을 정리하는 데 36초가 걸렸고, 그중 VIP 를 통한 요청이 실패한 것은 1초였습니다.
파드가 새로 뜨지 않는 시간에 부르세요.
====

=== 스냅샷 릴리스

`-SNAPSHOT` 으로 끝나는 버전은 개발용 빌드입니다. 같은 이름으로 내용이 계속 바뀌므로
두 노드가 같은 스냅샷을 보고해도 같은 것을 들고 있다고 볼 수 없고, 따라서 **업그레이드의
출발점이 될 수 없습니다.**

[cols="1,1,3"]
|===
|설치된 버전 |목표 버전 |판정

|릴리스 |릴리스 |`upgradable_from` 에 있으면 허용
|릴리스 |스냅샷 |허용. 릴리스를 내기 전 업그레이드 경로를 시험하는 용도
|스냅샷 |동일 스냅샷 |허용. 업그레이드가 아니라 **재배포**이며 개발 중 몇 번이든 가능
|스냅샷 |그 외 |**거부.** `reset.sh` 후 `setup.sh` 로 재구축
|===

릴리스를 낼 때는 `release.yml` 의 `version` 에서 `-SNAPSHOT` 을 떼고 커밋한 뒤 태그를 붙이고,
다음 개발 버전으로 다시 올립니다. 이 문서의 `:version:` 속성은 사용자가 체크아웃할 태그를 가리키므로
릴리스 버전까지만 올리고, 다음 개발 버전으로는 올리지 않습니다.

[source,shell]
----
# 개발 중        version: "1.36.1-SNAPSHOT"    태그 없음
# 릴리스         version: "1.36.1"   → commit → git tag v1.36.1
# 다음 개발      version: "1.36.2-SNAPSHOT"
----

다음 개발 버전은 패치를 올린 것입니다. 쿠버네티스 마이너를 하나 더 지원하게 되는 릴리스라면
`k8s_versions` 의 제일 높은 키가 올라가므로 그때는 `1.37.0-SNAPSHOT` 입니다.
<<릴리스와 쿠버네티스 버전>> 을 보세요.

번들도 릴리스마다 하나이므로 스냅샷은 스냅샷의 번들을 읽습니다. 이름이 그대로인 채 내용이 바뀌는
유일한 번들이고, 공개된 릴리스 번들을 덮어쓸 수 없는 곳에 두어야 합니다.

=== 제어 노드 인계

제어 노드가 인벤토리의 어느 노드인지는 `inventory.yml`의 `control_node_ih`가 선언합니다.
옮기는 것은 그 선언 한 줄과 SSH 키뿐입니다. `ki_cp_node` 는 모두 같은 `ansible` 디렉토리를
들고 있으므로 옮겨 갈 노드에 이미 필요한 것이 다 있습니다.

인계받을 `ki_cp_node`에서 `control_node_ih`를 그 노드로 바꾸고, 그 노드의 SSH 키를 관리 노드에 심으면 됩니다.
SSH 설정 스크립트는 ansible 디렉토리에 함께 동기화되므로 소스 트리를 다시 받을 필요가 없습니다.

[source,shell]
----
# 인계받을 ki_cp_node 에서
vi /opt/k8s-installer/ansible/inventory.yml    # control_node_ih: node2
sudo /opt/k8s-installer/ansible/configure-control-node-ssh.sh   # 출력된 안내에 따라 모든 관리 노드에 SSH 설정
----

선언이 실제로 플레이북을 실행하는 노드를 가리키지 않으면 모든 플레이북이 시작 단계에서 중단됩니다.

=== 고장난 노드 제거

접속이 되지 않는 노드는 `remove-node` 로 뺄 수 없습니다. 그 플레이북이 하는 일의 대부분이
빼려는 노드 위에서 이뤄지기 때문입니다. 접속되지 않는 노드는 `inventory.yml` 의 `broken_node`
그룹에 넣습니다.

[source,yaml]
----
broken_node:
  hosts:
    node2: {}
----

그룹에 넣는 것만으로 *모든 플레이북이 그 노드를 건너뜁니다.* 노드 한 대가 죽었다고 해서
나머지 노드에 대한 작업까지 막히지 않게 하는 것이 이 그룹의 목적이고, 클러스터에서 빼는 것은
그 다음 문제입니다.

[source,shell]
----
source /opt/k8s-installer/venv/bin/activate
cd /opt/k8s-installer/ansible
ansible-playbook -i inventory.yml playbooks/remove-broken-node.yml -e fenced=
----

살아있는 노드들에서만 동작합니다. 클러스터에서 노드와 etcd 멤버를 지우고, 남은 `ki_cp_node`
들의 서비스를 그 노드가 없는 구성으로 다시 만듭니다. 노드 자체는 아무것도 정리하지 않습니다.
정리할 대상에 닿을 수 없기 때문입니다.

.전제 조건
* *전원을 내리거나 네트워크에서 격리한 뒤* 실행해야 합니다. 접속이 안 될 뿐 살아있는 노드는
  여전히 가상 IP를 주장하고 레지스트리를 서빙합니다. 플레이북은 접속 불가까지만 확인할 수
  있으므로, 격리했다는 사실은 `-e fenced=` 로 사람이 선언합니다
* 고장난 노드가 제어 노드라면 *다른 `ki_cp_node` 로 제어 노드를 먼저 인계*하세요
* 고장난 노드가 `k8s_cp` 라면 *etcd 쿼럼이 남아 있어야 합니다.* 노드를 지우는 것도 etcd 멤버를
  빼는 것도 쓰기 작업입니다. cp 노드가 2대인 구성에서는 1대만 잃어도 쿼럼이 깨지므로 이 경로로는
  고칠 수 없고, etcd 복구가 먼저입니다
* 남은 `ki_cp_node` 가 한 대뿐이라면 서비스를 다시 만드는 동안 가상 IP가 잠깐 사라집니다.
  넘겨받을 상대가 없기 때문입니다

[IMPORTANT]
====
*제거한 머신을 그대로 다시 켜지 마세요.* kubelet이 이 클러스터가 받아주는 인증서를 그대로
들고 있어서 노드 등록을 계속 시도합니다. 워커였다면 성공해서 설치기가 모르는 노드로 되살아나고,
컨트롤 플레인이었다면 kubelet이 자기 노드의 apiserver를 보는데 그 apiserver에 붙을 etcd가
없어서 크래시루프만 돕니다. 어느 쪽이든 재투입은 OS 재설치부터입니다.
====

되돌릴 때는 노드를 재설치하고 `broken_node` 그룹에서 뺀 뒤 `setup-k8s-installer.yml`,
`add-node.yml` 순으로 실행합니다. ki PKI는 살아있는 `ki_cp_node` 에서 복사됩니다.

=== 클러스터 제거

[source,shell]
----
source /opt/k8s-installer/venv/bin/activate
cd /opt/k8s-installer/ansible
ansible-playbook -i inventory.yml playbooks/reset-cluster.yml
ansible-playbook -i inventory.yml playbooks/reset-k8s-installer.yml
deactivate

sudo /opt/k8s-installer/ansible/reset-control-node-ssh.sh   # 출력된 안내에 따라 모든 관리 노드의 SSH 설정 제거
sudo /opt/k8s-installer/reset.sh
----

==== 클러스터가 응답하지 않을 때

`reset-cluster.yml` 은 먼저 apiserver 에게 노드 객체를 지워 달라고 합니다. **클러스터가 끝까지
서지 못했거나 컨트롤 플레인이 이미 없으면** 그 단계에서 멈춥니다 — 지울 것이 없는데 지우러 가는
셈입니다. `-e sdfc=` 로 그 단계만 건너뜁니다.

[source,shell]
----
ansible-playbook -i inventory.yml playbooks/reset-cluster.yml -e sdfc=
----

뒤의 단계는 전부 노드 자체에 하는 일이라 그대로 돕니다. `setup-cluster.yml` 이 중간에 실패해
다시 돌리려 할 때 필요합니다 — 그 시점의 노드에는 설치본이 깐 containerd 가 이미 있어서
`check-node-state.sh` 가 재실행을 거부하므로, 먼저 이 명령으로 되돌린 뒤 다시 설치합니다.

`remove-node.yml` 에도 같은 옵션이 있습니다. 다만 그쪽은 노드가 클러스터에 등록된 채로 남으므로,
apiserver 가 돌아온 뒤 `kubectl delete node` 로 직접 빼야 합니다.

== 모니터링

설치본이 내보내는 것을 사이트의 수집기에 물리는 방법입니다. 수집기 자체는 깔지 않습니다 —
이미 돌리고 있는 것을 쓰시면 됩니다.

ki cp 서비스는 노드에서 도커 컨테이너로 돕니다. 쿠버네티스 오브젝트가 아니라서 클러스터 안의
수집기가 서비스 디스커버리로 찾지 못하므로, 긁으려면 주소를 직접 적어 줘야 합니다. 노드의
인증서 만료처럼 긁을 표면이 아예 없는 것은 파일로 남깁니다. 무엇을 적고 어디를 봐야 하는지가
여기에 있습니다.

=== apiserver 로드밸런서

각 ki cp 노드의 stats 포트(18404)가 `/metrics` 에 프로메테우스 형식으로 답합니다. 인증은 없고,
그 포트는 루프백과 노드의 내부망 주소에만 열려 있습니다. VIP 에는 올라가지 않아 VIP 로는 아예
긁힐 수 없으므로 — 연결이 거부됩니다 — **노드마다** 따로 긁어야 합니다. 백엔드를 빼 둔
노드가 어느 것인지도 그 노드를 직접 물어야 알 수 있습니다.

[source]
----
http://<노드 내부망 주소>:18404/metrics
----

같은 포트의 `/` 는 사람이 보는 stats 페이지이고 `admin` + 클러스터마다 생성된 비밀번호를
요구합니다. 비밀번호는 각 ki cp 노드의
`/etc/k8s-installer/services/ki-cp-k8s-cp-lb/stats-password` 에 있습니다.

`/lb-healthz` 는 keepalived 가 쓰는 자리라 감시 대상으로 삼지 마세요. 로드밸런서가 살아 있는지만
답하고 백엔드 상태는 일부러 보지 않습니다.

NOTE: 이미 서 있는 클러스터에는 <<클러스터 업그레이드>> 가 반영합니다. <<설정 변경 적용>> 은
바뀐 변수가 있을 때만 서비스를 다시 쓰므로 이 변경만으로는 반영되지 않습니다.

=== 인증서 만료 메트릭

각 노드가 자기 인증서의 만료를 파일로 씁니다. 형식은 node exporter 의 textfile collector 가
읽는 것이고, 수집기 자체는 설치본이 깔지 않습니다.

[source]
----
/var/lib/k8s-installer/metrics/certificate-expiry.prom
----

[source]
----
# HELP ki_certificate_not_after_seconds Unix time at which the certificate expires
# TYPE ki_certificate_not_after_seconds gauge
ki_certificate_not_after_seconds{path="/etc/kubernetes/pki/apiserver.crt"} 1852934400
ki_certificate_not_after_seconds{path="/etc/k8s-installer/pki/ki-ca.crt"} 2074204800
...
----

node exporter 를 이 디렉토리로 향하게 하면 됩니다. 로드밸런서와 달리 긁을 주소가 아니라
읽을 디렉토리이므로, 노드마다 수집기를 따로 겨눌 필요는 없습니다.

[source,shell]
----
node_exporter --collector.textfile.directory=/var/lib/k8s-installer/metrics
----

남은 일수가 아니라 만료 시각입니다. 얼마나 남았는지는 읽는 쪽에서 빼서 씁니다.

[source]
----
(ki_certificate_not_after_seconds - time()) / 86400 < 180
----

주기적으로 다시 쓰지 않습니다. 만료 시각은 인증서가 발급되거나 갱신될 때만 바뀌고, 그 둘은
모두 플레이북이 하는 일이기 때문입니다. 클러스터 설치·노드 추가·인증서 갱신·클러스터 업그레이드가
끝나면서 파일이 다시 쓰이므로, 놓여 있는 값은 계속 맞습니다.

NOTE: <<인증서 만료 확인>> 을 직접 돌려도 같은 파일이 쓰입니다. 이 기능이 들어오기 전에 설치된
클러스터에 파일을 만드는 방법이기도 합니다.

== 지원하는 쿠버네티스 버전

이 릴리스가 지원하는 쿠버네티스 버전입니다. 마이너마다 릴리스가 패치 하나를 고정하며, 클러스터가
어느 마이너로 돌지는 `vars.yml` 의 `k8s_minor_version` 이 고릅니다. 목록의 출처는
`release.yml` 의 `k8s_versions` 이고, 자세한 것은 <<릴리스와 쿠버네티스 버전>> 에 있습니다.

[cols="1,1,3"]
|===
|마이너 |이 릴리스가 고정한 패치 |비고

|1.36
|v1.36.4
|이 릴리스의 마이너. 새로 설치할 때의 기본값

|1.35
|v1.35.8
|

|1.34
|v1.34.11
|윈도의 제일 아래. 다음 마이너 릴리스에서 빠집니다
|===

세 마이너의 패키지와 이미지를 번들이 모두 들고 가므로, 릴리스를 그대로 두고 마이너만 올리는 데는
매체를 다시 반입할 필요가 없습니다. 아래 <<지원하는 운영체제>> 의 모든 운영체제에 대해 세 마이너가
다 들어 있습니다.
