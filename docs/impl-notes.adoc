= 구현 노트

여러 파일에 걸쳐 있어서 한 곳의 주석으로는 담기지 않는 설계 판단을 기록합니다.
한 파일만 봐서는 왜 그렇게 되어 있는지 드러나지 않는 것만 남기고, 한 파일 안에서 설명되는
내용은 그 파일의 주석에 둡니다.

== ephemeral-storage 전용 디스크

노드의 컨테이너 데이터가 전부 루트 디스크에 쌓이면 이미지 하나나 오래 쌓인 파드 로그가
루트 파일시스템을 채우고, 그 시점에 노드 전체가 불안정해집니다. `ephemeral_storage_device`
를 선언한 노드는 그 디스크를 포맷해 ephemeral-storage 회계 대상 경로 전체를 옮깁니다.

=== 대상 경로

kubelet이 파드의 ephemeral-storage 사용량으로 세는 것은 세 가지고, 그래서 옮기는 경로도
셋입니다.

[cols="2,3"]
|===
|경로 |담기는 것

|`/var/lib/kubelet`
|emptyDir (`pods/<uid>/volumes/kubernetes.io~empty-dir`)

|`/var/log/pods`
|컨테이너 로그. `/var/log/containers` 의 심볼릭 링크가 이 아래를 가리킵니다

|`/var/lib/containerd`
|컨테이너 writable layer 와 이미지
|===

디스크 하나를 세 경로에 동시에 마운트할 수는 없습니다. 베이스 마운트포인트
(`ki_ephemeral_root_path`) 를 하나 두고 그 하위 디렉토리를 각 경로로 bind mount 합니다.

----
/dev/disk/by-uuid/<uuid>   →  <base>                  (실제 마운트)
<base>/kubelet             →  /var/lib/kubelet        (bind)
<base>/pod-logs            →  /var/log/pods           (bind)
<base>/containerd          →  /var/lib/containerd     (bind)
----

`/var/log/pods` 는 kubelet이 처음 뜰 때 생기므로 마운트포인트를 미리 만들어 둡니다.

=== root path 변경이 아니라 bind mount 인 이유

*`/var/log/pods` 에는 kubelet 설정 플래그가 없습니다.* 하드코딩이라 bind mount 외에는 옮길
방법이 없고, 이 항목 하나로 방식이 결정됩니다.

`/var/lib/kubelet` 은 `--root-dir` 로 옮길 수 있지만 CSI 드라이버와 node-driver-registrar,
로그 수집 DaemonSet 등 외부 매니페스트가 이 경로를 hostPath 로 하드코딩합니다. 경로를 바꾸면
가져다 쓰는 차트마다 손을 대야 합니다.

containerd 만 `root =` 로 옮기고 나머지 둘은 bind mount 하는 혼종보다 세 경로를 한 방식으로
통일하는 편이 낫습니다. 그래서 `containerd_root_path` 변수를 없앴습니다 (아래 참고).

=== 세 경로가 용량을 공유합니다

한 파일시스템을 셋이 나눠 쓰므로 이미지가 디스크를 채우면 파드 로그와 emptyDir 도 같이
죽습니다. LVM 으로 나누면 격리되지만 공간이 낭비되고 운영이 복잡해져서 택하지 않았습니다.

kubelet 이 nodefs 와 imagefs 를 같은 파일시스템으로 보게 되는데, 이건 kubelet 의 기본
가정이고 `create-kubelet-reservations.py` 가 원래부터 그렇게 계산합니다.

=== 파일시스템을 ext4 로 고정한 이유

overlayfs 상성과 프로젝트 쿼타만 보면 XFS 가 낫지만 쓸 수 없습니다. K8S Installer는 패키지를
`bundle/linux-packages/` 에 번들해서 설치하는 오프라인 구조인데, 디스크를 마운트하는 시점은
`install-packages` 보다 *앞* 입니다. 즉 `xfsprogs` 가 스톡 이미지에 없으면 그 시점에
설치할 방법이 없습니다. RHEL 8 은 기본 탑재지만 Ubuntu 는 보장되지 않습니다.

`e2fsprogs` 는 지원하는 세 OS 모두 base 에 들어 있습니다. 덤으로 ext4 는 XFS 의 `ftype=1`
요구사항(없으면 overlayfs 가 마운트를 거부)도 없습니다.

포맷할 때 `quota,project` 피처를 켜 둡니다. 지금은 쓰지 않지만 kubelet 의 쿼타 기반
ephemeral-storage 격리를 나중에 쓰려면 파일시스템 단에 켜져 있어야 하고, 나중에 켜려면
재포맷입니다. 마운트 옵션 `prjquota` 는 실제로 쓸 때 붙이면 되므로 지금 넣지 않습니다.

마운트 옵션에 `noexec` / `nosuid` / `nodev` 를 *넣으면 안 됩니다.* 컨테이너 rootfs 가
여기서 실행됩니다.

=== 마운트가 안 걸린 채 서비스가 뜨는 것을 막아야 합니다

bind mount 없이 kubelet 과 containerd 가 뜨면 아무 에러 없이 루트 디스크를 쓰다가 한참
뒤에 루트가 찹니다. 이 조용한 실패를 막는 것이 이 기능에서 제일 중요한 부분입니다.

* fstab 의 bind 항목에 `x-systemd.requires-mounts-for=<base>` 를 명시합니다. 최근 systemd
  는 bind 소스 의존을 추론하지만 지원 OS 전 범위에서 확인하는 것보다 적는 편이 쌉니다
* `nofail` 을 쓰지 않습니다. 마운트 실패는 부팅 실패로 드러나야 합니다
* `containerd.service` 와 `kubelet.service` 에 `RequiresMountsFor=` drop-in 을 넣어
  마운트가 없으면 서비스가 아예 뜨지 않게 합니다

=== 실행 순서 제약

`get-node-resources.sh` 가 `df` 로 nodefs/imagefs 크기를 재서 kubelet 예약량을 계산합니다.
마운트가 `gather-facts` 보다 먼저 끝나지 않으면 *루트 디스크 크기로 예약량이 계산됩니다.*
`install-packages` 가 kubelet/containerd 패키지를 깔면서 대상 디렉토리를 만들기도 하므로
그보다도 앞서야 합니다. `preflight-playbook` 직후, `gather-facts` 직전에 넣는 이유입니다.

그 자리는 `setup-vars-file` 보다 앞이라 `ki_tmp_vars_path` 가 아직 없습니다. `vars.yml` 에
`kubelet_reservations` 가 들어가고 그건 `gather-facts` 의 결과물이므로, 이 순서는 뒤집을 수
없습니다. 그래서 이 스크립트만 `--vars-path` 대신 필요한 값을 직접 인자로 받습니다.
`get-node-resources.sh` 가 같은 이유로 같은 방식입니다.

변수 검증도 `validate-hostvars` 보다 앞서 일어나므로 스크립트가 자체적으로 방어합니다.

같은 이유로 플레이북의 조건식이 `ephemeral_storage_device` 를 그냥 읽지 않고
`default(None)` 을 거칩니다. 업그레이드는 사용자의 `vars.yml` 을 보존하므로 새 릴리스가
추가한 변수는 사용자가 병합하기 전까지 없고, `validate-hostvars` 의 pydantic 기본값은 아직
적용되기 전입니다. 이 방어가 없으면 디바이스를 주지 않은 노드에서 조건식이
"undefined" 로 터집니다.

=== reset 순서 제약

`uninstall-packages.sh` 는 `rm -rf /var/lib/containerd` 를 합니다. bind mount 가 살아 있는
상태로 이걸 돌리면 내용은 지워지지만 마운트포인트 `rmdir` 이 `EBUSY` 로 실패하고, 스크립트가
`set -Eeuo pipefail` 이라 reset 전체가 거기서 죽습니다.

따라서 `reset-ephemeral-storage` 는 `uninstall-packages` 보다 *반드시 앞* 이어야 합니다.
`reset-containerd` 직후에 둡니다. 그 시점이면 containerd 와 kubelet 이 이미 내려가 있어서
안전하게 umount 할 수 있습니다.

`reset-cluster` 와 `remove-node` 가 같은 순서를 갖고 있으므로 *양쪽 모두* 넣어야 합니다.
`remove-node` 를 빠뜨리면 기존 노드에 이 기능을 적용하는 유일한 경로인 `remove-node` →
`add-node` 가 막힙니다.

reset 은 마운트를 걷고 데이터를 비우지만 *파일시스템은 남깁니다.* 포맷하지 않습니다.

=== 멱등성과 안전장치

이 기능의 유일한 파괴적 실패 모드는 재실행이 mkfs 로 라이브 데이터를 날리는 것입니다.
`setup-cluster` 와 `add-node` 는 여러 번 도는 전제이므로 판정을 명시합니다.

[cols="3,2"]
|===
|상태 |동작

|`ephemeral_storage_device` 가 null |아무것도 하지 않음
|디바이스가 없거나 블록 디바이스가 아님 |실패
|디바이스에 파티션 테이블이 있음 |실패
|디바이스에 ext4 가 아닌 파일시스템이 있음 |실패
|디바이스가 이미 어딘가 마운트되어 있음 |실패
|디바이스에 ext4 가 있음 |포맷하지 않고 재사용
|디바이스가 비어 있음 |포맷
|대상 경로에 이미 데이터가 있음 |실패
|베이스 하위 디렉토리에 데이터가 있음 |실패
|containerd 또는 kubelet 이 이미 enabled |실패
|이미 구성이 끝나 있음 |아무것도 하지 않음
|===

강제 재포맷은 제공하지 않습니다. 디스크를 재사용하려면 운영자가 `wipefs` 로 직접 비웁니다.

포맷 여부와 데이터 유무를 나눈 것은 reset 이 파일시스템을 남기기 때문입니다. "기존
파일시스템이 있으면 실패" 로 두면 reset 후 재설치가 막힙니다.

=== 기존 노드에는 적용하지 않습니다

이미 이미지와 파드 데이터가 있는 노드에 bind mount 를 걸면 기존 데이터가 가려진 채 루트
디스크를 계속 점유합니다. 마이그레이션 경로를 만드는 대신 위 표의 가드로 실패시키고, 기존
노드에는 `remove-node` → `add-node` 로 적용합니다.

=== 파드 로그는 리셋이 지웁니다

`kubeadm reset` 은 `/var/lib/kubelet` 을 비우지만 `/var/log/pods` 는 건드리지 않고, 다른
어떤 스크립트도 지우지 않고 있었습니다. 남은 로그는 노드가 다시 조인할 때 그대로
ephemeral-storage 사용량으로 잡히고, 디스크를 새로 붙이는 노드에서는 빈 디렉토리 검사에
걸려 `remove-node` → `add-node` 경로 자체를 막습니다. 바로 위에서 그 경로로 적용하라고
해 둔 것이라 `reset-k8s-node-kubelet.sh` 가 내용을 비우게 했습니다.

디렉토리 자체는 남깁니다. 마운트포인트일 수 있습니다.

=== 휘발성 디스크를 붙이면 안 됩니다

기능 이름은 ephemeral-storage 지만 `/var/lib/kubelet` 에는 `cpu_manager_state`,
`memory_manager_state`, 파드 체크포인트처럼 재부팅을 넘어 유지되어야 하는 상태가 들어
있습니다. 클라우드 instance store 처럼 인스턴스가 멈추면 내용이 사라지는 디스크를 여기
붙이면 안 됩니다.

=== containerd_root_path 제거

bind mount 방식에서는 의미가 없어져 없앴습니다. 대상 경로가 고정되면서 systemd drop-in 도
템플릿이 아닌 고정 파일이 되었습니다.

업그레이드하면 사용자의 `vars.yml` 은 보존되므로 이 키가 남습니다. `VarsModel` 은 pydantic
기본 설정이라 모르는 키를 조용히 무시하는데, 그러면 커스텀 경로가 계속 먹는 줄 알지만
실제로는 containerd 가 `/var/lib/containerd` 를 쓰게 되어 기존 이미지가 고아가 됩니다.
그래서 `validate-hostvars.py` 가 이 키를 발견하면 실패시킵니다.

=== 모니터링 영향

같은 파일시스템이라 용량과 사용량 수치는 같지만, cadvisor 가 보고하는 `device` /
`mountpoint` 라벨이 베이스 경로로 잡힐 수 있습니다. 디스크 대시보드나 알람이
`/var/lib/kubelet` 을 문자열로 매칭하고 있다면 확인이 필요합니다.

=== 검수 기준

[cols="1,4"]
|===
|# |항목

|1 |`kubectl describe node` 의 `ephemeral-storage` Capacity 가 새 디스크 크기를 반영
|2 |`findmnt` 로 4개 마운트 확인, `/var/lib/kubelet` 의 PROPAGATION 이 `shared`
|3 |파드가 실제로 뜸 (overlayfs 동작)
|4 |`kubelet_reservations` 의 nodefs/imagefs 가 새 디스크 기준으로 계산됨
|5 |재부팅 후 마운트 유지, 종료 시 hang 없음
|6 |`setup-cluster` 재실행이 포맷하지 않고 통과
|7 |fstab 을 고의로 깨뜨리면 kubelet/containerd 가 *뜨지 않음* (루트 디스크로 fallback 하지 않음)
|8 |`reset-cluster` 가 끝까지 완주하고 이후 재설치가 됨
|9 |디스크가 있는 노드와 없는 노드가 한 클러스터에 공존
|===

7번과 8번이 이 기능의 실질적 회귀 테스트입니다.

== 번들에 담는 컨테이너 이미지

번들은 두 종류의 이미지를 나릅니다. ki cp 서비스가 도커로 실행하는 이미지와, 클러스터가
당겨 쓰도록 레지스트리에 채워 넣을 이미지입니다. 목적지가 다르면 적재 방법이 다르고,
적재 방법이 다르면 담는 포맷도 달라야 합니다.

[cols="1,2,2"]
|===
|  |`ki-cp-service-images/` |`ki-cp-<registry>-images/`

|적재
|`docker load`
|`crane push`

|포맷
|docker archive
|OCI layout

|단위
|서비스당 tar 하나
|이미지당 디렉토리 하나
|===

=== 서비스 이미지를 레지스트리에서 받을 수는 없습니다

레지스트리에 넣고 거기서 받게 하면 디렉토리가 하나로 줄지만 순환합니다. 레지스트리 주소를
풀려면 dns 서버가 떠 있어야 하는데 그 dns 서버가 이 이미지 중 하나이고, 레지스트리 자신도
마찬가지입니다. 그래서 이 다섯은 끝까지 tar 에서 로드해야 하고, 두 디렉토리는 합쳐지지
않습니다.

=== 서비스 이미지가 OCI layout 일 수 없는 이유

`docker load` 가 읽는 것은 docker archive 뿐입니다. OCI layout 을 넘기면 docker archive 로
파싱하다 `blobs/json` 이 없다며 실패합니다. 도커를 containerd 이미지 스토어로 바꾸면 읽지만,
그러자고 ki cp 노드 도커의 스토어를 통째로 갈아엎을 이유가 없습니다. 이 다섯은 다이제스트로
참조되지도 않습니다.

=== 레지스트리 이미지가 docker archive 일 수 없는 이유

docker archive 를 푸시하면 매니페스트가 재구성되면서 다이제스트가 바뀝니다. OCI layout 은
받은 것을 그대로 올립니다. 차트가 이미지를 다이제스트로 고정하는 일이 흔하므로, 바꾸지 않는
쪽을 택합니다.

=== 이미지당 디렉토리 하나인 이유

여러 이미지를 한 OCI layout 에 넣을 수는 있고 레이어도 공유됩니다. 그런데 `crane push` 는
항목이 둘 이상인 layout 을 참조 하나로 올리라고 거부합니다. 각각을 제 참조로 올리려면
이미지마다 layout 이 하나씩 있어야 합니다.

디렉토리의 경로가 곧 푸시될 참조입니다. `kube-apiserver:v1.34.1` 디렉토리는
`<레지스트리>/kube-apiserver:v1.34.1` 로 올라갑니다. 그래서 파일과 참조를 이어 주는 별도의
매니페스트가 필요 없습니다.

=== 플랫폼 하나만 담습니다

업스트림 태그는 대개 멀티아치 인덱스입니다. 인덱스를 통째로 담으면 업스트림 다이제스트와
정확히 일치하지만, `pause:3.10.1` 한 개가 547MB 가 됩니다. 윈도우 변형까지 전부 들어오기
때문입니다. `--platform linux/amd64` 로 받으면 340KB 입니다.

그래서 amd64 매니페스트만 담고, 그 경우 레지스트리가 서비스하는 다이제스트는 인덱스의 것이
아니라 amd64 매니페스트의 것이 됩니다. *인덱스 다이제스트로 고정한 차트는 이 레지스트리에서
찾지 못합니다.* 도커로 받아 도커로 올리던 이전 방식도 플랫폼 하나만 담았으므로 새로 생긴
제약은 아니고, 이전 방식은 그 위에 매니페스트까지 재구성해 어느 쪽과도 다른 다이제스트를
내놓았습니다.

=== 레이어를 압축된 채로 나릅니다

`docker save` 는 레이어를 풀어서 담고 `crane pull` 은 레지스트리에 있던 그대로, 즉 압축된
채로 담습니다. 서비스 이미지 다섯이 379MB 에서 125MB 가 된 것이 그 차이입니다.

== apiserver 로드밸런서의 런타임 관리

인증서 갱신이나 컴포넌트 업그레이드는 apiserver 를 한 번 내립니다. 로드밸런서가 그 사실을
헬스체크로 알아내는 구조에서는, 알아내기까지 보낸 요청이 전부 실패합니다. `/readyz` 로
바꾸면서 그 창이 줄긴 했지만 닫히지는 않습니다. 미리 빼 두는 수밖에 없고, 그래서 haproxy 의
런타임 api 를 열고 `lb-admin.sh` 로 말을 겁니다.

=== 포트가 아니라 컨테이너 안의 유닉스 소켓인 이유

런타임 api 는 자격증명을 받지 않고 백엔드를 내릴 수 있습니다. 포트로 내보내면 호스트
루프백뿐 아니라 같은 도커 브리지에 있는 모든 컨테이너가 닿습니다. 컨테이너 안에만 두면
거기 닿는 조건이 도커 데몬에 말을 걸 수 있는 것, 즉 노드의 root 인 것과 같아집니다.

노드에는 socat 이 없는 배포판이 있고 bash 의 `/dev/tcp` 는 유닉스 소켓을 못 엽니다.
haproxy 이미지가 socat 을 가지고 있어서, `docker compose exec` 로 그것을 씁니다. 소켓 경로를
`/var/lib/haproxy` 아래 두는 것은 컨테이너의 haproxy 사용자가 쓸 수 있는 디렉토리가 거기뿐이기
때문입니다. `/var/run` 에 두면 바인드 자체가 권한 거부로 실패합니다.

=== maint 가 아니라 drain 인 이유

백엔드에 `on-marked-down shutdown-sessions` 가 걸려 있습니다. 죽은 apiserver 에 물린 세션을
끊어 주자는 설정인데, `maint` 는 서버를 내리는 것이라 이 설정이 같이 발동해서 세션을 끊습니다.
`drain` 은 새 연결만 막고 있던 세션은 그대로 둡니다. 무중단으로 빼려는 목적에 맞는 것은
`drain` 쪽입니다.

=== wait-ready 가 헬스체크 결과가 아니라 운영 상태를 보는 이유

`show stat` 의 `check_status` 는 마지막 체크 결과(`L7OK`)고, `status` 는 로드밸런서가 그 서버를
어떻게 취급하는지(`UP`)입니다. 체크가 막 통과하기 시작한 서버는 `rise` 를 채울 때까지
`DOWN 1/2` 이며 트래픽을 받지 않습니다. 다음 노드로 넘어가도 되는지를 판단하려면 `status` 가
`UP` 인지를 봐야 합니다.

=== 모든 ki cp 노드에서 빼야 합니다

ki cp 노드는 각자 제 로드밸런서를 돌리고 VIP 는 언제든 옮겨 갈 수 있습니다. 한 노드에서만
빼 두면 VIP 가 옮겨 간 순간 아직 빼지 않은 로드밸런서가 그 백엔드로 다시 보냅니다. 노드를
정말로 뺀 상태는 모든 ki cp 노드에서 `drain` 한 상태입니다.

== VIP 를 언제 옮기는가

VIP 는 apiserver 로드밸런서의 주소이면서 dns 서버와 레지스트리의 주소이기도 합니다.
옮기면 그 위의 모든 연결이 끊어지므로, 옮겨서 나아지는 경우에만 옮겨야 합니다.

=== 헬스체크가 백엔드 유무를 보면 안 됩니다

`/lb-healthz` 가 "쓸 수 있는 백엔드가 있는가"까지 보게 만들었다가 설치가 통째로
교착됐습니다. 새 클러스터에는 apiserver 가 아직 하나도 없으니 모든 노드가 체크에 실패하고,
아무도 VIP 를 들지 않고, 그러면 레지스트리의 dns 이름이 안 풀리고, kubeadm 은 첫 apiserver 를
만들 이미지를 못 받습니다. 스스로를 막는 구조입니다.

교착이 아니더라도 판단 기준으로 틀렸습니다. 모든 노드의 로드밸런서는 같은 백엔드 목록을
봅니다. apiserver 가 전부 닿지 않는 상황에서 VIP 를 옮겨 봐야 가는 곳도 똑같고, 대신 VIP 에
같이 붙어 있는 dns 와 레지스트리 세션만 끊깁니다. 노드마다 달라지는 값, 그래서 판단에 쓸 수
있는 유일한 값은 "이 노드의 로드밸런서가 살아 있는가" 입니다.

=== weight 가 아니라 FAULT 인 이유

`nopreempt` 와 `weight` 는 같이 못 씁니다. weight 는 우선순위를 깎을 뿐이고, 낮아진
우선순위를 보고 피어가 가져가는 행위가 곧 preempt 라서 `nopreempt` 가 그것을 막습니다.
체크가 실패해도 MASTER 는 계속 advert 를 보내는 살아 있는 MASTER 이므로, 둘을 같이 걸면
로드밸런서가 멈춘 노드가 VIP 를 끝까지 붙들고 있습니다. 실측으로 50초 동안 전 구간 거부였습니다.

weight 를 빼면 실패한 스크립트가 인스턴스를 FAULT 로 보냅니다. 노드가 advert 자체를 멈추니
피어는 "내가 더 높아서"가 아니라 "아무도 안 들고 있어서" 가져갑니다. 우선순위 간격이 충분한지
따질 필요도 사라집니다.

=== 돌아온 노드는 VIP 를 되찾지 않습니다

`nopreempt` 가 없으면 장애 하나가 장애 둘이 됩니다. 로드밸런서가 죽어 VIP 가 넘어가고,
그 노드가 복구되는 순간 우선순위가 높다는 이유만으로 다시 가져오면서 지금 서비스 중인 노드의
연결을 전부 끊습니다. 실측으로 복구 15초 뒤에 두 번째 이동이 일어났습니다. 들고 있는 노드가
서비스하고 있다면 옮길 이유가 없습니다.

`nopreempt` 는 인스턴스가 MASTER 로 시작하면 무시되므로 모든 노드가 `state BACKUP` 입니다.
그 대가로 설치 후 VIP 가 node1 에 고정되지 않고 keepalived 가 먼저 안정된 노드에 붙습니다.
어느 ki cp 노드가 들든 서비스는 같으므로 받아들일 만하고, 대안은 설치마다 VIP 를 한 번씩
헛되이 옮기는 것입니다.
