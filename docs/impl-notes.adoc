= 구현 노트

여러 파일에 걸쳐 있어서 한 곳의 주석으로는 담기지 않는 설계 판단을 기록합니다.
한 파일만 봐서는 왜 그렇게 되어 있는지 드러나지 않는 것만 남기고, 한 파일 안에서 설명되는
내용은 그 파일의 주석에 둡니다.

== ephemeral-storage 전용 디스크

노드의 컨테이너 데이터가 전부 루트 디스크에 쌓이면 이미지 하나나 오래 쌓인 파드 로그가
루트 파일시스템을 채우고, 그 시점에 노드 전체가 불안정해집니다. `ephemeral_storage_device`
를 선언한 노드는 그 디스크를 포맷해 ephemeral-storage 회계 대상 경로 전체를 옮깁니다.

=== 대상 경로

kubelet이 파드의 ephemeral-storage 사용량으로 세는 것은 세 가지고, 그래서 옮기는 경로도
셋입니다.

[cols="2,3"]
|===
|경로 |담기는 것

|`/var/lib/kubelet`
|emptyDir (`pods/<uid>/volumes/kubernetes.io~empty-dir`)

|`/var/log/pods`
|컨테이너 로그. `/var/log/containers` 의 심볼릭 링크가 이 아래를 가리킵니다

|`/var/lib/containerd`
|컨테이너 writable layer 와 이미지
|===

디스크 하나를 세 경로에 동시에 마운트할 수는 없습니다. 베이스 마운트포인트
(`ki_ephemeral_root_path`) 를 하나 두고 그 하위 디렉토리를 각 경로로 bind mount 합니다.

----
/dev/disk/by-uuid/<uuid>   →  <base>                  (실제 마운트)
<base>/kubelet             →  /var/lib/kubelet        (bind)
<base>/pod-logs            →  /var/log/pods           (bind)
<base>/containerd          →  /var/lib/containerd     (bind)
----

`/var/log/pods` 는 kubelet이 처음 뜰 때 생기므로 마운트포인트를 미리 만들어 둡니다.

=== root path 변경이 아니라 bind mount 인 이유

*`/var/log/pods` 에는 kubelet 설정 플래그가 없습니다.* 하드코딩이라 bind mount 외에는 옮길
방법이 없고, 이 항목 하나로 방식이 결정됩니다.

`/var/lib/kubelet` 은 `--root-dir` 로 옮길 수 있지만 CSI 드라이버와 node-driver-registrar,
로그 수집 DaemonSet 등 외부 매니페스트가 이 경로를 hostPath 로 하드코딩합니다. 경로를 바꾸면
가져다 쓰는 차트마다 손을 대야 합니다.

containerd 만 `root =` 로 옮기고 나머지 둘은 bind mount 하는 혼종보다 세 경로를 한 방식으로
통일하는 편이 낫습니다. 그래서 `containerd_root_path` 변수를 없앴습니다 (아래 참고).

=== 세 경로가 용량을 공유합니다

한 파일시스템을 셋이 나눠 쓰므로 이미지가 디스크를 채우면 파드 로그와 emptyDir 도 같이
죽습니다. LVM 으로 나누면 격리되지만 공간이 낭비되고 운영이 복잡해져서 택하지 않았습니다.

kubelet 이 nodefs 와 imagefs 를 같은 파일시스템으로 보게 되는데, 이건 kubelet 의 기본
가정이고 `create-kubelet-reservations.py` 가 원래부터 그렇게 계산합니다.

=== 파일시스템을 ext4 로 고정한 이유

overlayfs 상성과 프로젝트 쿼타만 보면 XFS 가 낫지만 쓸 수 없습니다. K8S Installer는 패키지를
`bundle/linux-packages/` 에 번들해서 설치하는 오프라인 구조인데, 디스크를 마운트하는 시점은
`install-packages` 보다 *앞* 입니다. 즉 `xfsprogs` 가 스톡 이미지에 없으면 그 시점에
설치할 방법이 없습니다. RHEL 8 은 기본 탑재지만 Ubuntu 는 보장되지 않습니다.

`e2fsprogs` 는 지원하는 세 OS 모두 base 에 들어 있습니다. 덤으로 ext4 는 XFS 의 `ftype=1`
요구사항(없으면 overlayfs 가 마운트를 거부)도 없습니다.

포맷할 때 `quota,project` 피처를 켜 둡니다. 지금은 쓰지 않지만 kubelet 의 쿼타 기반
ephemeral-storage 격리를 나중에 쓰려면 파일시스템 단에 켜져 있어야 하고, 나중에 켜려면
재포맷입니다. 마운트 옵션 `prjquota` 는 실제로 쓸 때 붙이면 되므로 지금 넣지 않습니다.

마운트 옵션에 `noexec` / `nosuid` / `nodev` 를 *넣으면 안 됩니다.* 컨테이너 rootfs 가
여기서 실행됩니다.

=== 마운트가 안 걸린 채 서비스가 뜨는 것을 막아야 합니다

bind mount 없이 kubelet 과 containerd 가 뜨면 아무 에러 없이 루트 디스크를 쓰다가 한참
뒤에 루트가 찹니다. 이 조용한 실패를 막는 것이 이 기능에서 제일 중요한 부분입니다.

* fstab 의 bind 항목에 `x-systemd.requires-mounts-for=<base>` 를 명시합니다. 최근 systemd
  는 bind 소스 의존을 추론하지만 지원 OS 전 범위에서 확인하는 것보다 적는 편이 쌉니다
* `nofail` 을 쓰지 않습니다. 마운트 실패는 부팅 실패로 드러나야 합니다
* `containerd.service` 와 `kubelet.service` 에 `RequiresMountsFor=` drop-in 을 넣어
  마운트가 없으면 서비스가 아예 뜨지 않게 합니다

=== 실행 순서 제약

`get-node-resources.sh` 가 `df` 로 nodefs/imagefs 크기를 재서 kubelet 예약량을 계산합니다.
마운트가 `gather-facts` 보다 먼저 끝나지 않으면 *루트 디스크 크기로 예약량이 계산됩니다.*
`install-packages` 가 kubelet/containerd 패키지를 깔면서 대상 디렉토리를 만들기도 하므로
그보다도 앞서야 합니다. `preflight-playbook` 직후, `gather-facts` 직전에 넣는 이유입니다.

그 자리는 `setup-vars-file` 보다 앞이라 `ki_tmp_vars_path` 가 아직 없습니다. `vars.yml` 에
`kubelet_reservations` 가 들어가고 그건 `gather-facts` 의 결과물이므로, 이 순서는 뒤집을 수
없습니다. 그래서 이 스크립트만 `--vars-path` 대신 필요한 값을 직접 인자로 받습니다.
`get-node-resources.sh` 가 같은 이유로 같은 방식입니다.

변수 검증도 `validate-hostvars` 보다 앞서 일어나므로 스크립트가 자체적으로 방어합니다.

=== reset 순서 제약

`uninstall-packages.sh` 는 `rm -rf /var/lib/containerd` 를 합니다. bind mount 가 살아 있는
상태로 이걸 돌리면 내용은 지워지지만 마운트포인트 `rmdir` 이 `EBUSY` 로 실패하고, 스크립트가
`set -Eeuo pipefail` 이라 reset 전체가 거기서 죽습니다.

따라서 `reset-ephemeral-storage` 는 `uninstall-packages` 보다 *반드시 앞* 이어야 합니다.
`reset-containerd` 직후에 둡니다. 그 시점이면 containerd 와 kubelet 이 이미 내려가 있어서
안전하게 umount 할 수 있습니다.

`reset-cluster` 와 `remove-node` 가 같은 순서를 갖고 있으므로 *양쪽 모두* 넣어야 합니다.
`remove-node` 를 빠뜨리면 기존 노드에 이 기능을 적용하는 유일한 경로인 `remove-node` →
`add-node` 가 막힙니다.

reset 은 마운트를 걷고 데이터를 비우지만 *파일시스템은 남깁니다.* 포맷하지 않습니다.

=== 멱등성과 안전장치

이 기능의 유일한 파괴적 실패 모드는 재실행이 mkfs 로 라이브 데이터를 날리는 것입니다.
`setup-cluster` 와 `add-node` 는 여러 번 도는 전제이므로 판정을 명시합니다.

[cols="3,2"]
|===
|상태 |동작

|`ephemeral_storage_device` 가 null |아무것도 하지 않음
|디바이스가 없거나 블록 디바이스가 아님 |실패
|디바이스에 파티션 테이블이 있음 |실패
|디바이스에 ext4 가 아닌 파일시스템이 있음 |실패
|디바이스가 이미 어딘가 마운트되어 있음 |실패
|디바이스에 ext4 가 있음 |포맷하지 않고 재사용
|디바이스가 비어 있음 |포맷
|대상 경로에 이미 데이터가 있음 |실패
|베이스 하위 디렉토리에 데이터가 있음 |실패
|containerd 또는 kubelet 이 이미 enabled |실패
|이미 구성이 끝나 있음 |아무것도 하지 않음
|===

강제 재포맷은 제공하지 않습니다. 디스크를 재사용하려면 운영자가 `wipefs` 로 직접 비웁니다.

포맷 여부와 데이터 유무를 나눈 것은 reset 이 파일시스템을 남기기 때문입니다. "기존
파일시스템이 있으면 실패" 로 두면 reset 후 재설치가 막힙니다.

=== 기존 노드에는 적용하지 않습니다

이미 이미지와 파드 데이터가 있는 노드에 bind mount 를 걸면 기존 데이터가 가려진 채 루트
디스크를 계속 점유합니다. 마이그레이션 경로를 만드는 대신 위 표의 가드로 실패시키고, 기존
노드에는 `remove-node` → `add-node` 로 적용합니다.

=== 파드 로그는 리셋이 지웁니다

`kubeadm reset` 은 `/var/lib/kubelet` 을 비우지만 `/var/log/pods` 는 건드리지 않고, 다른
어떤 스크립트도 지우지 않고 있었습니다. 남은 로그는 노드가 다시 조인할 때 그대로
ephemeral-storage 사용량으로 잡히고, 디스크를 새로 붙이는 노드에서는 빈 디렉토리 검사에
걸려 `remove-node` → `add-node` 경로 자체를 막습니다. 바로 위에서 그 경로로 적용하라고
해 둔 것이라 `reset-k8s-node-kubelet.sh` 가 내용을 비우게 했습니다.

디렉토리 자체는 남깁니다. 마운트포인트일 수 있습니다.

=== 휘발성 디스크를 붙이면 안 됩니다

기능 이름은 ephemeral-storage 지만 `/var/lib/kubelet` 에는 `cpu_manager_state`,
`memory_manager_state`, 파드 체크포인트처럼 재부팅을 넘어 유지되어야 하는 상태가 들어
있습니다. 클라우드 instance store 처럼 인스턴스가 멈추면 내용이 사라지는 디스크를 여기
붙이면 안 됩니다.

=== containerd_root_path 제거

bind mount 방식에서는 의미가 없어져 없앴습니다. 대상 경로가 고정되면서 systemd drop-in 도
템플릿이 아닌 고정 파일이 되었습니다.

=== 모니터링 영향

같은 파일시스템이라 용량과 사용량 수치는 같지만, cadvisor 가 보고하는 `device` /
`mountpoint` 라벨이 베이스 경로로 잡힐 수 있습니다. 디스크 대시보드나 알람이
`/var/lib/kubelet` 을 문자열로 매칭하고 있다면 확인이 필요합니다.

=== 검수 기준

[cols="1,4"]
|===
|# |항목

|1 |`kubectl describe node` 의 `ephemeral-storage` Capacity 가 새 디스크 크기를 반영
|2 |`findmnt` 로 4개 마운트 확인, `/var/lib/kubelet` 의 PROPAGATION 이 `shared`
|3 |파드가 실제로 뜸 (overlayfs 동작)
|4 |`kubelet_reservations` 의 nodefs/imagefs 가 새 디스크 기준으로 계산됨
|5 |재부팅 후 마운트 유지, 종료 시 hang 없음
|6 |`setup-cluster` 재실행이 포맷하지 않고 통과
|7 |fstab 을 고의로 깨뜨리면 kubelet/containerd 가 *뜨지 않음* (루트 디스크로 fallback 하지 않음)
|8 |`reset-cluster` 가 끝까지 완주하고 이후 재설치가 됨
|9 |디스크가 있는 노드와 없는 노드가 한 클러스터에 공존
|===

7번과 8번이 이 기능의 실질적 회귀 테스트입니다.

== 장치를 게스트에게 통과시키기

컨테이너가 GPU 를 받는 쪽은 호스트가 벤더 드라이버를 들고 그 위로 장치를 빌려 주는 구조입니다.
가상머신에 카드를 통째로 넘기는 쪽은 그 반대입니다 — 호스트는 그 카드를 건드리지 않아야 하고,
부팅 시점에 vfio-pci 가 먼저 잡고 있어야 합니다.

=== 세 가지가 부팅 때 다 참이어야 합니다

IOMMU 가 켜져 있어야 하고, vfio 모듈이 initramfs 에 있어야 하고, 장치 ID 가 벤더 드라이버보다
먼저 청구되어야 합니다. 셋 중 하나만 빠져도 카드는 평소 드라이버가 잡고, 그 뒤에 무엇을 해도
게스트에게 줄 수 없습니다. 그래서 이것은 실행하는 명령이 아니라 노드가 다음 부팅에 읽을 설정을
쓰는 일이고, 설치본은 재부팅하지 않습니다.

스크립트가 끝나면서 이 노드가 아직 재부팅을 기다리는지 말해 주는 것은 그 때문입니다. 재부팅하지
않은 노드와 설정이 잘못된 노드는 겉으로 똑같이 보입니다.

그걸 IOMMU 상태로 판단하지 않습니다. IOMMU 는 사이트가 자기 사정으로 켜 둡니다 — 카드를 빼 줄
만한 기계라면 이 설치본이 돌기 한참 전부터 `/etc/default/grub` 에 `intel_iommu=on` 이 들어 있을
가능성이 높고, 아래 "이미 켜져 있던 인자는 건드리지 않습니다" 가 다루는 것이 바로 그 노드입니다.
그 노드에서 IOMMU 를 "재부팅했다" 로 읽으면, 정작 재부팅이 필요한 노드에서만 경고가 사라집니다.
그래서 `/proc/cmdline` 에 우리가 쓴 `vfio-pci.ids=` 가 실려 있는지를 봅니다. 그 인자는 남의 것일
수 없고(설치본이 항상 쓰고, 노드의 다른 무엇도 쓸 일이 없습니다), 재생성된 grub 설정으로 부팅해야만
거기 올라옵니다. 값까지 비교하므로 마지막 부팅 뒤에 ID 가 바뀐 노드도 같이 잡힙니다 — IOMMU 로는
아예 보이지 않던 상태입니다.

같은 이유로 적어 준 ID 가 그 노드에 실제로 있는지를 먼저 봅니다. 없으면 거부합니다. 오타 하나는
파일이 다 써지고 "Configured" 까지 찍힌 뒤 재부팅하고 나서야 "통과가 안 된다" 로 나타나는데,
그것이 위에서 말한 구분할 수 없는 두 상태 중 하나입니다. 조회는 `lspci` 가 아니라 sysfs 로 합니다.
`lspci` 는 pciutils 에 들어 있고 번들은 그것을 나르지 않습니다.

=== 재부팅을 미루면 사라지지 않고 제일 비싼 순간으로 옮겨집니다

이 설정은 재부팅 전까지 아무 효과가 없습니다. 그래서 질문은 "재부팅할 것인가"가 아니라 "언제
재부팅할 것인가"입니다.

`setup-vfio-pci.sh` 는 원래 `add-k8s-node.yml` 안에 있었는데, 거기는 재부팅하기에 늦습니다. 그
시점에 ki cp 노드는 이미 DNS·NTP·레지스트리를 다른 노드에 서비스하고 있고, `add-node.yml` 이
끝나고 나면 그 노드는 파드를 들고 있습니다. 문서가 시키는 대로 `remove-node` 후 `add-node` 를
한 운영자는 결국 살아 있는 노드를 손으로 drain 하고 재부팅하게 됩니다 — 설치본이 빈 노드에서
공짜로 할 수 있었던 일을요.

그래서 `tasks/setup-vfio-pci.yml` 은 `check-node-state.sh` 직후, 노드에 아무것도 올라가기 전에
돕니다. 실행 자체에도 그 자리가 마지막 기회입니다: `ki_tmp_root_path` 가 `/tmp/k8s-installer`
이고 그 시점에 거기 있는 것은 vars 파일 하나뿐이라, 재부팅으로 `/tmp` 가 비어도 바로 뒤에서
`setup-vars-file.yml` 을 다시 태우면 복구됩니다. PKI 도 CA 인증서도 join 자격증명도 전부 이
다음에 그 디렉토리로 들어옵니다.

재부팅 자체는 `vfio_pci_reboot` 로 켭니다. 기본값이 꺼짐인 것은 기계를 재부팅하는 것이 사이트의
결정이고, 변경 창 안에서만 허용하는 곳이 많기 때문입니다. 켜면 재부팅 후 검증까지 하고, 묶이지
않았으면 거기서 멈춥니다 — 일부러 재부팅했는데도 안 됐다면 그건 알림이 아니라 실패이고, 아직
아무것도 안 올라간 노드에서 멈추는 것이 가장 쌉니다.

*제어 노드는 어느 쪽이든 재부팅하지 않습니다.* ansible 이 도는 기계라서 재부팅하면 실행 자체가
같이 죽습니다. `run-all-node-script-control-node-last.yml` 이 docker 스크립트를 위해 하는 "제어
노드는 마지막에"가 여기서는 통하지 않습니다 — 순서의 문제가 아니라 불가능입니다. 그 노드는
`vfio_pci_reboot` 가 꺼진 노드와 같은 길로 떨어집니다. 설정은 쓰이고, 사람이 재부팅할 때까지
아래의 보고가 매번 말해 줍니다.

=== 썼는지가 아니라 먹었는지를 봅니다

`report_state` 가 재부팅을 기다리는지 말해 주긴 하지만, 그건 커널 명령줄만 본 것입니다. 명령줄이
제대로 실렸는데도 카드는 여전히 벤더 드라이버가 물고 있을 수 있고, 그 상태가 "통과가 안
된다"의 대부분입니다. 그래서 `check-vfio-pci.sh` 는 유일하게 결론이 나는 질문을 합니다 — 인벤토리가
적은 장치 하나하나가 *지금* vfio-pci 에 묶여 있는가, 그리고 이 노드의 IOMMU 가 올라와 있는가.

무엇이 아닌지까지 말합니다. 설정대로 부팅한 적이 없으면 재부팅이 남은 것이고, 부팅은 했는데 IOMMU 가
없으면 **기계가 IOMMU 를 내주지 않는 것**이고, 둘 다 됐는데 장치가 벤더 드라이버에 있으면 initramfs 나
modprobe 옵션이 그 장치까지 닿지 않은 것입니다. 할 일이 서로 다르고, 장치 목록만 봐서는 구분되지
않습니다.

재부팅 여부의 판단 근거는 IOMMU 가 아니라 `/proc/cmdline` 의 `vfio-pci.ids=` 입니다. 위에 적은 이유
그대로이고, 틀렸을 때의 대가가 더 큽니다 — 재부팅만 하면 될 노드를 두고 initramfs 를 읽으러 가게
만듭니다.

그렇다고 IOMMU 상태를 버리면 안 됩니다. 요청 인자를 달고 부팅했는데도 IOMMU 가 없는 노드는 **여기서
쓴 것으로는 고칠 수 없는 유일한 경우**입니다 — 펌웨어에서 VT-d/AMD-Vi 가 꺼져 있거나, IOMMU 를 안 준
게스트입니다. 재부팅해도 같고 initramfs 를 봐도 없습니다. 그 노드에 "재부팅하라"(옛 IOMMU 판정) 나
"initramfs 를 보라"(cmdline 판정만) 를 말하면 둘 다 헛걸음을 시킵니다. IOMMU 가 없는 테스트 VM 에
설정을 넣어 보고서야 드러났습니다.

실패시키지 않고 보고만 합니다. 재부팅을 기다리는 노드는 고장난 노드가 아니라 할 일이 남은
노드이고, 재부팅할 수 있는 사람이 이걸 돌리는 사람이 아닐 수도 있습니다. 대신 **매 실행 끝에
다시 말합니다.** 이 기능이 조용히 틀리는 방식은 잘못 쓰이는 것이 아니라 재부팅이 잊히는 것이라,
잊히지 않게 만드는 것이 답입니다. `check-cert-expiry.yml` 이 같은 자리에서 같은 일을 합니다.

세 가지를 구분해서 말합니다. 아무것도 안 쓰인 노드(인벤토리는 적었는데 setup 이 그 노드에서 돈
적이 없는 경우 — `update-cluster.yml` 은 변수를 적용하지 저 노드를 프로비저닝하지 않습니다),
설정대로 부팅한 적이 없는 노드(재부팅을 안 했거나, 마지막 부팅 뒤에 ID 가 바뀐 것), 부팅은 했는데
IOMMU 가 안 올라온 노드(기계가 안 내주는 것), 둘 다 됐는데 장치가 벤더 드라이버에 있는 노드
(initramfs 나 modprobe 옵션이 안 닿은 것). 할 일이 각각 다릅니다 — 첫째는 add-node, 둘째는
재부팅, 셋째는 재부팅이 아니라 그 노드의 설정을 봐야 합니다.

첫째 상태가 생기는 경로가 하나 더 있습니다. 릴리스가 `vfio_pci_device_ids` 를 처음 들고 온 직후에는
어느 노드의 기록에도 그 변수가 없어서, `diff-applied-vars.py` 가 그것을 변경이 아니라 baseline 으로
셉니다(main 의 `b368f8f`). 그래서 **그 첫 실행에서는 `node_rebuild` 가 "노드를 다시 만들라"고
말하지 않습니다.** 의도된 동작이고 — 안 그러면 카드가 없는 노드까지 전부 재생성 대상이 됩니다 —
대신 그 창을 덮는 것이 이 검사뿐입니다.

장치 ID 를 vars 파일이 아니라 인자로 받는 이유가 있습니다. `ki_tmp_vars_path` 는 플레이북이 도는
동안에만 있고 `reset-vars-file.yml` 이 끝나기 전에 치웁니다. 인자로 받아야 재부팅한 사람이
아무 때나 태스크 파일을 직접 돌려 확인할 수 있고, 그 명령이 경고 메시지 안에 적혀 있습니다.

=== blacklist 가 아니라 softdep 입니다

blacklist 는 드라이버에 대한 것이고 여기서 정하려는 것은 장치에 대한 것입니다. 카드를 두 장
꽂은 노드가 한 장만 넘긴다면 나머지 한 장은 여전히 그 드라이버가 몰아야 합니다. `softdep` 은
순서만 정하므로, vfio-pci 가 먼저 떠서 자기 ID 목록에 있는 것만 가져가고 나머지는 원래 드라이버에
갑니다.

어느 드라이버를 뒤로 보낼지는 노드에 물어서 정합니다. 이름을 적어 두면 적은 사람이 생각한 카드만
담기는데, AMD 카드나 NIC 를 넘기는 것도 똑같이 이 기능입니다. 그리고 지금 바인딩된 드라이버를
읽어서는 안 됩니다 — 한 번 재부팅한 뒤에는 그게 vfio-pci 라서, 두 번째 실행이 자기에게 자기를
softdep 걸게 됩니다. 장치의 modalias 는 무엇이 바인딩되어 있든 변하지 않으므로 그것을
`modprobe -R` 로 해석합니다.

=== ID 는 modprobe.d 와 커널 명령줄 양쪽에 씁니다

`modprobe.d` 의 `options vfio-pci ids=...` 는 **modprobe 가 올리는 모듈에만** 적용됩니다. 배포판이
vfio-pci 를 커널에 내장해 두면(`modinfo vfio-pci` 가 `filename: (builtin)`) 그 파일은 아무도 읽지
않고, 카드는 벤더 드라이버가 그대로 잡습니다. softdep 도 같은 이유로 무의미합니다 — 순서를 정할
모듈 로드 자체가 없습니다. 내장 드라이버는 파라미터를 커널 명령줄로만 받습니다.

이 실패가 고약한 것은 **쓰인 파일이 동작하는 노드와 완전히 똑같아 보인다**는 점입니다.
`modprobe.d`, `modules-load.d`, initramfs 블록, grub drop in 이 전부 제자리에 있고 IOMMU 도
올라와 있는데 장치만 안 묶입니다. 설정을 아무리 들여다봐도 안 나옵니다.

그래서 `vfio-pci.ids=` 를 커널 명령줄에도 씁니다. 모듈인 배포판에서도 무해합니다 — 커널이 값을
들고 있다가 모듈이 올라올 때 넘겨주고, 그건 `modprobe.d` 가 주는 값과 같습니다. 한쪽만 고르는
대신 양쪽에 쓰는 이유는 어느 쪽인지 노드마다 다르고, 틀렸을 때의 증상이 "통과가 안 된다" 하나뿐이기
때문입니다.

(Ubuntu 22.04 의 5.15 커널에서 내장인 것을 테스트 노드에서 확인했습니다. 같은 노드에서 커널
명령줄에 ID 를 넣자 바로 묶였습니다.)

=== IOMMU 인자는 프로세서를 보고 고릅니다

`intel_iommu=on` 과 `amd_iommu=on` 중 어느 쪽인지는 그 기계의 사실이지 운영자가 고를 값이
아닙니다. 변수로 받으면 틀리게 적을 수 있고, 틀리면 IOMMU 가 영영 올라오지 않는 노드가 되며
증상은 "통과가 안 된다" 뿐입니다. `/proc/cpuinfo` 의 `vendor_id` 로 정합니다.

=== 우분투는 drop in, rhel8 은 grubby

우분투의 `/etc/default/grub.d` 는 본 파일 뒤에 읽히므로, 파일 하나를 놓고 지우는 것이 설정의
전부이자 되돌리기의 전부가 됩니다. 사이트가 적어 둔 `GRUB_CMDLINE_LINUX_DEFAULT` 는 그대로 두고
뒤에 붙입니다.

rhel8 에는 그 디렉토리가 없어서 `grubby` 가 부트 엔트리를 고칩니다. 인자는 하나씩 그냥 다
넘깁니다 — `grubby` 는 같은 이름의 인자를 찾으면 두 번째를 붙이지 않고 값을 갈아치웁니다.

무엇을 보고 판단하느냐가 여기서 갈립니다. 고치는 대상은 부트 엔트리이고 `/proc/cmdline` 은 지금
돌고 있는 커널입니다. 둘은 재부팅 전까지 다릅니다. 엔트리에서 인자가 빠졌는데 아직 재부팅하지
않은 노드는 `/proc/cmdline` 에 그것이 그대로 남아 있고, 그 노드가 바로 다시 넣어 줘야 하는
노드입니다. `remove-node` 후 `add-node` 가 정확히 그 경로입니다.

그리고 이 중 무엇을 이 설치본이 넣었는지를 적어 둡니다(`ki_etc_root_path` 의
`vfio-pci-kernel-args`). 사이트 이미지가 원래 `intel_iommu=on` 을 달고 있었다면 이 설치본은 거기에
아무것도 더하지 않은 것이고, 나중에 그것을 떼는 것은 사이트가 소유한 설정을 빼앗는 일입니다.
우분투에서 drop in 파일 하나만 소유하기로 한 것과 같은 규칙을 rhel8 에서 지키는 방법입니다.

그 기록은 **덮어쓰지 않고 더합니다.** 덮어쓰면 두 번째 실행이 기록을 비웁니다 — 인자가 이미 줄에
있으니 새로 넣은 것이 없고, 그래서 아무것도 안 적게 됩니다. `upgrade-k8s-nodes.yml` 이 매
업그레이드마다 setup 을 다시 돌리므로 그건 모든 노드에서 일어나고, 그 뒤 reset 은 커널 인자를
영영 못 뗍니다.

그리고 **인자 전체가 아니라 이름만** 적습니다. ID 는 바뀔 수 있는데 grubby 는 이름으로 지우므로,
`vfio-pci.ids` 만 적어 두면 줄에 어떤 값이 있든 떼어집니다. 이름 매칭은 정확해서 `iommu` 를 떼도
사이트가 소유한 `intel_iommu` 는 남습니다 — RHEL 8.10 의 grubby 8.40 에서 확인했습니다.

initramfs 도 갈립니다 — 우분투는 `/etc/initramfs-tools/modules` 의 마커 블록(파일은 배포판
것이고 사이트가 적어 둔 것이 있을 수 있으므로 파일이 아니라 블록을 소유합니다), rhel8 은
`dracut.conf.d` 의 `add_drivers` 입니다.

=== 빈 목록은 "할 일 없음"이 아닙니다

카드가 없는 노드에는 아무것도 하지 않아야 합니다. 부트로더를 여는 일은 그것이 필요한 노드에서만
일어나야 합니다. 그런데 목록이 비어 있는 노드에는 두 종류가 있습니다 — 한 번도 적지 않은 노드와,
적었던 것을 지운 노드입니다. 후자에서 그냥 끝내면 그 노드는 지운 뒤에도 영영 카드를 vfio-pci 에
묶은 채 부팅합니다.

그래서 빈 목록의 답은 reset 스크립트입니다. reset 은 변수가 아니라 자기가 쓴 파일이 있는지로
판단하므로, 한 번도 적지 않은 노드에서는 그대로 즉시 끝납니다 — 부트로더도 initramfs 도 열리지
않습니다. 두 종류를 구분하는 일을 변수가 아니라 노드의 상태에 맡긴 것입니다.

`vfio_pci_device_ids` 는 `node_rebuild` 클래스입니다. update-cluster.yml 은 변경을 거부하고
노드를 다시 만들라고 말하고, upgrade-cluster.yml 은 그 클래스를 적용하지도 기록하지도 않으므로
지운 값이 조용히 기록에 박히지도 않습니다. 그래도 위의 자가 치유가 필요한 이유는 따로입니다 —
거부는 "노드를 다시 만들라"고 말할 뿐이고, 그 말을 듣는 동안에도 노드는 계속 카드를 vfio-pci 에
묶은 채 부팅합니다. 운영자가 원한 것은 통과를 그만두는 것이지 노드를 다시 만드는 것이 아닙니다.

=== 검수 기준

재부팅 전에는 아무것도 참이 아니므로, 확인은 전부 재부팅을 끼고 합니다.

. `list-pci-devices.yml` 로 ID 를 확인. 아직 IOMMU 가 꺼져 있으므로 그룹은 안 보인다고 나옴
. ID 를 적고 add-node. 플레이북 끝에서 그 노드가 "not taken it / iommu: off" 로 보고됨
. 재부팅 후 `check-vfio-pci.yml`. 아무 노드도 보고되지 않고 "Every node ... bound to vfio-pci" 가 나옴.
  `list-pci-devices.yml` 에는 그룹과 `driver["vfio-pci"]` 가 보이고, 목록에 없는 다른 카드는 원래 드라이버를 그대로 들고 있음
. 없는 ID 를 적고 add-node. 노드가 만들어지기 전에 거부됨
. remove-node 후 *재부팅하지 않고* add-node. rhel8 에서 `grubby --info=ALL` 에 IOMMU 인자가 다시 들어 있음
. 사이트가 `intel_iommu=on` 을 미리 달아 둔 rhel8 노드에서 add-node 후 remove-node. 그 인자가 엔트리에 남아 있음
. 사이트가 IOMMU 를 미리 켜 둔 노드에서 setup 을 돌리고 *재부팅하지 않은 채* 확인. setup 이 재부팅
  경고를 내고, `check-vfio-pci.yml` 이 initramfs 가 아니라 재부팅을 가리킴 (IOMMU 는 그 전부터 켜져
  있으므로, 이것을 재부팅 신호로 쓰면 둘 다 조용해집니다)
. 이미 적용되어 돌고 있는 노드에서 setup 재실행. 재부팅 경고가 나오지 않음 (업그레이드마다 도는 경로)
. 적용된 노드의 ID 목록을 늘리고 재부팅 전에 확인. 실린 ID 와 적힌 ID 를 같이 보여 주며 재부팅을 가리킴
. IOMMU 가 없는 기계(가상 IOMMU 를 안 준 게스트)에 설정을 넣고 재부팅. 재부팅이나 initramfs 가 아니라
  **기계가 IOMMU 를 안 내준다**고 말함
. `gpu_passthrough: true` 인데 GPU 를 하나 빼고 적기. setup 이 남는 장치를 이름까지 대며 거부
. BMC VGA 가 달린 서버에서 `true` + NVIDIA 카드 전부 적기. 콘솔 VGA 때문에 거부당하지 *않음*
. NVIDIA 드라이버가 없는 노드에서 `modprobe -R` 이 NVIDIA 카드를 알아보는지. 우분투와 rhel8 양쪽,
  `nouveau` 를 블랙리스트한 상태까지
. `gpu_passthrough: false` 인데 GPU ID 를 적기. 같은 방식으로 거부
. GPU 가 달린 노드에서 `true` 로 setup. 드롭인이 생기고 `systemctl show -p Restart` 가 `no` 를 냄
. 같은 노드에서 GPU 가 아닌 장치만 넘기며 `false`. 드롭인이 없고 `Restart` 가 `on-failure` 그대로
. 그 노드를 reset. 드롭인과 그 디렉토리가 사라지고 `Restart` 가 돌아옴
. 목록을 비우고 upgrade-cluster. 그 노드의 `/etc/modprobe.d`, `/etc/modules-load.d`, drop in, dracut 파일이 사라짐
. `/etc/initramfs-tools/modules` 에 사이트 항목을 넣고 add-node 와 remove-node. 그 항목이 살아 있음
. `vfio_pci_reboot: true` 로 add-node. 노드가 한 번 재부팅되고, 플레이북은 끝까지 가며, 끝에서 아무것도 보고되지 않음
. 같은 설정으로 제어 노드에 ID 를 적고 setup-cluster. 제어 노드는 재부팅되지 않고 "reboot it yourself" 가 나오며 설치는 계속됨
. `vfio_pci_reboot: true` 인데 일부러 틀린 ID 를 적어 add-node — 3번에서 이미 거부되므로, initramfs 를 망가뜨려 재부팅 후에도 안 묶이게 만들고 실행. 플레이북이 그 자리에서 멈춤

6번과 7번과 8번이 이 기능의 실질적 회귀 테스트이고, 재부팅을 켜고 쓴다면 10번이 더해집니다.
넷 다 "재부팅하지 않은 상태"나 "설치본이 소유하지 않은 설정"을 건드리는 쪽이고, 그것이 이
기능에서 조용히 틀리는 지점입니다.

=== DGX 처럼 같은 모델이 여러 장인 노드

NVSwitch 도 PCI 장치라 ID 를 하나 더 적으면 그만이고, 개수는 상관없습니다. GPU 8장과 NVSwitch
여러 개가 ID 두 개로 전부 묶이고, softdep 은 modalias 로 유도되므로 `nvidia` 한 줄로 정리됩니다.

걸리는 것은 `ids=` 가 모델 단위라는 점입니다. 같은 모델 중 일부만 고를 수 없으므로, GPU 8장이
전부 같은 모델인 DGX 에서는 **전부 넘기거나 하나도 안 넘기거나** 입니다. 위 softdep 문단의 "카드를
두 장 꽂은 노드가 한 장만 넘긴다면"은 두 장이 서로 다른 모델일 때의 이야기이고, DGX 에서는
해당하지 않습니다. 일부만 넘겨야 한다면 `ids=` 가 아니라 PCI 주소별 `driver_override` 이고, 그건
지금 구조가 아닙니다.

`nvidia-fabricmanager` 는 설치본이 건드리지 않습니다. 번들의 nvidia 패키지는 컨테이너 툴킷뿐이고
드라이버도 FM 도 사이트 것입니다. DGX 에서 GPU 와 NVSwitch 를 통째로 넘기면 FM 은 게스트가 띄우고
호스트는 띄우면 안 되는데, 호스트에 FM 이 떠 있는 채로 넘기면 증상은 또 "통과가 안 된다" 하나뿐이니
알고 시작해야 합니다.

IOMMU 그룹도 오디오 기능 수준이 아닙니다. DGX 는 GPU 와 NVSwitch 가 PCIe 스위치 뒤에 걸려 있어
ACS 설정에 따라 스위치 아래가 한 그룹이 될 수 있습니다. `list-pci-devices.yml` 이 그룹을 보여
주는 것은 이 때문이고, 재부팅해서 IOMMU 를 올린 뒤 한 번 봐야 무엇을 함께 적어야 하는지 알 수
있습니다.

== 컨테이너에게 GPU 를 주는 쪽 (CDI)

가상머신에 카드를 통째로 넘기는 것과 반대편입니다. 이쪽은 설치본이 거의 아무것도 하지 않는데,
그게 게으름이 아니라 확인한 결과입니다.

=== 설치본이 할 일이 없습니다

containerd 2.3.5 가 `enable_cdi = true` 와 `cdi_spec_dirs = ['/etc/cdi', '/var/run/cdi']` 를 기본으로
들고 있습니다(`containerd config dump` 로 확인). 그리고 그 디렉토리에 들어갈 스펙은
`nvidia-cdi-refresh` 가 씁니다 — `nvidia-container-toolkit-base` 에 딸려 오는 systemd 유닛 두 개로,
툴킷 설치·드라이버 설치·부팅 때마다 돕니다. `install-packages.sh` 는 이미 그 패키지를 전 노드에
깔고, 드라이버는 사이트 것입니다.

즉 **노드는 설치본이 아무것도 안 해도 준비됩니다.** 남는 가치는 "안 됐을 때 말해 주는 것" 하나뿐이고,
그래서 이 기능은 검사 스크립트와 보고 태스크가 전부입니다.

=== 다만 파드가 받는 스펙은 refresh 의 것이 아닙니다

실물에서 확인하고 고친 부분입니다. NVIDIA device plugin 을 `--device-list-strategy=cdi-cri` 로
돌리면 그 플러그인이 **자기 CDI 스펙을 따로 생성해서** 그것을 넘깁니다 —
`/var/run/cdi/k8s.device-plugin.nvidia.com-gpu.json`, 장치 이름은
`k8s.device-plugin.nvidia.com/gpu=<uuid>` 입니다. `nvidia-cdi-refresh` 가 쓴 `nvidia.yaml` 을
**치워도 파드는 GPU 를 정상적으로 받습니다** (k3s 와 이 설치본 클러스터 양쪽에서 확인).

그래도 refresh 를 무시하면 안 됩니다. 노드가 CDI 로 GPU 를 낼 수 있는 상태인지를 **device plugin
없이** 말해 주는 것은 그쪽뿐이고, 검사 스크립트가 보는 것도 그것입니다. 다만 "refresh 가 쓴 스펙을
containerd 가 읽어서 파드에 꽂힌다" 는 서술은 틀렸습니다. 둘은 같은 디렉토리를 쓰는 별개의 경로이고,
파드에 실제로 꽂히는 쪽은 플러그인이 만든 것입니다.

(`check-nvidia-cdi.sh` 의 `nvidia-ctk cdi list` 집계는 두 스펙을 다 셉니다 — `nvidia.com/gpu` 가
`k8s.device-plugin.nvidia.com/gpu` 의 부분 문자열이라서요. 묻는 것이 "CDI GPU 장치가 하나라도
있는가" 라 판정은 그대로 옳습니다.)

`.path` 유닛이 감시하는 것은 `/lib/modules/<커널>/modules.dep` 와 `/usr/bin/nvidia-ctk` 입니다.
드라이버를 어떤 방식으로 깔든(deb/rpm/runfile/DKMS) `depmod` 가 `modules.dep` 를 건드리므로 잡힙니다.
그리고 유닛에 `ConditionPathExists=|.../nvidia-smi` 가 걸려 있어서 드라이버 없는 노드에서는 **실패가
아니라 조건 불만족으로 건너뜁니다** — 전 노드에 툴킷을 깔아도 잡음이 없는 이유입니다.

=== 선언하지 않고 물어봅니다

어느 노드에 GPU 가 있는지를 인벤토리에 적지 않습니다. 그건 기계에 대한 사실이라 물어보는 쪽이 싸고
참입니다. 적어 두면 현실과 어긋날 수 있고, 어긋난 장부는 없는 것만 못합니다.

그래서 검사는 넷으로 갈립니다 — `nvidia-ctk` 이 없으면 침묵(그건 패키지 문제고
`install-packages.sh` 가 말합니다), `nvidia-smi` **바이너리 자체가** 없으면 침묵(GPU 없는
노드입니다), 바이너리는 있는데 드라이버에 닿지 못하면 **보고**(아래), 드라이버는 있는데 CDI 장치가
0 이면 **보고**합니다.

=== 패스스루 노드에서 툴킷 유닛이 영구히 돕니다

이 기능과 vfio-pci 가 만나는 자리이고, 실제로 돌려 보니 **서로를 밟습니다.**

카드를 vfio-pci 로 넘긴 노드는 드라이버가 그 카드를 못 봅니다. 컨테이너 쪽으로는 보고할 게 없습니다 —
일부러 넘긴 것이니까요. 문제는 툴킷이 들고 오는 `nvidia-cdi-refresh.service` 입니다. 첫 `ExecStart`
가 `nvidia-smi -L` 인데 `-` 접두어가 없어 실패가 치명적이고, `Restart=on-failure` 에
`RestartSec=1s` 이며 start limit 이 실효가 없습니다. 그래서 **노드가 켜져 있는 내내 1초마다 실패하고
재시작합니다.** L40S 4장을 묶고 재부팅한 호스트에서 부팅 5분 만에 재시작 45회를 봤습니다.

ExecCondition 은 `modules.dep` 에 `nvidia.ko` 가 적혀 있는지만 보므로, **드라이버 패키지가 깔려
있기만 하면** 카드를 하나도 못 보더라도 통과합니다. 드라이버가 아예 없는 노드는 이 조건에서 걸려
`inactive` 로 앉아 있어 루프가 생기지 않습니다 — 그래서 갈림길을 `nvidia-smi` **바이너리 유무**로
잡습니다. 모듈이 아니라 바이너리인 이유는, 커널만 올라가고 드라이버가 따라가지 못한 노드도 같은
상태에 빠지고 같은 보고를 받아야 하기 때문입니다.

=== 일부러 넘긴 것인지는 물어볼 수 없어서 선언합니다

드라이버가 GPU 를 못 보는 노드가 둘인데 겉으로 같습니다 — 일부러 넘긴 노드와, 커널이 드라이버를
앞질렀거나 하드웨어가 상한 노드입니다. **기계에 물어서 가를 수 없습니다.** `vfio_pci_device_ids` 도
답이 못 됩니다. 그 변수는 GPU 전용이 아니라서 거기 적힌 것이 NIC 이나 USB 컨트롤러일 수 있고, 남은
카드가 남으라고 남은 것인지도 말해 주지 않습니다.

그래서 `gpu_passthrough` 를 선언합니다. 뜻은 **"이 노드의 GPU 는 전부 게스트로 간다"** 이고, 참이면
`vfio_pci_device_ids` 가 필수입니다(`validate-hostvars.py`). 이 변수가 있으면 갈립니다:

* `true` + 드라이버가 못 봄 → 시킨 대로입니다. 드롭인이 이미 유닛을 재웠으니 **보고할 것 없음**
* `false` + 드라이버가 못 봄 → **사고입니다.** 카드를 뭔가가 가져갔고 유닛은 계속 돕니다. 보고

이 브랜치가 `nvidia_gpu` 를 지우면서 변수를 새로 들이는 게 모순처럼 보이지만 성질이 다릅니다.
`nvidia_gpu` 는 기계에 대한 사실("이 노드에 GPU 가 있다")이라 물어보는 쪽이 싸고 참이었습니다.
`gpu_passthrough` 는 **의도**라서 물어볼 데가 없습니다.

=== 선언은 노드가 검증합니다

의도라고 해서 믿고 넘어가지는 않습니다. "전부" 라는 주장이 카드 한 장 틀리면, 드라이버가 여전히
GPU 를 보는 노드에서 그 유닛의 재시도를 빼앗는 꼴이 됩니다. 그래서 `setup-vfio-pci.sh` 가 노드에서
맞춰 봅니다 — `true` 인데 id 에 안 걸리는 NVIDIA 카드가 있으면 거부, `false` 인데 id 가 덮고 있으면
거부.

=== 클래스가 아니라 무엇이 잡을 카드인지로 셉니다

디스플레이 클래스(`03xx`)를 세면 안 됩니다. **서버는 자기 콘솔을 그릴 장치를 항상 하나 들고
있습니다** — 이 하드웨어에서는 L40S 네 장(`0302`) 옆의 Matrox G200(`0300`), BMC 의 VGA 입니다.
그걸 게스트에게 넘기면 호스트 콘솔이 같이 사라지므로 아무도 안 넘기고, 세어 넣으면
`gpu_passthrough: true` 는 **어떤 서버에서도 만족할 수 없는 주장**이 됩니다. 실물에서 첫 실행이
정확히 그렇게 거부당했습니다.

`boot_vga` 로 빼는 것도 답이 아닙니다. 그 값은 "메인보드 GPU" 가 아니라 **펌웨어가 부팅 때 주
디스플레이로 고른 장치**입니다. 서버에서 보통 BMC 가 되는 건 펌웨어가 콘솔로 그걸 써서일 뿐이고,
온보드 비디오가 없는 워크스테이션에서는 외장 카드가, BIOS 에서 Primary Display 를 PCIe 로 바꾼
서버에서는 역시 외장 카드가 그 값을 받습니다. 그 구성에서는 BMC 가 "안 넘긴 GPU" 로 세어져 같은
거부가 되살아납니다. 순수 3D 컨트롤러(`0302`)는 VGA arbiter 대상이 아니라 그 파일이 아예 없기도
합니다.

그래서 **그 장치를 무엇이 잡을 것인지**를 봅니다. softdep 목록을 만드는 것과 같은 방식입니다 —
`modalias` 를 `modprobe -R` 에 물으면 BMC 는 `mgag200`, L40S 는 `nvidiafb nouveau nvidia_drm
nvidia` 가 나옵니다. 펌웨어가 뭘 골랐는지 추측할 필요가 없고, 이미 vfio-pci 에 묶여 있는 노드에서도
답이 같습니다(현재 바인딩이 아니라 카드가 자기를 뭐라고 말하는지를 읽으므로).

여기서 nvidia 를 이름으로 적는 것은 `vendor_drivers_of_device_ids` 가 피하려는 "카드 목록을 적어
두는 일" 과 다릅니다. 묻는 것이 "이게 GPU 인가"(아무도 적어 둘 수 없는 질문)가 아니라 **"이게 refresh
유닛이 필요로 하는 카드인가"** 이고, 그 유닛이 돌리는 것이 `nvidia-smi` 이기 때문입니다.

`nouveau` 도 같이 세는 이유는 **드라이버가 없는 노드에서도 답이 나와야** 하기 때문입니다. 카드를 다
넘기는 호스트는 NVIDIA 드라이버를 쓸 일이 없어 보통 안 깔고, 그게 이 기능의 주 대상입니다. 그 노드에서
`modprobe -R` 이 답하는 것은 커널이 들고 오는 모듈뿐입니다:

* Ubuntu 22.04 — `nvidiafb nouveau`. `nvidiafb` 는 선택 패키지가 아니라 기본 `linux-modules` 것
* RHEL 8.10 — `nouveau`. 역시 기본 `kernel-modules` 것

둘 다 기본 커널 패키지라 항상 있습니다. **`nouveau` 를 블랙리스트해도 답이 바뀌지 않습니다** — 패스스루
호스트에서 흔히 하는 일이라 따로 확인했는데, alias 해석은 로딩 정책과 무관합니다.

한계 하나: `nouveau` 와 `nvidiafb` 가 **둘 다** 없는 커스텀 커널에서는 이 검사가 조용해집니다. 선언
검증이 약해지는 것이고, 그런 노드엔 드라이버도 없으니 루프도 드롭인도 무관해서 기능상 피해는 없습니다.

=== 드롭인 하나로 유닛을 재웁니다

`gpu_passthrough` 가 참이면 설치본이 파일 하나를 씁니다:

[source]
----
/etc/systemd/system/nvidia-cdi-refresh.service.d/99-ki-vfio-pci.conf
[Service]
Restart=no
----

`systemctl disable` 이 아닌 이유가 있습니다. **툴킷 postinst 가 명시적으로 `unmask` 하고 다시
`enable` 하고 `start` 합니다.** `install-packages.sh` 는 `dpkg -R -i` 를 upgrade 마다 돌리므로,
손으로 끈 유닛은 **설치본이 업그레이드할 때마다 스스로 되살립니다.** `/lib` 은 패키지 것이고 `/etc`
는 기계를 운영하는 쪽 것이라, 드롭인은 postinst 가 건드리지 않습니다.

`Restart=no` 이지 start limit 을 넓히는 것이 아닌 이유도 있습니다. 벤더의 한도가 실패하는 까닭이
"제어할 수 없는 실패 시간에 맞춰 잰 값" 이라서인데, 여기서 숫자를 고르면 같은 내기를 다시 하는
것입니다. GPU 를 하나도 안 남긴다고 선언한 노드에서는 재시도가 찾아낼 것이 없으므로, 재시도를 안
하는 것이 원하는 전부이고 그건 무엇이 얼마나 걸리든 상관없습니다.

드라이버가 있든 없든 씁니다. 카드를 다 넘긴 호스트는 드라이버를 쓸 일이 없어 보통 안 깔지만, 사이트
이미지가 들고 오는 경우가 흔하고 **업그레이드로 어느 날 들어올 수도** 있습니다. 파일이 먼저 가 있으면
그때 막힙니다. 그리고 다른 세 파일과 같은 수명을 삽니다 — 노드가 패스스루를 그만두면 reset 이 같이
걷어내고 유닛은 제 행동을 돌려받습니다.

=== 유닛 상태가 아니라 결과를 봅니다

`nvidia-cdi-refresh.service` 는 oneshot 이라 **정상일 때 `inactive (dead)`** 이고, 드라이버 없는
노드에서는 `condition failed` 입니다. `systemctl is-active` 로 보면 멀쩡한 노드를 고장으로
보고합니다. 그래서 `nvidia-ctk cdi list` 가 장치를 내놓는지를 봅니다 — containerd 가 읽는 것과 같은
디렉토리를 같은 방식으로 읽으므로, 여기서 비면 거기서도 빕니다.

=== MIG 재구성은 손으로 해야 합니다

NVIDIA 문서가 명시하는 두 구멍이 있습니다 — 드라이버 *제거* 와 **MIG 재구성** 때는 스펙이 다시
생성되지 않습니다. MIG 프로파일을 바꾸면 장치 집합이 바뀌는데 스펙은 그대로라, 재구성 뒤에는
`systemctl restart nvidia-cdi-refresh.service` 를 직접 돌려야 합니다. 설치본이 메울 수 없는 종류라
검사 메시지와 이 문서에 적어 두는 것이 대응입니다.

`/dev/nvidia-caps/*`(MIG capability 노드)도 그 서비스가 만들지 않습니다. 만드는 것은
`nvidia-ctk system create-device-nodes --control-devices` 인데 그 옵션은 `nvidiactl`, `nvidia-uvm`,
`nvidia-modeset` 만 다룹니다. MIG 를 쓰는 사이트라면 확인이 필요한 지점입니다.

=== nvidia_gpu 와 nvidia 런타임을 없앴습니다

`nvidia_gpu` 는 노드에 벤더 런타임을 붙이는 변수였습니다. containerd 에는
`99-nvidia.toml` 드롭인이 `default_runtime_name = "nvidia"` 를 박고 nvidia 런타임을 정의했고,
docker 에는 `daemon.json` 의 `runtimes.nvidia` 가 들어갔습니다. 둘 다 지웠습니다.

CDI 가 같은 일을 런타임 교체 없이 하기 때문입니다. containerd 2.3.5 는 `enable_cdi` 와
`cdi_spec_dirs` 를 기본으로 들고 옵니다. 그러면 컨테이너는 runc 로 돌면서 장치만 주입받습니다 — 노드의 기본 런타임을 통째로 갈아 끼울 이유가
없습니다. 남겨 두면 노드마다 기본 런타임이 다른 클러스터가 되고, 그 차이를 아는 것은 인벤토리의
변수 하나뿐입니다.

**대가가 있고 작지 않습니다.** 이제 파드가 GPU 를 받는 길은 CDI 하나뿐이라, device plugin 을
`--device-list-strategy=cdi-cri` 로 돌리지 않으면 **GPU 가 파드에 꽂히지 않습니다.** 기존
클러스터가 다른 전략(`envvar`, `volume-mounts`)을 쓰고 있었다면 이 릴리스에서 같이 바꿔야 합니다.

그리고 대가가 하나 더 있는데, 실제로 깔아 보고서야 나왔습니다. **device plugin 자신이 GPU 를 볼
길이 있어야 합니다.** 플러그인은 장치를 세려고 NVML 을 불러오는데, 드라이버가 주입되지 않은
컨테이너에는 그게 없습니다. 아무 준비 없이 띄우면 이렇게 죽습니다:

----
error starting plugins: unable to validate flags:
CDI --device-list-strategy options are only supported on NVML-based systems
----

=== 그래서 nvidia 런타임을 핸들러로는 남깁니다

지운 것이 사실은 **두 가지**였습니다 — 런타임을 핸들러로 등록하는 것과, 그것을 노드의 기본
런타임으로 삼는 것. 문제였던 쪽은 후자입니다. 노드의 모든 컨테이너가 필요도 없는 shim 을 거치게
되고, 노드마다 기본 런타임이 다른 클러스터가 되며, 그 차이를 아는 것은 인벤토리의 변수
하나뿐이었습니다. 앞쪽은 죄가 없고, 없애고 나니 위의 부트스트랩 문제가 생겼습니다.

그래서 `99-nvidia.toml` 을 되살리되 **`default_runtime_name` 없이** 핸들러만 등록합니다. 기본
런타임은 `runc` 이고 CDI 는 containerd 가 직접 읽습니다. `runtimeClassName: nvidia` 를 적은 파드만
그 핸들러를 거치고, 그게 device plugin 이 드라이버를 얻는 길입니다.

벤더 도구가 같은 선을 긋습니다. `nvidia-ctk runtime configure --runtime=containerd` 는 핸들러를
등록할 뿐이고, 기본 런타임을 바꾸려면 `--set-as-default` 를 따로 줘야 합니다. 이전 릴리스가 박아
두었던 `default_runtime_name = "nvidia"` 가 바로 그 옵트인을 설치본이 대신 눌러 둔 것이었습니다.

드롭인에는 핸들러 블록만 넣습니다. containerd 는 `config.toml` 을 **대체하지 않고 병합**하므로
`runtimes.runc` 는 자기 옵션을 지키고 `default_runtime_name` 도 `runc` 로 남습니다(실측). 이전
템플릿이 `runc` 와 `pinned_images` 를 다시 적어 둔 것은 불필요했고, 두 군데를 맞춰야 하는 짐만
됐습니다.

**전 노드에 조건 없이 씁니다.** `/usr/bin/nvidia-container-runtime` 은
`nvidia-container-toolkit-base` 가 주고 `install-packages.sh` 가 그 패키지를 전 노드에 깔기
때문에, 노드에 물어볼 것이 없고 인벤토리 변수도 필요 없습니다. **`gpu_passthrough: true` 인
노드에도 씁니다** — 거기서도 핸들러는 아무도 고르지 않으면 아무 일도 하지 않습니다. GPU 워크로드를
그 노드에서 막는 것은 핸들러가 아니라 `nvidia.com/gpu` 리소스이고, 그 노드는 드라이버가 카드를 못
보므로 광고할 것이 없습니다. device plugin DaemonSet 을 그런 노드에서 빼는 것(nodeSelector)은
사이트 몫입니다.

=== RuntimeClass 는 사이트가 만듭니다

핸들러는 노드의 것이고 `RuntimeClass` 는 클러스터의 것입니다. 이 설치본은 `kubectl apply` 를 한
번도 쓰지 않고 클러스터 안의 것은 전부 kubeadm 을 통하므로, 여기서 첫 예외를 만들지 않습니다.
device plugin 과 같은 자리입니다:

[source,yaml]
----
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: nvidia
handler: nvidia
----

그리고 device plugin DaemonSet 에 `runtimeClassName: nvidia` 를 적습니다. 그러면 플러그인이
드라이버를 받아 NVML 이 살고, 워크로드 파드는 `--device-list-strategy=cdi-cri` 로 containerd 가
직접 주입합니다.

`nvidia-ctk runtime configure` 는 **돌릴 필요가 없고 돌리면 안 됩니다.** 그 명령은 자기 드롭인을
`/etc/containerd/conf.d/` 에 넣고 `config.toml` 의 `imports` 를 고치는데, 설치본은
`/etc/containerd/config.d/` 를 쓰고 다음 실행에서 `config.toml` 을 다시 렌더하므로 그 수정이
날아갑니다. 핸들러는 이미 등록돼 있습니다.

드라이버 라이브러리를 플러그인 파드에 hostPath 로 넣는 방법도 되긴 합니다. 런타임을 못 쓰는
상황의 차선책이고, 이때 `/usr/lib/x86_64-linux-gnu` 를 통째로 마운트하면 컨테이너의 libc 까지
덮여 `stack smashing` 으로 죽으므로 `libnvidia-ml` 과 `libcuda` 만 따로 모은 디렉토리를 넣어야
합니다. NVIDIA GPU Operator 는 이 문제를 자기가 해결합니다.

`setup-containerd.sh` 는 `99-nvidia.toml` 을 매 실행마다 지웁니다. `config.toml` 이 디렉토리를
통째로 import 하므로, 이전 릴리스가 쓴 드롭인이 남아 있으면 그 노드는 계속 nvidia 런타임을
기본으로 씁니다. "첫 실행" 을 아는 실행이 없으니 조건 없이 지웁니다.

=== 지운 변수는 지웠다고 말합니다

`nvidia_gpu` 를 클래스 목록에서 빼기만 하면, 그 변수를 적어 둔 기존 인벤토리는 **"아무 클래스에도
없는 변수"** 로 거부당합니다. 틀린 안내입니다 — 분류를 잊은 게 아니라 없어진 변수인데, 어디에
넣으라고 시키는 꼴입니다.

그래서 `ki_removed_vars` 에 무엇이 대신하는지와 함께 적어 두고, `validate-hostvars.py` 가 그
경우에 다른 메시지를 냅니다. 무시하지 않고 거부하는 이유는, 조용히 버려진 변수는 인벤토리가
말하는 것과 다르게 만들어진 노드이고 그걸 알려 주는 것이 아무것도 없기 때문입니다. 거부는 파일에서
한 줄 지우는 값이면 끝납니다.

=== device plugin 은 사이트 몫입니다

여기까지가 "노드가 CDI 로 GPU 를 낼 수 있는 상태"입니다. 파드가 실제로 GPU 를 받으려면 device
plugin 이 있어야 하고, 이 설치본은 애드온을 설치하지 않습니다 — 레지스트리 이미지 목록에도
없습니다. 그리고 plugin 을 `--device-list-strategy=cdi-cri` 로 돌려야 containerd 가 주입합니다.
**"CDI 를 지원한다"가 "파드가 GPU 를 받는다"로 읽히면 안 되는 경계가 여기입니다.**

== 번들에 담는 컨테이너 이미지

번들은 두 종류의 이미지를 나릅니다. ki cp 서비스가 도커로 실행하는 이미지와, 클러스터가
당겨 쓰도록 레지스트리에 채워 넣을 이미지입니다. 목적지가 다르면 적재 방법이 다르고,
적재 방법이 다르면 담는 포맷도 달라야 합니다.

[cols="1,2,2"]
|===
|  |`ki-cp-service-images/` |`ki-cp-<registry>-images/`

|적재
|`docker load`
|`crane push`

|포맷
|docker archive
|OCI layout

|단위
|서비스당 tar 하나
|이미지당 디렉토리 하나
|===

=== 서비스 이미지를 레지스트리에서 받을 수는 없습니다

레지스트리에 넣고 거기서 받게 하면 디렉토리가 하나로 줄지만 순환합니다. 레지스트리 주소를
풀려면 dns 서버가 떠 있어야 하는데 그 dns 서버가 이 이미지 중 하나이고, 레지스트리 자신도
마찬가지입니다. 그래서 이 다섯은 끝까지 tar 에서 로드해야 하고, 두 디렉토리는 합쳐지지
않습니다.

=== 서비스 이미지가 OCI layout 일 수 없는 이유

`docker load` 가 읽는 것은 docker archive 뿐입니다. OCI layout 을 넘기면 docker archive 로
파싱하다 `blobs/json` 이 없다며 실패합니다. 도커를 containerd 이미지 스토어로 바꾸면 읽지만,
그러자고 ki cp 노드 도커의 스토어를 통째로 갈아엎을 이유가 없습니다. 이 다섯은 다이제스트로
참조되지도 않습니다.

=== 레지스트리 이미지가 docker archive 일 수 없는 이유

docker archive 를 푸시하면 매니페스트가 재구성되면서 다이제스트가 바뀝니다. OCI layout 은
받은 것을 그대로 올립니다. 차트가 이미지를 다이제스트로 고정하는 일이 흔하므로, 바꾸지 않는
쪽을 택합니다.

=== 이미지당 디렉토리 하나인 이유

여러 이미지를 한 OCI layout 에 넣을 수는 있고 레이어도 공유됩니다. 그런데 `crane push` 는
항목이 둘 이상인 layout 을 참조 하나로 올리라고 거부합니다. 각각을 제 참조로 올리려면
이미지마다 layout 이 하나씩 있어야 합니다.

디렉토리의 경로가 곧 푸시될 참조입니다. `kube-apiserver:v1.34.1` 디렉토리는
`<레지스트리>/kube-apiserver:v1.34.1` 로 올라갑니다. 그래서 파일과 참조를 이어 주는 별도의
매니페스트가 필요 없습니다.

=== 플랫폼 하나만 담습니다

업스트림 태그는 대개 멀티아치 인덱스입니다. 인덱스를 통째로 담으면 업스트림 다이제스트와
정확히 일치하지만, `pause:3.10.1` 한 개가 547MB 가 됩니다. 윈도우 변형까지 전부 들어오기
때문입니다. `--platform linux/amd64` 로 받으면 340KB 입니다.

그래서 amd64 매니페스트만 담고, 그 경우 레지스트리가 서비스하는 다이제스트는 인덱스의 것이
아니라 amd64 매니페스트의 것이 됩니다. *인덱스 다이제스트로 고정한 차트는 이 레지스트리에서
찾지 못합니다.* 도커로 받아 도커로 올리던 이전 방식도 플랫폼 하나만 담았으므로 새로 생긴
제약은 아니고, 이전 방식은 그 위에 매니페스트까지 재구성해 어느 쪽과도 다른 다이제스트를
내놓았습니다.

=== 레이어를 압축된 채로 나릅니다

`docker save` 는 레이어를 풀어서 담고 `crane pull` 은 레지스트리에 있던 그대로, 즉 압축된
채로 담습니다. 서비스 이미지 다섯이 379MB 에서 125MB 가 된 것이 그 차이입니다.

== apiserver 로드밸런서의 런타임 관리

인증서 갱신이나 컴포넌트 업그레이드는 apiserver 를 한 번 내립니다. 로드밸런서가 그 사실을
헬스체크로 알아내는 구조에서는, 알아내기까지 보낸 요청이 전부 실패합니다. `/readyz` 로
바꾸면서 그 창이 줄긴 했지만 닫히지는 않습니다. 미리 빼 두는 수밖에 없고, 그래서 haproxy 의
런타임 api 를 열고 `lb-admin.sh` 로 말을 겁니다.

=== 포트가 아니라 컨테이너 안의 유닉스 소켓인 이유

런타임 api 는 자격증명을 받지 않고 백엔드를 내릴 수 있습니다. 포트로 내보내면 호스트
루프백뿐 아니라 같은 도커 브리지에 있는 모든 컨테이너가 닿습니다. 컨테이너 안에만 두면
거기 닿는 조건이 도커 데몬에 말을 걸 수 있는 것, 즉 노드의 root 인 것과 같아집니다.

노드에는 socat 이 없는 배포판이 있고 bash 의 `/dev/tcp` 는 유닉스 소켓을 못 엽니다.
haproxy 이미지가 socat 을 가지고 있어서, `docker compose exec` 로 그것을 씁니다. 소켓 경로를
`/var/lib/haproxy` 아래 두는 것은 컨테이너의 haproxy 사용자가 쓸 수 있는 디렉토리가 거기뿐이기
때문입니다. `/var/run` 에 두면 바인드 자체가 권한 거부로 실패합니다.

=== maint 가 아니라 drain 인 이유

백엔드에 `on-marked-down shutdown-sessions` 가 걸려 있습니다. 죽은 apiserver 에 물린 세션을
끊어 주자는 설정인데, `maint` 는 서버를 내리는 것이라 이 설정이 같이 발동해서 세션을 끊습니다.
`drain` 은 새 연결만 막고 있던 세션은 그대로 둡니다. 무중단으로 빼려는 목적에 맞는 것은
`drain` 쪽입니다.

=== wait-ready 가 헬스체크 결과가 아니라 운영 상태를 보는 이유

`show stat` 의 `check_status` 는 마지막 체크 결과(`L7OK`)고, `status` 는 로드밸런서가 그 서버를
어떻게 취급하는지(`UP`)입니다. 체크가 막 통과하기 시작한 서버는 `rise` 를 채울 때까지
`DOWN 1/2` 이며 트래픽을 받지 않습니다. 다음 노드로 넘어가도 되는지를 판단하려면 `status` 가
`UP` 인지를 봐야 합니다.

=== 모든 ki cp 노드에서 빼야 합니다

ki cp 노드는 각자 제 로드밸런서를 돌리고 VIP 는 언제든 옮겨 갈 수 있습니다. 한 노드에서만
빼 두면 VIP 가 옮겨 간 순간 아직 빼지 않은 로드밸런서가 그 백엔드로 다시 보냅니다. 노드를
정말로 뺀 상태는 모든 ki cp 노드에서 `drain` 한 상태입니다.

== 모니터링

ki cp 서비스는 노드에서 도커 컨테이너로 돕니다. 쿠버네티스 오브젝트가 아니라서 클러스터 안의
수집기가 서비스 디스커버리로 찾지 못하고, 무엇을 어떤 조건으로 내주는지는 서비스마다
따로 정해야 합니다.

=== 메트릭은 stats 포트에 인증 없이 답합니다

로드밸런서가 무엇을 하고 있는지는 지금까지 stats 페이지로만 볼 수 있었습니다. 사람이 열어
보는 페이지라 백엔드가 언제 빠졌는지는 사람이 보고 있을 때만 알려집니다. `/metrics` 는
같은 것을 긁어 갈 수 있는 형식으로 답할 뿐이고, 익스포터가 이미지에 컴파일되어
있어서(`USE_PROMEX=1`) 노드에 도는 것이 늘지 않습니다.

stats 포트에 얹은 것은 답하는 내용이 stats 페이지와 같기 때문입니다. 그 포트는 루프백과 노드의
내부망 주소에만 공개되고 VIP 에는 올라가지 않으므로, 노드 밖에서 닿으려면 내부망 안이어야
합니다. 노드 안에서는 그냥 닿습니다 — 컨테이너 안의 bind 는 0.0.0.0 이고 브리지 네트워크라,
같은 docker0 의 다른 ki cp 서비스가 컨테이너 주소로 부릅니다. admin 소켓을 포트로 내보내지
않은 이유가 바로 그 경로인데, 여기서는 받아들입니다. 내주는 것이 stats 페이지의 숫자와
노드 이름 — 그 컨테이너들이 이미 다 풀고 있는 이름 — 이지 백엔드를 내릴 수 있는 api 가
아니기 때문입니다.

인증을 걸지 않았습니다. stats 비밀번호는 클러스터마다 새로 만들어져 ki cp 노드에만 있으므로,
여기에 인증을 걸면 수집기마다 클러스터별로 다른 비밀을 쥐여 줘야 합니다. 그것은 사람이 가끔
여는 페이지가 치를 값이지 15초마다 긁는 기계가 치를 값이 아닙니다. 내주는 것은 stats 페이지를
못 읽던 사람이 같은 숫자를 다른 경로로 읽게 되는 것인데, 그 경로에 닿는 조건은 위의
둘뿐입니다.

`http-request` 규칙은 stats 애플릿보다 먼저 돕니다. 그래서 `/metrics` 는 익스포터가 답하고,
`monitor-uri` 가 먼저 가로채는 `/lb-healthz` 를 뺀 나머지 경로는 그대로 페이지로 넘어갑니다.

== VIP 를 언제 옮기는가

VIP 는 apiserver 로드밸런서의 주소이면서 dns 서버와 레지스트리의 주소이기도 합니다.
옮기면 그 위의 모든 연결이 끊어지므로, 옮겨서 나아지는 경우에만 옮겨야 합니다.

=== 헬스체크가 백엔드 유무를 보면 안 됩니다

`/lb-healthz` 가 "쓸 수 있는 백엔드가 있는가"까지 보게 만들었다가 설치가 통째로
교착됐습니다. 새 클러스터에는 apiserver 가 아직 하나도 없으니 모든 노드가 체크에 실패하고,
아무도 VIP 를 들지 않고, 그러면 레지스트리의 dns 이름이 안 풀리고, kubeadm 은 첫 apiserver 를
만들 이미지를 못 받습니다. 스스로를 막는 구조입니다.

교착이 아니더라도 판단 기준으로 틀렸습니다. 모든 노드의 로드밸런서는 같은 백엔드 목록을
봅니다. apiserver 가 전부 닿지 않는 상황에서 VIP 를 옮겨 봐야 가는 곳도 똑같고, 대신 VIP 에
같이 붙어 있는 dns 와 레지스트리 세션만 끊깁니다. 노드마다 달라지는 값, 그래서 판단에 쓸 수
있는 유일한 값은 "이 노드의 로드밸런서가 살아 있는가" 입니다.

=== weight 가 아니라 FAULT 인 이유

`nopreempt` 와 `weight` 는 같이 못 씁니다. weight 는 우선순위를 깎을 뿐이고, 낮아진
우선순위를 보고 피어가 가져가는 행위가 곧 preempt 라서 `nopreempt` 가 그것을 막습니다.
체크가 실패해도 MASTER 는 계속 advert 를 보내는 살아 있는 MASTER 이므로, 둘을 같이 걸면
로드밸런서가 멈춘 노드가 VIP 를 끝까지 붙들고 있습니다. 실측으로 50초 동안 전 구간 거부였습니다.

weight 를 빼면 실패한 스크립트가 인스턴스를 FAULT 로 보냅니다. 노드가 advert 자체를 멈추니
피어는 "내가 더 높아서"가 아니라 "아무도 안 들고 있어서" 가져갑니다. 우선순위 간격이 충분한지
따질 필요도 사라집니다.

=== 돌아온 노드는 VIP 를 되찾지 않습니다

`nopreempt` 가 없으면 장애 하나가 장애 둘이 됩니다. 로드밸런서가 죽어 VIP 가 넘어가고,
그 노드가 복구되는 순간 우선순위가 높다는 이유만으로 다시 가져오면서 지금 서비스 중인 노드의
연결을 전부 끊습니다. 실측으로 복구 15초 뒤에 두 번째 이동이 일어났습니다. 들고 있는 노드가
서비스하고 있다면 옮길 이유가 없습니다.

`nopreempt` 는 인스턴스가 MASTER 로 시작하면 무시되므로 모든 노드가 `state BACKUP` 입니다.
그 대가로 설치 후 VIP 가 node1 에 고정되지 않고 keepalived 가 먼저 안정된 노드에 붙습니다.
어느 ki cp 노드가 들든 서비스는 같으므로 받아들일 만하고, 대안은 설치마다 VIP 를 한 번씩
헛되이 옮기는 것입니다.

=== 설정이 바뀌어도 컨테이너를 다시 만들지 않습니다

노드를 넣거나 뺄 때마다 로드밸런서 컨테이너가 통째로 다시 만들어졌고, 그때마다 그 노드를
지나던 apiserver 연결이 전부 끊겼습니다. `docker compose down` 뒤 `up -d` 였기 때문인데,
`down` 이 있었던 이유는 `up -d` 만으로는 바인드 마운트된 `haproxy.cfg` 의 변경이 반영되지
않아서입니다.

이제 렌더 전후로 `haproxy.cfg` 를 해시로 비교해서, 바뀌었으면 `SIGUSR2` 를 보냅니다. haproxy
마스터가 새 설정으로 워커를 하나 더 띄우고 리스너를 넘긴 뒤 옛 워커에게 들고 있던 연결을
끝내게 하므로, 진행 중인 것은 끊기지 않습니다. `compose.yml` 자체가 바뀐 경우에는 compose 가
컨테이너를 갈아치우고 그쪽이 이미 새 설정을 읽었으므로, 컨테이너 ID 를 전후로 비교해서
그때는 reload 를 건너뜁니다.

이것만으로는 아무 효과가 없었습니다. `compose.yml` 이 **매번** 달라졌기 때문입니다. 아래를
보세요.

=== stats 비밀번호를 매번 새로 만들면 안 됩니다

`gather-facts.yml` 이 실행마다 `generate-password.sh` 를 불러 새 비밀번호를 만들었고, 그것이
`compose.yml` 의 `STATS_ADMIN_PW` 로 들어갔습니다. 그래서 플레이북을 돌릴 때마다
`compose.yml` 이 달라지고 compose 가 컨테이너를 다시 만들었습니다. 실측으로 `add-node` 전후
`compose.yml` 의 차이는 비밀번호 한 줄뿐이었는데 컨테이너는 교체되었습니다. 위의 reload 는
이것을 고치기 전까지 한 번도 실행되지 않습니다.

운영자 쪽에서도 쓸 수 없는 물건이었습니다. stats 페이지에 로그인하려면 `compose.yml` 을
열어 봐야 했고, 그렇게 알아낸 값은 다음에 무엇이든 실행하면 무효가 되었습니다.

그래서 비밀번호는 한 번 만들어 서비스 디렉토리의 `stats-password` 에 두고, `gather-facts.yml`
이 새로 만들기 전에 그 파일을 먼저 읽습니다. 읽는 곳이 제어 노드 자신인데도 노드 간 값이
갈리지 않는 이유는, 제어 노드가 반드시 ki cp 노드이고 모든 ki cp 노드가 같은 값을 받기
때문입니다. 제어 노드가 다른 노드로 옮겨가도 같은 값을 읽습니다. 별도의 전파 장치가 필요 없고,
파일이 서비스 디렉토리 안에 있으므로 `reset-k8s-cp-lb.sh` 가 서비스를 지울 때 같이 사라집니다.

=== reload 가 무중단의 전부는 아닙니다

옛 워커는 자기가 들고 있는 연결이 끝날 때까지 삽니다. apiserver 의 watch 는 client-go 가
30초마다 핑을 보내므로 idle 타임아웃에 걸리지 않고, 따라서 끝나지 않습니다. 실측으로 reload
두 번 뒤에도 첫 번째 이전의 워커가 살아 있었습니다. `hard-stop-after 30m` 이 그 상한이고,
`timeout client`/`timeout server` 와 같은 값이라 이 프록시가 붙들 수 있는 시간을 넘지 않습니다.

그 시점이 되면 옛 워커가 들고 있던 연결은 한꺼번에 끊깁니다. reload 가 얻는 것은 재렌더
**순간**에 서비스가 끊기지 않는 것, 그 사이 자연히 끝나는 연결은 살아남는 것, 남은 것도
한산할 때 끊긴다는 것입니다. `down` 뒤 `up` 이 즉시 전부 끊는 것과의 차이가 그것입니다.

=== 무중단을 무엇으로 재야 하는가

처음에는 VIP 로 raw TCP 를 몇 개 열어 두고 세어 보았는데, `remove-node` 뒤 여섯 개 중
다섯이 사라졌습니다. 로드밸런서를 의심할 일이 아니었습니다. 끊긴 시점에 세 apiserver 가
모두 200 이었고 백엔드도 전부 UP 이었으며, 컨테이너도 그대로였습니다. 연 지 정확히 31초
였다는 것이 답입니다. TLS 핸드셰이크를 하지 않은 연결을 apiserver 가 30초쯤 뒤에 닫습니다.
측정 대상이 잘못되었지 제품이 잘못된 것이 아니었습니다.

제대로 재려면 지키려는 것과 같은 연결이어야 합니다. `kubectl get events -A --watch` 를
VIP 로 띄우고 그 연결의 **로컬 포트**를 추적하면, 끊겼다가 다시 붙은 것과 계속 살아 있던
것이 구분됩니다. 그렇게 재니 `remove-node` 와 `add-node` 를 지나는 3분 동안 같은 포트가
유지되었고 이벤트 111 줄을 받았습니다. 그 사이 백엔드 재렌더와 reload 가 한 번씩 있었습니다.

세는 것이 연결의 **개수** 이면 무엇이 왜 끊겼는지 알 수 없습니다. 특정 연결의 생존을 보고,
끊긴 시각을 로드밸런서 쪽 사건과 맞춰 보아야 합니다.

== apiserver 에 인자를 더하는 자리

감사 정책이든 oidc 발급자든, 클러스터가 반드시 켜고 돌아야 하는 apiserver 옵션은 있습니다.
지금까지 그것을 넣는 방법은 노드마다 정적 파드 매니페스트를 손으로 고치는 것뿐이었고, 그렇게
넣은 것은 다음 `kubeadm upgrade` 가 지웁니다.

=== 패치 디렉토리가 아니라 ClusterConfiguration 입니다

kubeadm 의 `patches` 디렉토리가 후보였습니다. 이미 kubelet 설정을 노드별로 얹는 데 쓰고 있어서
자리가 있고, 파일을 하나 더 놓으면 되는 것처럼 보입니다.

ClusterConfiguration 을 고른 이유는 수명입니다. 패치는 노드의 파일이라 노드마다 배포해야 하고,
`kubeadm upgrade` 에 `--patches` 를 넘기지 않으면 업그레이드가 지나가면서 조용히 빠집니다.
ClusterConfiguration 은 클러스터의 ConfigMap 이라 나중에 조인하는 컨트롤 플레인 노드가 그것을
읽고, 업그레이드도 그것을 읽습니다. 한 군데에 두면 "어느 노드에는 있고 어느 노드에는 없는
인자" 라는 상태가 아예 만들어지지 않습니다.

`apiServer.extraArgs` 와 `apiServer.extraVolumes` 는 v1beta4 가 이미 들고 있는 필드라
설치본이 새로 만드는 개념도 아닙니다.

=== 올리는 것만으로는 아무 일도 일어나지 않습니다

`cluster_config` 클래스는 설정을 다시 써서 올리는 것으로 끝납니다. 인증서 유효기간처럼 "다음에
발급할 때 읽히는" 값에는 그것이 맞습니다.

apiserver 인자는 다릅니다. 지금 도는 apiserver 가 무엇을 들고 있는지는 kubelet 이 읽는
매니페스트 파일이 정하고, 그 파일은 ConfigMap 이 바뀐다고 다시 쓰이지 않습니다. 올리기만 하면
값은 클러스터에 있는데 apiserver 는 예전 그대로이고, 반영되지 않았다는 사실을 말해 주는 것이
아무것도 없습니다. 그래서 `control_plane` 은 별도 클래스이고 적용이 두 단계입니다 — 올리고,
그 다음 노드마다 매니페스트를 다시 씁니다. 올리는 쪽은 `control_plane` 이 바뀌었을 때도 돌아야
합니다. 노드가 읽는 것이 그 ConfigMap 이기 때문입니다.

=== 다시 쓰는 명령이 upgrade node phase control-plane 인 이유

`kubeadm init phase control-plane apiserver` 는 InitConfiguration 을 요구합니다. 조인해서
들어온 컨트롤 플레인 노드에는 그런 파일이 없고, 만들어 주려면 이 설치본이 노드의
`advertiseAddress` 를 다시 조립해야 합니다. 틀리게 조립하면 apiserver 매니페스트가 틀리게
쓰입니다.

`kubeadm upgrade node phase control-plane` 은 클러스터가 들고 있는 설정을 읽습니다. 노드에
아무것도 요구하지 않고, 이미 `update-k8s-node-kubelet.sh` 가 버전이 움직이지 않는 클러스터에서
`upgrade node phase kubelet-config` 를 같은 방식으로 쓰고 있습니다. 인증서 갱신은 꺼서 넘깁니다 —
업그레이드에서는 기본이 켜짐이고, 인자 하나 바꿀 때마다 인증서가 같이 갱신되면 한 단어 아래
두 가지 일이 일어납니다.

=== 한 대씩, 로드밸런서에서 빼고

매니페스트가 다시 쓰이면 kubelet 이 apiserver 컨테이너를 갈아끼웁니다. 인증서 갱신과 같은
상황이라 절차도 같습니다 — 모든 ki cp 노드의 로드밸런서에서 빼고, 다시 쓰고, 그 노드의
apiserver 가 다시 답할 때까지 기다린 뒤 넣고, 그러고 나서 다음 노드입니다.

이 phase 는 apiserver 만 쓰지 않습니다. 컨트롤 플레인 정적 파드를 전부 — etcd 를 포함해 —
다시 쓰고, 내용이 같은 것은 kubelet 이 컨테이너를 건드리지 않아 그대로 지나갑니다. 그래서
apiserver 인자만 바뀌면 etcd 는 재시작되지 않지만, 재시작될 수 있는 자리라는 것은 알고
있어야 합니다. 같은 이유로 바뀐 것이 없으면 세 노드를 도는 데 2분 20초가 들고 apiserver 는
한 번도 재시작되지 않습니다.

가장 있을 법한 실패는 없는 파일을 가리키는 인자 때문에 apiserver 가 뜨지 않는 것입니다.
**그때 kubeadm 은 매니페스트를 되돌립니다.** 새 매니페스트를 넣고 파드가 뜨기를 5분 기다린 뒤,
안 뜨면 백업해 둔 예전 것을 제자리에 놓습니다. 그래서 노드는 실패한 매니페스트를 든 채 남지
않고 예전 설정으로 스스로 돌아옵니다 — 값을 고치는 것은 노드를 살리기 위해서가 아니라 변경을
반영하기 위해서입니다. 그 5분을 세는 것도 `wait-k8s-apiserver.sh` 가 아니라 kubeadm 자신이라
`APISERVER_READY_TIMEOUT` 은 이 경로에 닿지 않습니다. 기다리는 동안 그 노드는 자기 apiserver 가
없어서 `NotReady` 로 보이는데, kubelet 이 VIP 가 아니라 자기 노드의 apiserver 를 보기
때문입니다. 클러스터 자체는 남은 노드로 계속 답합니다. 그 노드는 로드밸런서에 되돌려 놓고
멈추므로 뒤 노드는 손대지 않습니다.

== 노드를 비우는 방법이 두 가지인 이유

`kubectl drain` 은 두 곳에서 부릅니다. 하나는 노드를 뺄 때, 다른 하나는 클러스터를 통째로
없앨 때이고, 옵션이 정반대입니다. 같아 보여서 한쪽으로 통일하기 쉬운 자리입니다.

=== 노드를 뺄 때는 eviction api 를 씁니다

`remove-node` 의 drain 은 `--disable-eviction` 이었습니다. 이것은 eviction api 를 건너뛰고
파드를 곧바로 지우며, PodDisruptionBudget 은 eviction api 를 통해서만 강제되므로 예산을 전혀
지키지 않습니다. 레플리카 셋 중 둘은 떠 있어야 한다고 선언해 두어도 한 노드의 것이 통째로
사라졌고, 그 서비스는 대체 파드가 뜰 때까지 내려갔습니다. 노드를 비우는 이유와 정반대입니다.

`--grace-period 10` 도 빠졌습니다. 파드가 선언한 종료 유예를 10초로 덮어썼기 때문에, 마무리에
그보다 오래 걸린다고 말해 둔 파드는 그 시간을 받지 못했습니다.

`--force` 도 넘기지 않습니다. 이 옵션이 덮는 것은 컨트롤러가 없는 파드, 즉 다른 곳에서 다시
뜨지 않을 파드입니다. 거부하는 쪽이 정직합니다. 이 노드에 옮길 수 없는 것이 있으니 사람이
정하라는 뜻입니다.

실측: `minAvailable: 3` 이라 허용 중단이 0인 상태에서 drain 은 5분 동안 거부당하고 실패했고
파드는 셋 다 그대로였습니다. `minAvailable: 1` 로 완화하자 2초 만에 끝났습니다.

=== 클러스터를 없앨 때는 쓰지 않습니다

`reset-cluster` 의 `delete-all-nodes.sh` 는 `--disable-eviction` 을 그대로 둡니다. 파드가 옮겨
갈 곳이 없고 지켜 줄 가용성도 없습니다. eviction 을 거치면 다시는 충족될 수 없는 예산을
기다리게 되고, 예산이 막을 수 있는 reset 은 클러스터를 반쯤 지운 채 멈추는 reset 입니다.

=== drain 이 실패해도 노드는 cordon 된 채 남습니다

`kubectl drain` 은 파드를 옮기기 전에 먼저 cordon 합니다. 그래서 타임아웃으로 실패한 뒤에도
노드는 새 워크로드를 받지 않는 상태로 남고, `uncordon-node.sh` 를 돌려야 돌아옵니다.
drain-node.sh 의 실패 메시지가 그것을 말해 줍니다.

== 변수를 바꾸면 무엇이 필요한가

`vars.yml` 을 고쳐도 이미 서 있는 클러스터에 반영할 길이 없었습니다. 값마다 필요한 조치가
전혀 다른데 (서비스 하나만 다시 렌더하면 되는 것부터 노드를 다시 만들어야 하는 것까지)
그것이 어디에도 적혀 있지 않았습니다. `constant-vars.yml` 의 `ki_var_classes` 가 그 표입니다.

[cols="1,3"]
|===
|클래스 |뜻

|`service`
|ki cp 서비스에 렌더되는 값. 해당 서비스만 다시 렌더하면 끝나고 노드와 클러스터는 그대로입니다

|`kubelet`
|kubelet 설정으로 가는 값. 다시 쓰고 kubelet 을 재시작하면 반영됩니다

|`cluster_config`
|kubeadm 설정에 들어가고 다음에 kubeadm 이 무언가를 발급할 때 읽힙니다. 이미 발급된 것은 바뀌지 않습니다

|`control_plane`
|같은 kubeadm 설정에 들어가되 컨트롤 플레인 정적 파드에까지 닿아야 하는 값. 설정을 올린 뒤
노드를 한 대씩 로드밸런서에서 빼고 매니페스트를 다시 씁니다

|`node_metadata`
|노드가 아니라 클러스터의 노드 오브젝트에 쓰이는 값. 컨트롤 플레인 노드에서 apiserver 에 말을
걸어 적용하므로 노드에서는 아무것도 재시작하지 않습니다

|`node_rebuild`
|노드를 만들 때 정해지고 그 뒤로는 손댈 수 없는 값. 어느 노드인지 알리고 멈춥니다

|`immutable`
|서 있는 클러스터에서는 바꿀 수 없는 값. 절반만 적용하느니 거부합니다
|===

=== VIP 주소가 바꿀 수 있는 값인 이유

`controlPlaneEndpoint` 는 IP 가 아니라 `ki-cp.<zone>:<port>` 라는 이름입니다. 그래서 VIP 주소를
바꾸는 데 필요한 것은 dns 서버와 keepalived 를 다시 렌더하는 것뿐이고, 클러스터는 자기가 어디에
붙는지 다시 배울 필요가 없습니다. 반면 `ki_cp_ha_mode` 자체를 켜고 끄는 것은 어떤 서비스가
도는지가 달라지는 일이라 `immutable` 입니다.

=== 파드와 서비스 서브넷이 값이면서 immutable 인 이유

두 서브넷은 `constant-vars.yml` 에 박혀 있었습니다. 설치본이 고를 수 있는 값이 아니어서가
아니라 고를 일이 없어 보여서였는데, 먼저 있던 망과 부딪히면 그때는 고를 수 있어야 합니다.
`10.244` 나 `10.96` 을 이미 다른 데 쓰고 있는 사이트에서는 클러스터가 서고 나서 그 대역의
무언가에 닿지 못하는 것으로 드러나고, 증상은 서브넷을 가리키지 않습니다.

그래서 `vars.yml` 로 올렸고 `immutable` 입니다. 서비스 서브넷은 모든 서비스의 주소를 정하고
그중 하나가 kubelet 이 클러스터 dns 로 아는 주소이며, 파드 서브넷은 CNI 가 그것을 전제로
설치됩니다. 서 있는 클러스터에서 바꾸는 것은 값을 고치는 일이 아니라 클러스터를 다시 세우는
일이라 절반만 적용하느니 거부합니다.

`constant-vars.yml` 에 폴백은 두지 않았습니다. 사는 곳이 한 군데여야 `vars.yml` 에서 줄을
지운 것이 조용히 기본값으로 떨어지지 않고 `Field required` 로 걸립니다. 폴백을 두면 그
검사가 닿을 수 있는 경로가 사라집니다.

겹침은 `validate-hostvars.py` 가 봅니다. 파드와 서비스끼리, 그리고 각각과
`internal_network_subnets` 입니다. 마지막 것이 실제로 아픈 자리인데, 내부망에는 apiserver 와
etcd peer 와 dns 서버와 레지스트리 둘이 있어서 겹치면 클러스터는 서고 이미지는 못 당기며
에러는 레지스트리 이름을 말합니다. kubeadm 은 겹침을 그대로 받고 아무 말도 하지 않습니다.
클러스터 밖에서 워크로드가 닿아야 하는 주소는 사이트가 아는 것이라 여기서 보지 않습니다.

=== kubelet 재시작에 drain 이 필요 없는 이유

kubelet 을 재시작해도 돌고 있던 컨테이너는 죽지 않습니다. containerd 가 계속 들고 있고
kubelet 이 돌아와서 다시 인식합니다. `systemReserved` 와 `kubeReserved` 는 스케줄러 회계에만
쓰이고, `evictionHard` 를 조이면 파드가 쫓겨날 수 있지만 그것이 조이는 목적입니다.

=== 분류를 빠뜨리면 플레이북이 거부합니다

`vars.yml` 에 있거나 `inventory.yml` 에서 노드에 준 값인데 어느 클래스에도 없는 변수가 있으면
`validate-hostvars.py` 가 멈춥니다. 이 검사가 없으면, 변수를 추가하면서 분류를 깜빡한 사람은
아무 경고도 받지 않고, 그 변수는 기존 클러스터에 조용히 적용되지 않는 값이 됩니다. 그런 것은
한참 뒤에 어렵게 발견됩니다.

두 파일을 파일째로 읽습니다. hostvars 에는 ansible 이 스스로 정의하는 이름이 수백 개 섞여
있어서, 사용자가 노드에 실제로 무엇을 주었는지는 준 파일에서만 보입니다. `ansible_` 로
시작하는 것은 접속 설정이라 제외합니다.

=== inventory.yml 에서 바꾸는 값도 같은 표를 씁니다

`k8s_cp` 를 바꾸는 것은 그 노드가 etcd 멤버를 지니는지를 바꾸는 일입니다. 돌고 있는 노드 밑에서
붙이거나 뗄 것이 아니라서 `node_rebuild` 이고, `remove-node` 와 `add-node` 가 그 경로입니다.
`internal_network_ip` 도 노드를 만들 때 정해지는 값이라 같습니다.

`control_node_ih` 만 `no_action` 입니다. `sync-ansible.yml` 이 모든 ki cp 노드의 ansible
디렉토리를 이미 맞춰 두므로, 제어 노드를 옮기는 데 필요한 것은 그 선언 한 줄뿐입니다.

이 변수는 `inventory.yml` 의 localhost 항목에만 있고 노드는 갖지 않으므로 노드의
`applied-vars.yml` 에도 들어가지 않습니다. 빠진 것이 아니라 앞뒤가 맞는 것입니다. 기록하지
않으면 비교도 하지 않으니 바뀌었다고 보고될 일이 없고, 보고된들 할 일이 없습니다.

=== applied-vars.yml 은 플레이북의 마지막에 씁니다

노드마다 하나씩 두고, 그 노드가 실제로 들고 있는 값을 적습니다. `inventory.yml` 에서 한 노드에만
다르게 준 값이 그 노드의 파일에 그 값으로 들어가야 하기 때문에, `vars.yml` 이 아니라 각 노드의
hostvars 에서 읽습니다.

쓰는 시점이 마지막인 것도 의도입니다. 중간에 실패한 실행은 노드가 실제로 남은 상태를 적어야
다음 update 가 아직 적용되지 않은 변경으로 보고 다시 시도합니다. 먼저 썼다면 적용되지 않은
값을 적용된 것으로 기록하게 됩니다.

=== 기록은 클래스를 가리지 않습니다

적용할 것이 없다는 것과 기록할 것이 없다는 것은 다릅니다. 노드가 들고 있는 변수라면
`no_action` 이어도 새 값이 `applied-vars.yml` 에 들어갑니다. 넣지 않으면 그 뒤의 모든 실행이 같은 변경을 계속 바뀐 것으로
보고하고, 파일은 영영 따라잡지 못합니다.

반대로 적용하지 못한 것은 기록하지 않습니다. `immutable` 로 거부했거나 `node_rebuild` 로 멈춘
실행은 아무것도 적용하지 않았으므로 파일도 그대로 두어야, 다음 실행이 그 변경을 여전히 해야 할
일로 봅니다. 그래서 update-cluster 는 먼저 전부 분류해서 거부할 것이 있으면 아무것도 적용하지
않고 멈추고, 끝까지 간 경우에만 기록합니다.

== 노드 라벨과 테인트

노드를 배치에 쓰려면 라벨이 필요하고, 비워 두려면 테인트가 필요합니다. 둘 다 설치본 밖에서
붙이면 노드를 다시 만들 때 사라지고, 어느 노드에 무엇이 붙어 있는지가 인벤토리에 없습니다.

=== kubelet 인자가 아니라 클러스터 측에서 붙입니다

kubeadm 은 `nodeRegistration.kubeletExtraArgs` 의 `node-labels` 로 라벨을 받습니다. 그 길을
쓰지 않은 이유는 NodeRestriction 입니다 — kubelet 이 스스로 붙일 수 있는 라벨은 제한되어 있고,
`node-role.kubernetes.io/*` 처럼 흔히 붙이고 싶은 것이 거기 걸립니다. 걸리면 라벨이 안 붙는
정도가 아니라 **노드 등록 자체가 거부**됩니다.

컨트롤 플레인 노드에서 `kubectl` 로 붙이면 그 제한이 없고, 값이 바뀌었을 때 다시 붙일 수도
있습니다. 그래서 라벨은 클러스터 측 한 길입니다.

=== 테인트만 등록 시점에도 붙입니다

테인트의 목적은 "아직 이 노드에 아무것도 들어오지 마라" 입니다. 조인이 끝난 뒤에 붙이면 그
사이의 몇 초 동안 스케줄러가 파드를 올릴 수 있고, `add-node` 는 살아 있는 클러스터에서 도는
일이라 그 창이 실재합니다. 그래서 테인트는 kubeadm 설정에도 들어가고, 값이 바뀌면 클러스터
측에서 다시 맞춥니다. 두 길이 같은 값을 쓰므로 나중 것은 대개 할 일이 없습니다.

=== kubeadm 의 taints 는 비어 있을 때만 기본값을 줍니다

`nodeRegistration.taints` 가 nil 이면 kubeadm 이 컨트롤 플레인 노드에
`node-role.kubernetes.io/control-plane:NoSchedule` 을 붙입니다. **비어 있지 않은 목록을 주면 그
기본값은 사라집니다.** 즉 컨트롤 플레인 노드에 테인트를 하나라도 주는 순간, 그 노드를
스케줄 가능하게 만들지 않으려면 컨트롤 플레인 테인트를 같이 적어야 합니다.

템플릿이 그것을 넣습니다. 사용자가 적는 것이 아니라 — `validate-hostvars.py` 가 그 키를
거부하므로 주인이 하나입니다.

=== 지우는 것은 우리가 붙인 것만입니다

인벤토리에서 키가 사라진 것과 그 키가 원래 없던 것은 인벤토리만 봐서는 구분되지 않습니다.
그래서 근거를 각 노드가 마지막 실행에서 기록한 `applied-vars.yml` 에서 가져옵니다. 지우는
대상은 **거기 있고 지금은 없는 키**뿐이고, 사람이 손으로 붙인 라벨이나 kubelet 이 붙인 라벨,
kubeadm 의 컨트롤 플레인 테인트는 후보에 들어가지 않습니다.

기록이 없는 클러스터(이 릴리스 이전)는 지울 것이 없는 것으로 읽힙니다. 다른 클래스와 같은
규칙이고, 안전한 쪽입니다.

=== 바뀐 노드만 고르지 않습니다

`apply-node-metadata.yml` 은 변경 여부를 묻지 않고 모든 노드에 대해 돕니다. 스크립트가 노드를
한 번 읽고 **다른 것만** 쓰기 때문에, 이미 맞는 노드는 `kubectl get` 한 번으로 끝납니다.
조건을 다는 것은 일을 줄이지 못하고, 대신 손으로 지워진 라벨이 다음 실행에 돌아오는 성질을
잃습니다.

=== 소유자가 둘인 키를 거부합니다

`kubernetes.io/hostname` 처럼 kubelet 이 스스로 붙이는 라벨은 붙여도 다음 등록에서
덮어써집니다 — 안 붙는 것이 아니라 **붙었다가 사라지는** 것이라 원인을 찾기 어렵습니다.
`node-role.kubernetes.io/control-plane` 은 `check-node-state.sh` 가 컨트롤 플레인 노드를 세는
데 쓰고, `node.kubernetes.io/*` 테인트는 쿠버네티스가 노드 상태를 말하는 수단입니다. 전부
시작 전에 거부합니다.

=== ki cp 라벨은 설치본이 아는 사실입니다

어느 노드가 dns·레지스트리·로드밸런서를 돌리는지는 인벤토리만 압니다. 클러스터 안에서는 그것을
물을 방법이 없어서, 그 노드들을 가리켜야 하는 쪽(모니터링, 레지스트리 옆에 붙어야 하는
워크로드)이 주소를 손으로 들고 다녀야 했습니다. 그래서 설치본이 자기가 아는 것을 라벨로 남깁니다.

사용자 라벨과 키 네임스페이스를 나눠 둔 것은 지울 때를 위해서입니다. 사용자 라벨은 기록과
비교해서 지우고, 이 라벨은 그룹 소속으로 결정되므로 기록이 필요 없습니다.

== update-cluster 가 하는 일

`vars.yml` 이나 `inventory.yml` 을 고친 뒤 이것을 돌리면, 각 노드의 `applied-vars.yml` 과
현재 값을 견주어 무엇이 달라졌는지 알아내고 클래스표가 시키는 대로 적용합니다.

=== 거부는 적용보다 먼저 판정합니다

`immutable` 이나 `node_rebuild` 에 걸리는 변경이 하나라도 있으면 아무것도 적용하지 않고 멈춥니다.
클래스 판정을 전부 끝낸 다음에 적용을 시작하기 때문에, 거부할 실행은 절반이 적용된 상태를 남기지
않습니다. 무엇이 어느 노드에서 어떤 값으로 바뀌려 했는지도 같이 알려 줍니다.

=== service 변경은 서비스를 가리지 않고 전부 다시 씁니다

어떤 변수가 어느 서비스로 가는지 표로 들고 있지 않습니다. 각 setup 스크립트가 이미 자기가 렌더한
것이 달라졌는지 스스로 판단하므로, 매핑을 따로 두면 같은 답이 사는 곳이 둘이 되고 언젠가 둘이
어긋납니다.

=== kubelet 은 클러스터 기준선 먼저, 그 다음 노드별로 한 대씩

기준선을 담은 ConfigMap 을 컨트롤 플레인 한 대에서 올리고, 그 다음 각 노드가 자기 용량으로 계산된
패치를 적용해 `/var/lib/kubelet/config.yaml` 을 다시 쓰고 kubelet 을 재시작합니다. 노드가 기준선을
그 ConfigMap 에서 읽어 오므로 순서가 뒤바뀌면 안 됩니다.

한 대씩 도는 것은 재시작이 위험해서가 아닙니다. 실측으로 파드 수는 15 에서 15 그대로였습니다.
다만 클러스터의 모든 kubelet 을 같은 순간에 내리면 그것들이 다 돌아올 때까지 아무도 파드를 보지
않는 구간이 생깁니다.

`allocatable` 까지 실제로 따라옵니다. `systemReserved.cpu` 를 625m 에서 1500m 으로 올리자 노드의
`allocatable.cpu` 가 71250m 에서 70375m 으로 줄었습니다. 설정 파일만 바뀐 것이 아니라 스케줄러가
보는 값이 바뀌었다는 뜻입니다.

=== upload-config kubelet 은 ClusterConfiguration 을 같이 요구합니다

`kubeadm init phase upload-config kubelet` 에 KubeletConfiguration 만 든 파일을 주면
`no InitConfiguration or ClusterConfiguration kind was found` 로 거부합니다. `kubeadm init` 에
넘겼던 파일과 같은 모양이어야 합니다. 둘은 서로 다른 템플릿이 렌더하고 서로 다른 변수가 바꾸므로
디스크에서는 따로 두고, 올릴 때만 임시 파일에 합칩니다.

=== 기록은 그 실행이 적용한 것만 적습니다

`applied-vars.yml` 은 "이 노드가 무엇으로 서 있는가" 를 적는 파일입니다. 그런데 오랫동안
`vars.yml` 이 무엇이라 말하는지를 적었습니다. `update-cluster.yml` 에서는 둘이 같지만 다른
플레이북에서는 다릅니다.

`upgrade-cluster.yml` 이 그 자리입니다. `kubeadm upgrade` 는 설정을 클러스터에서 읽지
`vars.yml` 에서 읽지 않으므로, 그 설정으로 가는 `kubelet`·`cluster_config`·`control_plane` 은
업그레이드가 적용하지 않습니다. `node_rebuild` 와 `immutable` 은 아예 아무도 적용하지 않습니다.
그런데도 전부 기록하면 두 가지가 벌어집니다.

첫째, 값이 조용히 사라집니다. 감사 정책을 적고 업그레이드를 돌리면 클러스터에는 들어가지 않은 채
기록에만 박히고, 다음 `update-cluster.yml` 은 "바뀐 것 없음" 이라 답합니다. 값을 다시 고쳐도
소용없습니다 — 기록과 이미 같으니까요. 반영되지 않았다는 사실을 말해 주는 것이 아무것도 없습니다.

둘째, 이쪽이 더 나쁜데, 막는 클래스의 가드가 꺼집니다. `immutable` 과 `node_rebuild` 가 존재하는
이유는 오직 거부하기 위해서인데, 새 값이 기록되면 거부할 근거가 사라집니다. 노드를 다시 만들어야
한다고 말해 줄 유일한 기계가 조용해지고, 기록 파일은 그 노드가 없는 값으로 지어졌다고 말합니다.
그 파일은 사이트 값을 잃었을 때의 복구원이기도 해서 복구원까지 오염됩니다.

그래서 `record-applied-state.yml` 은 `ki_recorded_classes` 를 받습니다. 기록하지 않는 클래스는
파일에 있던 값을 그대로 두므로, 반영되지 않은 변경은 기록에 남지 않고 다음 `update-cluster.yml`
이 그것을 봅니다. 기본값을 두지 않은 것은 의도입니다 — 기본이 "전부" 면 나중에 추가된 클래스가
적용되지 않은 채 기록되고, 기본이 "전부 빼고 몇 개" 여도 마찬가지입니다. 이름을 빠뜨리면 기록되지
않는 쪽으로 틀리고, 기록이 없는 변수는 `diff-applied-vars.py` 가 기준점으로 받습니다.

== 인증서를 무중단으로 갱신하는 법

`renew-certs.yml` 은 컨트롤 플레인 노드를 한 대씩 돌면서, 그 노드를 **모든** ki cp 노드의
로드밸런서에서 뺀 뒤 인증서를 갱신하고 static pod 를 재시작하고, 다시 넣고 트래픽을 받는 것까지
확인한 다음 다음 노드로 갑니다. 한 대씩인 이유는 그 사이 컨트롤 플레인을 지탱하는 것이 작업하지
않는 나머지 노드들이기 때문입니다.

실측: 세 노드를 도는 150초 동안 VIP 로 1초마다 던진 요청 150건이 전부 200 이었습니다.

=== 갱신했다고 끝이 아닙니다

apiserver, controller-manager, scheduler, etcd 는 인증서를 시작할 때 한 번 읽습니다. 파일만
갱신하고 재시작하지 않으면 디스크에는 새 인증서가 있고 프로세스는 옛 것을 계속 씁니다. 그 상태는
만료되는 날까지 아무 증상이 없습니다.

그래서 재시작할 컨테이너를 찾지 못하면 조용히 넘어가지 않고 실패합니다. 갱신을 보고하면서 아무도
그 인증서를 쓰지 않는 상태로 두는 것이 갱신 실패보다 나쁩니다.

=== rm -f 가 아니라 stop 입니다

`crictl rm -f` 는 SIGKILL 이라 진행 중이던 요청이 잘립니다. `crictl stop` 은 SIGTERM 을 보내고
기다리므로 apiserver 가 자기 `/readyz` 를 먼저 내리고 들고 있던 것을 마칠 수 있습니다. kubeadm 이
이 static pod 들에 `terminationGracePeriodSeconds` 를 걸지 않아 다른 상한이 없고, crictl 의 기본
10초는 요청을 마무리하기에 짧아서 45초를 줍니다.

=== 재시작 여부는 RESTARTS 로 볼 수 없습니다

`crictl` 로 컨테이너를 밖에서 교체하면 kubelet 이 restartCount 를 새로 세기 시작하고, 파드의
AGE 는 mirror pod 객체의 것이라 컨테이너와 무관합니다. 둘 다 0 과 옛 값 그대로여서 재시작이 안 된
것처럼 보입니다.

실제로 보아야 할 것은 **apiserver 가 핸드셰이크에서 제시하는 인증서**입니다. 거기에 새 만료일이
나오면 그 프로세스가 새 인증서로 서 있는 것이고, 그것 말고는 확인할 방법이 없습니다.

=== 기다리는 대상은 VIP 가 아니라 그 노드입니다

갱신한 노드를 다시 넣어도 되는지 판단하려면 그 노드의 apiserver 가 답하는지를 보아야 합니다.
VIP 는 아무 노드나 답할 수 있어서, 작업 중인 노드가 죽어 있어도 200 이 돌아옵니다.

== 인증서 만료를 파일로 내보내는 법

`check-cert-expiry.sh` 의 답은 플레이북을 돌린 사람의 화면에만 있었습니다. 3년짜리 kubeadm
인증서와 10년짜리 ki pki 에 대해 "사람이 물어봐야 알 수 있는 만료" 는 아무도 묻지 않는
만료이고, 지나간 실행의 출력은 아무도 보관하지 않습니다. 같은 측정을 파일로도 남겨서,
모니터링이 읽어 가게 합니다.

=== 수집기는 설치하지 않습니다

내보내는 형식은 node exporter 의 textfile collector 가 읽는 것입니다. 그러면 설치본은 파일을
쓰는 것까지만 하고, 그것을 긁어 가는 것은 사이트가 이미 돌리고 있는 무엇이든 됩니다. 수집기를
같이 깔면 그 수집기의 버전과 설정과 포트가 전부 이 저장소의 것이 되고, 이미 수집기가 있는
사이트에서는 두 벌이 됩니다.

디렉토리는 `{ki_var_root_path}/metrics` 입니다. etcd 스냅샷과 같은 이유로 설치본의 변수
데이터 아래에 두었고 — 노드에 쓰는 것은 한 루트 아래 — 이름은 읽는 쪽이 아니라 담는 것을
따릅니다. 수집기를 여기로 향하게 하는 것은 모니터링을 운영하는 쪽의 결정입니다.

=== 남은 일수가 아니라 만료 시각입니다

남은 일수는 쓰는 순간에만 맞습니다. 파일이 다시 쓰이지 않으면 그때 멈춘 숫자를 계속 답하고,
그것이 틀렸다는 것을 아무도 알 수 없습니다. 절대 시각은 놓여 있는 동안 계속 참이고, 얼마나
남았는지는 읽는 쪽이 어차피 하고 있는 뺄셈입니다.

이 선택이 타이머를 필요 없게 만듭니다. 값이 낡을 수 없으니 새로 고칠 일도 없고, 값이 바뀌는
유일한 순간은 플레이북이 인증서를 움직일 때라 그 자리에서 다시 쓰면 충분합니다.

=== .tmp 에 쓰고 옮깁니다

textfile collector 는 긁히는 순간에 있는 것을 그대로 읽습니다. 제자리에서 append 하면
반쯤 쓰인 파일이 읽히고, 그 노드의 메트릭이 인증서와 아무 상관 없는 이유로 사라졌다
나타납니다. `.tmp` 에 다 쓰고 `mv` 로 갈아끼우면 읽는 쪽에는 항상 온전한 파일만 보입니다.

=== 주기적으로 쓰지 않습니다

타이머가 없습니다. 값이 절대 시각이라 놓여 있는 동안 계속 참이고, 그 값이 바뀌는 때는 인증서가
발급되거나 갱신될 때뿐인데 그 둘은 전부 플레이북이 하는 일이기 때문입니다. 하루에 한 번 다시
쓴다면 어제와 같은 숫자를 다시 쓰는 것입니다.

그래서 파일을 쓰는 것은 `check-cert-expiry.yml` 이 맡습니다. 인증서를 움직이는 플레이북은
전부 이것을 마지막에 부르고 있었으므로 — `add-node`, `remove-node`, `renew-certs`,
`upgrade-cluster` — 배선을 따로 놓을 자리가 없습니다. `setup-cluster` 만 부르지 않고 있어서
거기에 추가했습니다.

`ki_certificate_metrics_written_seconds` 도 없습니다. 파일이 쓰인 시각은 갱신이 멈춘 것을
알리려고 있는 값인데, 애초에 주기적 갱신이 없으면 "오래됨" 이 정상이라 아무것도 알리지
못합니다. 읽는 쪽이 node exporter 라면 textfile collector 가 `node_textfile_mtime_seconds` 로
같은 것을 이미 내보냅니다.

=== reset 은 클러스터를 지울 때만 필요합니다

`reset-cluster` 는 `check-cert-expiry.yml` 을 부르지 않으므로, 두지 않으면 지워진 클러스터의
인증서를 계속 답하는 파일이 남습니다. 그래서 거기서만 디렉토리를 지웁니다.

`remove-node` 에는 없습니다. 노드를 빼는 길에 `kubeadm reset` 이 그 노드의 pki 를 비우고
`reset-pki` 가 ki pki 를 가져가므로, 마지막에 도는 `check-cert-expiry.yml` 이 샘플 없는 파일을
씁니다. 인증서가 없는 노드에 대해 그것이 맞는 답입니다.

== 업그레이드는 쿠버네티스만이 아닙니다

`upgrade-k8s-installer.yml` 은 `/opt/k8s-installer` 의 `bundle` 과 `scripts` 를 새 릴리스로
바꿉니다. 거기서 끝입니다. 노드의 containerd 와 kubelet 은 옛 버전 그대로이고,
`bundle/bin/helm` 은 새것인데 `/usr/local/bin/helm` 은 옛것인 상태가 됩니다. 그 간극을 메우는
것이 `upgrade-cluster.yml` 입니다.

[cols="1,2"]
|===
|영역 |방법

|레지스트리 이미지
|`setup-k8s-registry.sh --update`. **가장 먼저** 합니다

|ki cp 서비스
|`setup-*.sh --update`

|리눅스 패키지
|`install-packages.sh --update`

|유저 바이너리
|`install-programs.sh` 재실행

|쿠버네티스
|첫 cp 노드 `kubeadm upgrade apply`, 나머지 `kubeadm upgrade node`
|===

=== 레지스트리가 먼저인 이유

kubeadm 은 업그레이드하면서 새 버전의 이미지를 당깁니다. 에어갭 클러스터에서 그것을 줄 수 있는
곳은 이 레지스트리뿐이라, 노드를 먼저 손대면 받을 데가 없습니다.

=== 설치와 업그레이드가 유닛을 반대로 다룹니다

최초 설치는 패키지를 깔고 모든 유닛을 **disable** 합니다. 켜는 것은 그 뒤에 각 서비스를 세우는
플레이북의 몫이기 때문입니다. 업그레이드 때 그대로 하면 돌고 있던 서비스가 꺼집니다. 반대로
업그레이드에는 방금 교체된 바이너리 위로 **restart** 가 필요합니다. `--update` 가 그 차이이고,
재시작 대상은 그 노드에서 실제로 enable 된 유닛뿐입니다. docker 는 ki cp 노드에만 켜져 있습니다.

`require_not_installed` 가드도 `--update` 에서는 건너뜁니다. 최초 설치가 이미 깔린 패키지 위에서
멈추는 것은 그것이 요청받지 않은 업그레이드이기 때문이고, 업그레이드는 바로 그 일을 하러 온
것입니다.

=== 번들이 무엇을 들고 있는지는 아무도 말하지 않았습니다

`install-packages.sh` 는 디렉토리를 통째로 dpkg 와 rpm 에 넘깁니다. 그래서 노드가 받는 containerd
와 docker 의 버전은 그 디렉토리를 채울 때 거기 있던 것이고, 어느 파일에도 선언되어 있지 않았습니다.
릴리스가 "같은 릴리스를 보고하는 두 노드는 같은 것을 들고 있다" 를 내세우는데 그 부분만 아무도
확인하지 않았던 셈입니다.

실제로 어긋나 있었습니다. `1.36.0-SNAPSHOT` 번들을 세 OS 에서 읽어 본 결과입니다.

[cols="2,1,1,1"]
|===
|패키지 |ubuntu22.04 |ubuntu24.04 |rhel8

|containerd.io |1.7.29 |1.7.29 |*1.7.28*
|docker-ce |28.5.2 |28.5.2 |*28.5.1*
|docker-ce-rootless-extras |28.5.2 |*29.3.0* |*28.5.1*
|docker-buildx-plugin |0.29.1 |*0.31.1* |0.29.1
|docker-compose-plugin |2.40.3 |*5.1.0* |2.40.3
|===

`docker-ce` 는 28.5.2 인데 그 옆의 플러그인만 최신을 당겨 온 모양입니다. 결과는 테스트 클러스터에
그대로 남아 있었습니다 — ki cp 노드 두 대가 같은 릴리스를 보고하면서 하나는 compose v5.1.0, 다른
하나는 v2.40.3 으로 ki cp 서비스를 돌리고 있었습니다.

그래서 `release.yml` 의 `packages` 와 `binaries` 가 이것들을 버전으로 적고, 설치 스크립트가
아무것도 깔기 전에 번들과 대조합니다. 대조 대상은 **배포판 밖에서 온 것들뿐**입니다. 그것들은
만든 곳의 저장소에서 오기 때문에 이름 하나와 업스트림 버전 하나가 세 OS 를 다 덮지만, 나머지는
OS 저장소가 준 그대로라 이름도 버전도 OS 마다 다르고 아무도 고른 적이 없습니다.

바이너리는 실행해서 묻습니다. 패키지 파일과 달리 `bundle/bin/helm` 은 이름만으로는 어느 helm 인지
알 수 없고, 그것이 번들이 다른 것을 조용히 들고 있을 수 있는 이유이기도 합니다. 세 OS 와
`rpm`/`dpkg-deb` 양쪽에서 대조에 드는 시간은 0.2초에서 0.9초입니다.

=== containerd 2 로 올라가면 설정 스키마가 바뀝니다

2026-09-22 에 번들을 최신으로 맞추면서 containerd 가 1.7.29 에서 2.3.5 로 올라갔습니다. 고른
것이 아니라 묶여 있었습니다 — `docker-ce` 29.8.1 이 `containerd.io (>= 2.1.5)` 를 요구합니다.
containerd 1.x 와 갈 수 있는 마지막 도커는 29.5.3 (`>= 1.7.27`) 이므로, 도커만 최신으로 올리는
길은 없습니다.

설정 스키마가 따라 바뀌는데, **버전은 3 이 아니라 4 입니다.** 짐작하지 말고 containerd 에게
물어보는 편이 빠르고 정확합니다.

----
containerd --config <옛 config.toml> config migrate
----

[cols="1,1"]
|===
|`version = 2` |`version = 4`

|`plugins."io.containerd.grpc.v1.cri"`
|`io.containerd.cri.v1.runtime` 과 `io.containerd.cri.v1.images` 둘로 갈라집니다

|`sandbox_image = "..."`
|`[plugins."io.containerd.cri.v1.images".pinned_images]` 의 `sandbox`

|`sandbox_mode`
|`sandboxer`
|===

`imports` 는 그대로 동작합니다. `config migrate` 의 출력에 그것이 없는 이유는 마이그레이션이
드롭인을 이미 합쳐서 내놓기 때문이지 v4 가 받지 않아서가 아닙니다. 새 템플릿으로 `config dump`
를 떠서 드롭인의 `default_runtime_name = "nvidia"` 가 반영되는 것을 확인했습니다.

`config migrate` 는 기본값까지 전부 펼친 설정을 내놓습니다. 이 저장소의 템플릿은 기본값과
다른 것만 담으므로, 옮길 때 통째로 붙여넣지 말고 우리가 실제로 정하는 값이 어느 키로 갔는지만
보면 됩니다.

=== docker 29 가 nftables 를 요구합니다

`docker-ce` 29.8.1 의 의존성에 `nftables` 가 새로 들어왔습니다 (rpm 쪽은 `nftables` 와
`(iptables-nft or iptables)` 둘 다). RHEL 8.10 최소 설치에는 nftables 가 없으므로 에어갭
노드에서는 그대로 설치가 막힙니다. 그래서 번들에 `nftables` 디렉토리를 만들고 docker 바로
앞에서 깔도록 했습니다. ubuntu 쪽은 `libnftables1` 까지 같이 들고 갑니다.

`uninstall-packages.sh` 는 이것을 지우지 않습니다. iptables 나 socat 과 같은 부류입니다 —
배포판 유틸이라 설치기가 놓았다고 해서 거둘 것이 아닙니다.

=== rhel8 에서는 이미 깔린 rpm 을 다시 주지 않습니다

`containerd.io` 는 `containerd` 를 **Provides 하면서 동시에 Conflicts** 로 선언합니다. rpm 이
자기 충돌을 면제해 주는 것은 들어오는 패키지가 자신의 *다른* 버전을 대체할 때뿐이라, 이미 깔린
것과 같은 NEVRA 를 건네면 들어오는 쪽의 Conflicts 가 깔린 쪽의 Provides 와 맞아떨어져 트랜잭션
전체가 거부됩니다.

----
error: Failed dependencies:
        containerd conflicts with containerd.io-1.7.28-1.el8.x86_64
        containerd conflicts with (installed) containerd.io-1.7.28-1.el8.x86_64
----

containerd 를 그대로 둔 릴리스의 `--update` 는 전부 여기서 멈춥니다. 그 뒤의 패키지는 손대지
못한 채 노드가 반쯤 갱신된 상태로 남고, 패치 릴리스가 컴포넌트를 그대로 두는 일이 흔하므로 자주
만나게 됩니다.

그래서 `rhel8_install_rpms` 가 이미 그 버전으로 깔려 있는 rpm 을 목록에서 빼고 남은 것만 rpm 에
넘깁니다. 번들이 이미 넣어둔 것을 그대로 두는 것이 업그레이드가 요구하는 바이기도 하고, 덤으로
134개를 매번 다시 깔던 rhel8 의 `--update` 가 실제로 바뀐 것만 다룹니다. 실측으로 3분에서 9초가
되었습니다.

무버전 self-conflict 를 선언하는 것은 번들 안에서 `containerd.io` 하나뿐입니다
(`pkgconf-pkg-config` 도 `pkgconfig` 를 양쪽에 걸지만 `< 1:0.29.1-3` 제약이 있어 걸리지
않습니다). 그래도 그것은 지금 번들이 무엇을 담고 있는지에 대한 사실이지 rpm 에 대한 사실이
아니므로, 건너뛰기를 그 이름으로 쓰지 않았습니다. ubuntu 쪽 dpkg 는 같은 버전 재설치를 그냥
받아들이므로 이 문제가 없습니다.

=== 노드 안의 순서는 의존관계가 정합니다

drain 이 패키지보다 먼저입니다. 컨테이너 런타임을 갈아치우면 그 노드의 파드가 전부 재생성되기
때문입니다. 패키지가 kubeadm 보다 먼저인 것은 kubeadm 이 새 버전이어야 클러스터에 새 버전을
말할 수 있기 때문이고, kubelet 재시작이 kubeadm 뒤인 것은 kubeadm 이 그 사이 kubelet 의 설정을
다시 쓰기 때문입니다.

=== ki cp 서비스도 한 노드씩입니다

이 서비스들이 곧 VIP 가 가리키는 대상이고 keepalived 도 그중 하나입니다. 모든 ki cp 노드에서
동시에 바꾸면 VIP 를 든 노드가 하나도 없는 구간이 생깁니다. 실측으로 9초 동안 컨트롤 플레인이
닿지 않았습니다. 한 노드씩 하면 VIP 가 손대지 않는 노드로 옮겨 가고 `nopreempt` 가 그대로 두므로,
같은 측정에서 1초로 줄었습니다. 그 1초는 VIP 가 옮겨 가는 시간이라 VRRP 로는 더 줄이기 어렵습니다.

=== 실패해도 되돌리지 않습니다

kubeadm 은 클러스터가 기록한 버전을 올리고 그 아래 저장된 것을 옮깁니다. 그것을 되돌리는 쪽이
더 위험합니다. 대신 어느 노드까지 끝났고 클러스터가 두 버전으로 섞여 있다는 사실을 말하고 멈춥니다.
다시 실행하면 이미 새 버전인 노드는 건너뛰므로 멈춘 자리에서 이어집니다.

=== 이미지 목록은 그 릴리스의 kubeadm 에게 물어야 합니다

`kubeadm config images list --kubernetes-version <버전>` 의 답은 어느 kubeadm 으로 물었는지에
따라 달라집니다. 버전을 따라가는 것은 `kube-` 로 시작하는 넷뿐이고, coredns 와 pause 와 etcd 의
버전은 kubeadm 바이너리 안에 박혀 있습니다. 옛 kubeadm 은 자기가 아는 값으로 답하며 경고하지
않습니다.

[cols="1,2"]
|===
|물어본 kubeadm |`--kubernetes-version v1.36.0` 에 대한 답

|1.35
|coredns v1.13.1, pause 3.10.1, etcd 3.6.6-0

|1.36
|coredns v1.14.2, pause 3.10.2, etcd 3.6.8-0
|===

셋 다 다릅니다. 앞의 것으로 번들을 만들면 레지스트리에 새 kubeadm 이 찾을 이미지가 없고,
에어갭에서는 받아올 다른 곳이 없으므로 이미지를 당기는 preflight 에서 설치가 멈춥니다.
실제로 그렇게 한 번 멈춰 봤습니다. `linux-packages` 의 패키지에서 바이너리를 꺼내 실행하거나,
이미 그 버전인 노드에서 실행해야 합니다.

한 릴리스가 쿠버네티스 마이너를 여러 개 지원하므로 이 일은 마이너마다 반복됩니다.
`ki-cp-k8s-registry-images.yml` 은 마이너별 블록으로 되어 있고, 한 블록을 다른 블록에서 복사해
`kube-` 넷의 버전만 고치는 것이 정확히 위 표의 사고입니다. 블록마다 그 마이너의 kubeadm 에게
물어야 합니다.

=== 샌드박스 이미지는 kubelet 이 아니라 containerd 가 당깁니다

위 표의 pause 는 레지스트리에 넣는 것으로 끝나지 않습니다. 파드마다 쓰이는 샌드박스 이미지는
kubelet 이 알려주는 것이 아니라 containerd 가 자기 설정(`sandbox_image`)에 적힌 것을 직접
당깁니다. 그래서 kubeadm 이 요구하는 pause 와 containerd 에 적힌 pause 가 같아야 하고, 둘은
서로를 모릅니다.

pause 버전은 마이너를 따라 움직입니다 — 1.34 와 1.35 는 3.10.1, 1.36 은 3.10.2 입니다. 마이너를
고를 수 있게 되면서 `sandbox_image` 를 한 값으로 박아 둘 수 없게 되었습니다. 박아 두면 1.36 으로
새로 설치한 클러스터의 containerd 가 번들에 없는 `pause:3.10.1` 을 찾고, 에어갭에서는 받아올
곳이 없으므로 **파드가 하나도 뜨지 않습니다.** 노드는 Ready 인데 아무것도 스케줄되지 않는,
원인을 찾기 어려운 모양이 됩니다.

그래서 pause 는 `release.yml` 의 `k8s_versions` 안에 패치와 나란히 있습니다. 노드가 읽는 파일이
그것이기 때문입니다 — `ki-cp-k8s-registry-images.yml` 은 번들을 만들 때만 쓰이고 `/opt` 에
들어가지 않습니다. 두 곳에 적히는 값이 되었으므로 `build-bundle-images.sh` 가 빌드할 때 둘을
대조하고, 어긋나면 거부합니다. 레지스트리에 든 것과 노드가 찾는 것이 달라지는 사고는 빌드
시점에만 막을 수 있습니다.

=== kubelet 은 kubeadm 보다 먼저 재시작하면 안 됩니다

패키지를 교체한 자리에서 kubelet 을 바로 재시작했더니 업그레이드 전체가 실패했습니다.

kubeadm 은 kubelet 을 어떤 플래그로 띄울지 `/var/lib/kubelet/kubeadm-flags.env` 에 적어 둡니다.
릴리스가 플래그를 없애면 그 파일에는 새 바이너리가 모르는 이름이 남습니다. 1.35 가
`--pod-infra-container-image` 를 없앴고, 그 파일이 고쳐지기 전에 새 kubelet 을 올리자 자기 인자를
파싱하다 죽었습니다. 재시작 카운터가 59 까지 올라간 크래시루프였습니다.

거기서부터는 연쇄입니다. kubelet 이 없으니 static pod 을 집어가지 못하고, `kubeadm upgrade apply`
는 새 etcd 매니페스트를 써 두고 5분을 기다리다 해시가 바뀌지 않는다며 스스로 롤백했습니다. 겉으로
드러난 것은 `etcd static Pod hash did not change` 와 containerd 버전 경고였는데 **둘 다 증상**이고
원인이 아니었습니다.

그 파일을 다시 쓰는 것은 `kubeadm upgrade node` 입니다. 실측으로 확인했습니다:

....
[kubelet-start] Writing kubelet environment file with flags to file "/var/lib/kubelet/kubeadm-flags.env"
전: --node-ip=... --pod-infra-container-image=...
후: --node-ip=...
....

그래서 순서가 전부입니다. 패키지를 깔아도 kubelet 프로세스는 옛 바이너리로 계속 돌게 두고,
kubeadm 이 지나간 뒤에 재시작합니다. 같은 버전으로만 시험하면 절대 드러나지 않습니다. 플래그가
사라지는 마이너 경계에서만 나타납니다.

=== 패키지 설치는 유닛을 재시작하지 않습니다

`install-packages.sh --update` 는 패키지만 바꾸고 아무것도 재시작하지 않습니다. 교체된 패키지의
유닛은 전부 뒤에 오는 무언가가 더 많은 것을 알고 재시작합니다. containerd 와 docker 는 각자의
setup 스크립트가 설정을 렌더한 뒤에, kubelet 은 kubeadm 이 지나간 뒤에 노드 루프가 합니다.

여기서 한 번 더 하면 두 번 재시작이고, 그 첫 번째는 곧 다시 쓰일 설정 위에서 일어납니다.
실측으로 그것을 걷어내자 3노드 업그레이드가 666초에서 260초로 줄고, VIP 실패가 1건에서 0건,
keepalived 의 MASTER 전환이 1회에서 0회가 되었습니다. VIP 가 아예 움직이지 않았습니다.

=== 노드를 되돌리기 전에 그 노드의 apiserver 를 기다립니다

업그레이드가 컨트롤 플레인 노드를 로테이션에 되돌리는 시점이 너무 일렀습니다. kubeadm 은 static
pod 매니페스트를 다시 쓰고, 컨테이너를 바꾸는 것은 그 뒤의 kubelet 입니다. 그래서 업그레이드
명령이 돌아왔다는 것은 그 노드의 apiserver 가 떴다는 뜻이 아닙니다.

실측한 타임라인입니다.

....
01:55:45  apiserver 옛 컨테이너 종료
01:55:46  Server backend/node3 is UP (leaving forced drain)   <- 여기서 되돌렸다
01:55:50  Server backend/node3 is DOWN, Connection refused     <- 요청이 실패한 시각
01:55:57  apiserver 새 컨테이너 시작
....

drain 을 푸는 순간 로드밸런서는 그 서버를 곧바로 쓸 수 있는 것으로 봅니다. 헬스체크가 아직 UP
이기 때문입니다. 죽은 것을 알아채는 데 `inter` × `fall` 만큼 걸리고, 그 사이에 도착한 요청이
없는 apiserver 로 갑니다.

`wait-ready` 는 이것을 막지 못합니다. `ready` **뒤에** 실행되므로 이미 트래픽이 가기 시작한 뒤에
묻고, 그 시점에는 아직 UP 으로 보이므로 그대로 통과합니다.

그래서 kubelet 을 재시작한 뒤, 되돌리기 전에 그 노드의 apiserver 를 직접 기다립니다. VIP 가 아니라
`127.0.0.1` 로 묻습니다. VIP 는 아무 노드나 답하므로 작업 중인 노드가 살아났는지를 말해 주지
않습니다. `renew-certs` 는 이 순서를 처음부터 지켰고 150 번의 요청을 하나도 놓치지 않았는데,
업그레이드에는 그것이 빠져 있었습니다.

`--shutdown-delay-duration` 은 이 문제의 답이 아닙니다. 그 옵션은 종료하는 apiserver 가 `/readyz`
를 먼저 내려 로드밸런서에게 알아챌 시간을 주는 것인데, 여기서 로드밸런서는 이미 알고 있었습니다.
그 노드는 drain 상태였습니다. 문제는 아직 회복되지 않은 노드를 우리가 강제로 되돌린 것입니다.

== 사용자 레지스트리

클러스터가 프로비저닝되면 레지스트리가 둘이 됩니다. kubeadm 이 당겨 쓰는 `ki-cp-k8s-registry`
와, 그 위에서 돌 워크로드가 당겨 쓰는 `ki-cp-user-registry` 입니다. 담기는 것을 정하는 주체가
다릅니다. 앞의 것은 릴리스가 정하고 번들에 실려 오며, 뒤의 것은 클러스터를 운영하는 사람이
정하고 어떤 릴리스도 채워 주지 않습니다.

=== 쓰기가 플레이북 하나뿐인 이유

ki cp 노드마다 레지스트리가 하나씩 돌고, 파드는 그 순간 VIP 를 들고 있는 노드에서 당깁니다.
사용자가 VIP 로 직접 push 하면 그 한 노드에만 들어가고, 노드마다 내용이 달라집니다. 그러면 같은
파드가 어느 노드에 스케줄되느냐에 따라 뜨기도 하고 ImagePullBackOff 가 나기도 합니다. 원인과
증상이 멀어서 늦게 발견되는 종류의 고장입니다.

그래서 레지스트리는 readonly 로 돌고, `push-user-registry-images.yml` 이 모든 ki cp 노드에
같은 아카이브를 밀어 넣는 동안에만 쓰기가 열립니다.

=== 에어갭을 건너는 도구를 같이 줍니다

OCI layout 을 요구하면서 만드는 법을 주지 않으면 반쪽입니다. `tools/build-user-registry-images.sh`
가 목록 파일을 받아 아카이브 하나로 만듭니다.

crane 은 `bundle/bin/crane` 을 씁니다. 번들이 없으면 거부하고 `download-bundle.sh` 를 안내합니다.
각자 구해 온 crane 을 쓰면, 에어갭 양쪽에서 같은 물건이어야 할 도구가 두 버전이 됩니다.

=== 번들 빌드가 레지스트리를 고정합니다

`build-bundle-images.sh` 는 원래 프로젝트 루트의 `*-images.yml` 을 전부 훑었습니다. "파일을
추가하면 레지스트리가 추가된다"는 설계였는데, 사용자 레지스트리가 같은 모양으로 목록을 선언하기
때문에 그대로 두면 사용자 이미지가 릴리스 번들에 딸려 들어갑니다. 이제 `ki-cp-k8s-registry` 하나를
이름으로 고정합니다. 쓰인 적 없는 유연성이 실제 사고를 부르는 자리였습니다.

=== push 는 더하고 prune 은 뺍니다

아카이브는 "무엇을 더한다"이지 "무엇이 있어야 한다"가 아닙니다. push 를 선언적으로 만들면 목록에서
한 줄 빠뜨린 것이 곧 운영 중인 워크로드의 중단이 됩니다. 지우는 것은 `prune-user-registry.yml`
을 따로 부를 때만 일어납니다.

prune 은 기본적으로 아무것도 지우지 않고 지울 것을 출력합니다. `-e delete=` 를 줘야 실제로
지웁니다. 에어갭 안의 레지스트리는 그 이미지의 유일한 사본이라, 하나 더 지운 대가가 명령 한 번이
아니라 에어갭을 한 번 더 건너는 일입니다.

=== 지우려면 다이제스트여야 하고, 지워도 용량은 안 줄어듭니다

레지스트리는 태그로 지정한 매니페스트의 삭제를 거부합니다. 태그를 먼저 다이제스트로 풀어서
넘겨야 합니다. 그리고 삭제는 링크만 끊으므로, 용량은 `garbage-collect --delete-untagged` 가
스토리지를 훑어야 돌아옵니다. 레지스트리는 그동안 업로드가 없어야 하므로 내렸다가 올립니다.
이것 때문에 prune 은 한 노드씩 돕니다. 전부 동시에 내리면 워크로드 이미지를 당길 곳이 사라집니다.

=== readonly 는 DELETE 도 막습니다

`REGISTRY_STORAGE_DELETE_ENABLED` 를 켜 두어도 readonly 인 레지스트리는 삭제를 거부합니다.
둘이 따로 노는 설정이 아니라 readonly 가 위에 있습니다. 실측으로
`405 Method Not Allowed` 를 받았습니다.

그래서 prune 도 push 와 같이 지우는 동안에만 쓰기를 열고 닫습니다. 되돌리는 일은 가비지 컬렉션
함수 안에 묶어 두었습니다. 창이 열린 채 남으면 직접 push 가 가능해지고, 그러면 노드마다 내용이
달라지지 않게 하려고 만든 구조 전체가 무의미해집니다.

=== 가비지 컬렉션은 빈 저장소 디렉토리를 남깁니다

`garbage-collect` 가 회수하는 것은 blob 이고, 마지막 태그가 사라진 저장소의 디렉토리는 그대로
남습니다. `_catalog` 는 그 디렉토리 목록이라, 방금 지운 이미지가 카탈로그에 계속 보입니다.
당겨지지는 않지만 지운 사람은 안 지워졌다고 읽습니다. 그래서 가비지 컬렉션 뒤에 태그가 없는
저장소 디렉토리를 지웁니다. 레지스트리가 이미 내려가 있는 시점이라 안전합니다.


== etcd 백업과 복구

kubespray 는 이것을 핸들러로 둡니다. `Restart etcd` 알림을 받을 때만, 즉 etcd 를 건드리기
직전에만 돕니다. 그 발상은 그대로 가져왔습니다. 스냅샷이 값진 순간은 그 다음에 하는 일이
잘못됐을 때이고, 그때는 이미 늦습니다.

가져오지 않은 것이 둘 있습니다.

=== 받은 스냅샷을 읽어 봅니다

`etcdctl snapshot save` 가 0 으로 끝나도 파일이 쓸 수 있는 것인지는 별개입니다. 중간에 끊긴
스냅샷은 이름이 맞고 내용이 틀린 파일이고, 그것을 알게 되는 시점은 그것이 필요한 시점입니다.
`etcdutl snapshot status` 로 읽어 보고, 안 읽히면 지우고 실패합니다.

받는 동안에는 `.partial` 이름을 쓰고 읽어 본 뒤에 제 이름으로 옮깁니다. 그래야 디렉토리에
있는 파일은 전부 읽어 본 것이 됩니다.

`etcdutl` 이지 `etcdctl` 이 아닙니다. 파일 하나를 읽는 일이라 etcd 가 그 기능을 etcdctl 에서
떼어 냈고, etcdctl 쪽은 돌고 있는 클러스터에만 말을 겁니다.

=== 보관 개수를 둡니다

kubespray 에는 없습니다. 스냅샷은 제어 노드의 루트 파일시스템에 쌓이고, 거기서 계속 자라는
디렉토리의 끝은 디스크가 없어서 멈춘 컨트롤 플레인입니다. 이름에 고정폭 UTC 타임스탬프를
넣어서 이름순 정렬이 곧 오래된 순이 되게 했습니다.

=== 노드마다 받습니다

스냅샷 하나에 키스페이스 전체가 들어가므로 복구에는 아무 노드의 것 하나면 충분합니다. 그런데
한 부만 두면 그 한 부가 하필 잃은 노드에 있을 수 있습니다. 에어갭이라 오브젝트 스토리지나
외부 전송을 가정할 수 없어서, 노드마다 한 부씩이 할 수 있는 전부입니다. 노드 밖으로 빼는 것은
운영자 몫이고 README 에 적어 두었습니다.

=== 복구가 세 단계인 이유

`stop`, `restore`, `start` 로 나뉘어 있습니다. 복구는 컨트롤 플레인 전체가 한꺼번에 하는 일인데
ansible 은 태스크가 아니라 **플레이** 사이에서만 노드를 맞춥니다. 한 태스크에 셋을 몰아넣으면
노드마다 제 속도로 진행해서, 아직 멈추지 않은 멤버가 교체 중인 상태를 계속 서비스하거나 먼저
올라온 노드가 혼자 새 클러스터를 이루고 나머지를 거부합니다.

그래서 플레이북이 세 개의 플레이로 호출합니다. 모든 노드가 멈춘 뒤에 복구가 시작되고, 모든
노드가 복구된 뒤에 시작됩니다.

=== 복구는 고치는 것이 아니라 새로 만드는 것입니다

스냅샷에서 복구된 멤버들은 새 클러스터 id 를 받습니다. 기존 멤버와 합류하지 못하고, 스냅샷
이후에 쓰인 것은 없습니다. 그래서 `--confirm-data-loss` 없이는 거부하고, 플레이북도
`-e confirm_data_loss=` 를 요구합니다. 이것이 맞는지는 클러스터가 그 사이에 한 일에 대한
질문이라 여기서 판단할 수 없고, 운영자만 답할 수 있습니다.

`--initial-cluster-token` 은 복구 한 번에 하나씩 제어 노드에서 만들어 전 노드에 같은 값을
넘깁니다. 서로 다른 토큰으로 복구된 멤버들은 클러스터를 이루지 못합니다.

기존 데이터 디렉토리는 지우지 않고 이름만 바꿉니다. 엉뚱한 스냅샷으로 복구한 것을 알게 되는
순간이 그 데이터가 가장 아쉬운 순간인데, 그때는 스냅샷을 받을 대상이 이미 없습니다.

=== manifest 를 옆 디렉토리로 옮깁니다

정적 파드를 멈추는 방법은 kubelet 이 보는 디렉토리에서 manifest 를 빼는 것입니다. 같은
디렉토리 안에서 이름만 바꾸면 안 됩니다. kubelet 은 그 디렉토리의 **모든** 파일을 읽으므로
이름을 바꾼 사본은 같은 정적 파드가 하나 더 있는 것이 됩니다.

apiserver 도 같이 내립니다. etcd 에 말을 거는 유일한 것이고, 교체 중인 etcd 를 상대로 띄워 두면
크래시루프만 도는 파드가 남습니다.

manifest 가 사라진 것은 kubelet 에게 파드를 내리라고 말한 것일 뿐이라서, etcd 컨테이너가 실제로
사라질 때까지 기다린 다음에 데이터 디렉토리를 건드립니다.
